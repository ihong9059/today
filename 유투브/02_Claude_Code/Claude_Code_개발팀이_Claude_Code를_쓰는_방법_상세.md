### 1. 1년간의 변화 — 프롬프트 감시에서 목표 위임으로 (00:00–02:20)
[바로가기](https://www.youtube.com/watch?v=Bo2ImHzgOwc&t=20s)

#### 핵심 메시지
1년 전 "프롬프트 보내고 권한 요청 수락하던" 방식에서, 이제 업무의 70~80%를 Slack 통합 에이전트(Claude 태그)에 위임하는 방식으로 전환했다.

#### 상세 내용
- 팀원 업무의 대부분이 Claude 태그를 통해 처리됨. "이 클래스를 구현하세요" 같은 초기의 단순 문제와는 차원이 다른 문제를 맡김
- Slack 네이티브 통합의 강점: 에이전트가 팀의 제품 결정 이력 등 **추가 맥락 정보에 직접 접근**해 의사결정에 통합
- 나머지 20%는 TUI나 데스크톱 앱 — 세부 수정이나 세밀한 관리가 필요할 때만
- 예전에는 녹취록(transcript)·개별 도구 호출·모델의 모든 결정에 신경 썼지만, 이제는 "목표가 있고 이 목표를 달성하고 싶다"고 **목표 자체를 모델에게 위임**

#### 주요 발언
> "현재 제 업무의 70~80%는 클라우드 태그에서 이루어지고, 나머지 20% 정도는 TUI 버전이나 데스크톱 앱을 열어서 세부적인 부분을 수정하거나 클로드를 세밀하게 관리하고 싶을 때 사용합니다." (01:25)

> "이제는 좀 더 넓은 시각으로 '나는 목표가 있고, 이 목표를 달성하고 싶다'라고 생각하며 그 목표를 모델에게 맡겨 달성하게 된 것 같습니다." (01:45)

### 2. 기술 유효기간 2개월 — Claude Code 개발이 다른 이유 (02:20–05:30)
[바로가기](https://www.youtube.com/watch?v=Bo2ImHzgOwc&t=140s)

#### 핵심 메시지
과거 제품 기술의 유효기간은 몇 년이었지만 AI 제품은 **2개월마다 근본적으로 바뀐다**. 하네스 기능은 "현재 모델의 오류 모드 보완"이며, 모델이 좋아지면 기꺼이 제거해야 한다.

#### 상세 내용
- 최첨단에 머물러야 경쟁력이 있으면서도, **지금 이 순간의 사용자에게 가치를 제공**해야 하는 균형 (예술+과학)
- Claude Code 팀의 독특한 운영: **모델을 면밀하게 따라가는 소규모 팀** — 모델이 좋아지면 "완전히 새로운 능동형 에이전트를 만들자"며 권한 시스템 재작성 등 큰 변화를 동시에, 아주 빠르게 수행
- Claude Code 팀은 "소프트웨어 개발이 나아갈 방향을 보여주는 **과장된 시간의 방**(압축된 미래)" — 대부분 제품은 유통기한이 이렇게 짧지 않지만, 엔지니어라면 기능의 발전 방향을 이해해야 함

#### 언급된 사례/에피소드
- **할 일 목록(Todo List)의 흥망**: Sonnet 3.5 시절 모델은 장기 관점이 없어 "다섯 가지 일을 시키면 세 가지만 하고 포기" → 할 일 목록을 주니 극적으로 개선 → **1년 후 더 복잡한 메모리 상태가 생기며 사실상 불필요해짐**
  - 시사점: "만들어내는 것들에 너무 집착하지 말 것 — 꽤 빨리 사라진다"

#### 주요 발언
> "인공지능 모델들을 보면, 마치 기술이 2개월마다 근본적으로 바뀌는 것 같고, 시간이 흐를수록 그 변화가 압축되는 듯한 느낌도 듭니다." (02:38)

> "이러한 기능들을 클로드 코드 하네스에 내장하는 것은 현재 모델이 가지고 있는 몇 가지 오류 모드를 보완하기 위한 것입니다. 모델이 더 좋아짐에 따라 '우리가 구축했던 이 모든 기능들은 더 이상 필요하지 않네요. 없애버릴 수 있겠어요'라고 말할 수 있는 자유가 생겼습니다." (04:04)

### 3. AskUserQuestion 도구 — 유행을 따라잡은 또 하나의 예 (05:30–06:40)
[바로가기](https://www.youtube.com/watch?v=Bo2ImHzgOwc&t=339s)

#### 핵심 메시지
사용자에게 질문하는 도구를 오랜 시간 들여 설계했지만, 최근에는 Claude가 스스로 HTML 아티팩트(목업 포함)를 생성해 질문하는 방식으로 대체되는 중 — 기능의 수명 주기가 또 반복됐다.

#### 상세 내용
- 원래 의도: Claude 캐릭터가 사용자와 상호작용하게 하려는 것 → "그냥 호출할 수 있는 도구라면?"으로 전환
- Claude가 이 도구를 제대로 호출하게 만드는 것이 정말 어려웠고, 직접 설계 후에야 잘 작동하기 시작
- 최근에는 이 도구를 거의 사용하지 않음 — 아티팩트가 넥타이 이미지·목업이 담긴 HTML로 직접 질문
- 개발 과정의 본질: 권한·시각화 같은 **기본 요소(primitives)를 만들어 층(layer)으로 쌓는 것**

#### 주요 발언
> "그 도구를 설계하는 데 정말 오랜 시간이 걸렸어요. … 그러다가 최근에는 그 도구를 거의 사용하지 않게 됐어요. 제가 아티팩트를 생성했는데, 그 아티팩트가 저에게 질문을 하더군요." (06:01)

### 4. 로컬 → devbox → 웹 → 클라우드: 루프(루틴)의 탄생 (06:40–08:52)
[바로가기](https://www.youtube.com/watch?v=Bo2ImHzgOwc&t=403s)

#### 핵심 메시지
"노트북을 끄면 에이전트가 죽는" 문제에서 출발해 원격 devbox → 웹 Claude Code(호스팅 컨테이너) → 클라우드 상시 실행으로 진화했고, 이것이 매일 반복되는 루틴(예: 피드백 자동 분류·해결)을 가능하게 했다.

#### 상세 내용
- 진화 경로: 노트북 로컬 실행 → 퇴근하면 에이전트 중단 → 원격 호스팅 개발 환경(devbox, 생산성 10배) → SSH 접속의 번거로움 → **웹 Claude Code = 백그라운드에서 계속 실행되는 호스팅 컨테이너**
- 핵심 통찰: "**로컬에서 실행되려면 클라우드에서 실행되어야 한다**"
- 클라우드 실행이 열어준 것 — 루틴: 매일 모든 피드백을 살펴보고 중요도 분류 후 해결 가능성 높은 문제부터 처리
- Boris가 자주 언급하는 "순환적 여정": 세션 중 지시 → 세션 경계를 넘어 자율적으로 버그 수정

#### 주요 발언
> "루틴을 만들어서 매일 우리가 받는 모든 피드백을 살펴보고 중요도에 따라 분류한 다음, 실제로 해결할 가능성이 높은 문제부터 해결하는 식으로 진행할 수 있습니다." (08:17)

### 5. 코드 리뷰의 재편 — 인간은 큰 그림, Claude는 디테일 (08:52–11:10)
[바로가기](https://www.youtube.com/watch?v=Bo2ImHzgOwc&t=532s)

#### 핵심 메시지
코드 생성량이 폭증하는 상황에서, 코드 리뷰 봇이 사소한 지적을 전담하고 인간 리뷰어는 API 구조·서비스 경계 같은 **추상적·구조적 판단에 집중**하게 됐다.

#### 상세 내용
- 과거 인간 리뷰 문화: "사소한 문제 세 가지를 지적하는 것"은 사실상 '내가 읽었다'는 신호에 불과했음
- 이제 그런 것은 Claude가 스스로 파악·해결 → 인간 리뷰에서 중요도 하락
- Claude가 PR 작성 시점에 몰랐던 맥락(왜 이 API 구조인지, 서비스 경계가 왜 거기인지)을 리뷰에서 담당자에게 전달하는 것이 가치
- 코드 리뷰가 **대규모 팬아웃(의견 확산)의 첫 사례**: "어떻게 모든 버그를 찾아낼까?" → 크게 펼치고 하나로 합침 = **test-time compute** (추론 시간·계산을 문제에 대량 투입)

#### 주요 발언
> "누군가가 코드를 검토하고 사소한 문제점 세 가지 정도만 골라서 올리는 게 흔한 일이었죠. 그건 마치 내가 이 코드를 읽었다는 걸 너에게 알리는 신호 같은 거였어요." (09:31)

> "코드를 한 줄 한 줄 읽으면서 사소한 부분을 꼬투리 잡아야겠다는 생각에 빠지지 않고, 인간 코드 리뷰어가 추상적인 개념까지 생각할 수 있게 됩니다." (10:27)

### 6. 워크플로우 — 팬아웃 + 적대적 검증 + 결정론적 조율 (11:10–14:04)
[바로가기](https://www.youtube.com/watch?v=Bo2ImHzgOwc&t=671s)

#### 핵심 메시지
버그 찾기를 넓게 팬아웃한 뒤 **각 버그를 3가지 다른 관점의 적대적 검토로 검증**해 중요한 것만 남긴다. 그리고 에이전트가 하위 에이전트 조율 코드를 직접 작성 — 결정론적 코드와 LLM 동작의 혼합이 신뢰의 근거다.

#### 상세 내용
- 버그 리뷰 워크플로우: 넓은 팬아웃으로 버그 수집 → 버그별로 3가지 관점에서 실존 여부 적대적 검증 → 사용자 주의가 필요한 중요 버그만 잔존
- 같은 패턴이 범용 적용: 성능 버그, 심층 연구(deep research) 등
- 정보가 부챗살처럼 퍼진 뒤 다시 걸러내는 **맵리듀스(MapReduce) 문제** — 사람이 읽을 수 있게 필터링 필수, 확신은 test-time compute 투입으로 확보
- Claude는 **자기만의 하네스를 만드는 데 능숙**: 팬아웃 구조·토폴로지·에이전트 간 출력 연결을 스스로 설계
- 신뢰의 핵심: 에이전트가 for 루프 등 조율 코드를 작성하면 "**항목 하나도 건너뛰지 않는다**"는 결정론적 보장

#### 언급된 사례/에피소드
- **타호(Tahoe) 가족여행 계획**: "다음 주에 부모님 모시고 타호에 가는데 어디 묵을지" → 타호 호텔·에어비앤비 등 10가지 검색 요청 팬아웃 → 흥미로운 결과 선별 에이전트 → 검증 에이전트 → 최종 결과. 심층 연구도 코드 리뷰와 동일한 구조임을 보여주는 예

#### 주요 발언
> "각 버그에 대해 세 가지 다른 관점이나 시각에서 버그를 살펴보고 실제로 버그가 존재하는지 확인하는 적대적 검토를 수행할 수 있습니다." (11:33)

> "에이전트가 하위 에이전트들을 조율하기 위한 코드를 작성한다는 것입니다. 이것은 결정론적인 코드 정의 동작과 에이전트 방식의 LLM 동작이 멋지게 혼합된 것입니다." (13:28)

> "'아, 맞다. for 루프는 항목 중 하나라도 건너뛰지 않겠구나'라고 생각했다." (13:50)

### 7. Claude 태그 — 녹취록에서 완전히 분리된 첫 UI (14:04–18:39)
[바로가기](https://www.youtube.com/watch?v=Bo2ImHzgOwc&t=844s)

#### 핵심 메시지
Claude 태그(Slack 에이전트)로 Claude 태그 자체를 개발 중이며, 이는 **토큰 스트림보다 한 단계 높은 추상화**에서 일하는 첫 인터페이스다. 내면 독백은 보이지 않고 Claude가 언제·무엇을 말할지 스스로 선택한다.

#### 상세 내용
- 개발 목표: Claude 태그가 자기 자신을 개발하는 데 제약이 없도록 — 사람이 소프트웨어를 개발·e2e 테스트하는 데 필요한 모든 것을 기계가 대신하게 만드는 것
- Slack 메시지는 도구 호출로 발송되고, 내면 독백은 보이지 않음(전체 녹취록 링크는 존재). 처음엔 불안했지만 결국 **모델이 충분히 좋아져 녹취록 검토가 불필요**해짐
- 검증 문화: Claude가 PR을 생성하면 테스트를 거치고 **결과 스크린샷을 보내줌** → 확신 확보. 직접 확인이 필요하면 자체 녹화를 시키거나 복제해서 검증

#### 언급된 사례/에피소드
- **구매(procurement) 도구 개발 전 과정을 Slack에서**: ① 아이디어 → "누구랑 얘기해야 할까?" 이해관계자 수집 ② 목업 제작(모든 게 Slack이라 **휴대폰으로 확인**) ③ 구현 ④ 확신이 안 서서 이벤트(계측) 추가 ⑤ 내부 배포 ⑥ Claude 태그가 사용 현황 모니터링, 피드백 남으면 본인을 태그 ⑦ 퍼널 이탈 발견 → 구체적 지시 대신 "**퍼널을 개선해 달라**"고 높은 차원에서 위임
  - 시사점: 검증·코드 리뷰·피드백(지표·Slack·GitHub 이슈)이 모두 Claude Code의 기본 요소로 연결됨

#### 주요 발언
> "지금 우리는 클로드가 출력하는 실제 토큰보다 한 단계 높은 추상화 수준에서 작업하고 있는 것과 같습니다." (15:02)

> "클로드가 언제, 무슨 말을 할지 스스로 선택한다는 점에서 정말 자유로워진 것 같기도 해요." (15:34)

### 8. 회고 — 사고방식의 전환과 변하지 않는 본질 (18:39–22:23)
[바로가기](https://www.youtube.com/watch?v=Bo2ImHzgOwc&t=1119s)

#### 핵심 메시지
요즘 소프트웨어 엔지니어에게 가장 어려운 것은 "이제 무엇이 가능할까?"를 계속 묻는 **사고의 자유로움 유지**다. 디테일 장인정신은 Claude에게 넘기고, 아이디어→시제품→제품의 속도에 집중한다.

#### 상세 내용
- 지난 1년: Claude Code → 자동 모드·메모리·워크플로우 등 기본 요소 축적
- 그리워하는 것: 성능 엔지니어링의 즐거움 — "클로드가 지금의 저보다 훨씬 잘하지만, 성능 향상의 혜택은 여전히 누린다"
- 사고 전환: 세부에 깊이 파고들기 → 넓은 시각, 특정 기법 완벽 연마보다 아이디어 실현 속도
- 소프트웨어 엔지니어링 = "변화의 직업": 프레임워크 없는 손 JavaScript → 프레임워크·컴파일러 → 지금은 속도만 빨라졌을 뿐, **본질은 변함없이 문제 해결**

#### 언급된 사례/에피소드
- **Mac OS X 10.4 Aqua 버튼 CSS 재현**: 개인 웹사이트용으로 방사형 그라디언트 레이어를 쌓아 완벽 재현하는 데 하루 종일 — "이제 그런 일은 클로드가 다 해줄 수 있다"
- **7~8살 파워포인트 게임**: 코딩을 몰라 파워포인트 클릭 요소로 게임을 만들던 아이 → 이제 "기술적 능력이 없다"고 말할 필요 없이 목표를 분해해 Claude와 협력하면 됨

#### 주요 발언
> "요즘 소프트웨어 엔지니어에게 가장 어려운 점은 바로 그런 사고방식의 자유로움을 유지하는 것 같아요. 늘 '자, 이제 무엇이 가능할까?'라고 생각해야 했죠." (18:59)

> "제가 어떤 아이디어를 떠올리든, '아, 나한테는 기술적인 능력이 없어'라고 말할 필요가 없다는 뜻이에요." (21:19)

> "서로 다른 문제를 해결하는 것 같지만, 어쨌든 문제 해결이라는 건 변함없는 거죠." (22:12)

# [한영자막] Claude Code 팀이 새로 공개한 INTENT.MD의 정체와 AI-Native 개발 방식 - 상세 분석

## 영상 정보
- **채널**: Tech Bridge (원본: Switch Dimension — 강사가 자신의 코스·워크플로우를 함께 소개)
- **주제 원천**: Anthropic(Claude Code 팀, Boris Cherny 언급)이 공개한 **AI-Native SDLC 플레이북**
- **재생시간**: 15:11
- **업로드**: 2026-09-04
- **링크**: https://www.youtube.com/watch?v=rGaSkBWjoHA

> ⚠️ 한국어 자막은 영상에 하드코딩되어 있어, 본 분석은 **영어 자동 자막 기반 번역·정리**입니다. 자막 오기 보정: "Entropic/Antropic"=Anthropic, "claw code"=Claude Code, "Baris"=Boris (Cherny), "Matt PCO"=Matt Pocock 추정.

**한 줄 요약**: "코드가 아니라 **프로세스가 병목**"이 된 시대, Anthropic이 제안하는 AI-Native SDLC — 계획 단계에서 에이전트가 나를 인터뷰해 `intent.md`를 만들고, intent → spec → plan으로 이어지는 **아티팩트 체인**을 통해 독립 에이전트들이 SDLC 전 단계(계획·설계·구축·테스트·배포·유지보수)를 나눠 수행하되, 중요한 리뷰에는 인간이 남는다.

## 구간별 상세 내용

### 1. 배경 — "코드는 더 이상 병목이 아니다. 프로세스다" (00:00–01:10)
[바로가기](https://www.youtube.com/watch?v=rGaSkBWjoHA&t=0s)

#### 핵심 메시지
전통 SDLC(계획→설계→구축→테스트→배포→유지보수)에서 가장 길고 비쌌던 **구축(build) 단계가 에이전트로 압축**되어 2배 빨라졌다. Anthropic의 질문: "나머지 단계들도 에이전트로 어떻게 개선할 것인가?"

#### 상세 내용
- 이 문서는 Claude Code 팀(Boris 포함)이 실제로 일하는 방식을 담은 AI-Native SDLC 플레이북
- 구축 단계에서 되찾은 시간을 다른 단계 개선에 재투자하는 것이 문서 전체의 구도

#### 주요 발언
> "핵심 아이디어는 이것입니다: 코드는 더 이상 병목이 아닙니다. 여러분의 프로세스가 병목입니다." (00:38)

### 2. 계획 단계 — 에이전트가 나를 인터뷰해 intent.md를 만든다 (01:10–04:37)
[바로가기](https://www.youtube.com/watch?v=rGaSkBWjoHA&t=70s)

#### 핵심 메시지
요구사항 수집·PRD·워크숍 대신, **에이전트가 완전히 이해할 때까지 반복 질문**하게 하고 그 결과를 `intent.md`(사람이 읽을 수 있고 기계가 실행할 수 있는)로 저장한다. 이것이 아티팩트 체인의 시작이다.

#### 상세 내용
- 디스커버리 스킬 예시: 강사 자작 "Switch Dimension Discovery", Matt Pocock의 "Grill Me", Cursor의 "Requirements Discovery" — 도구는 달라도 원리는 같음
- 목적: 나의 경험·도메인 지식·맥락을 대화에 최대한 쏟아내면 에이전트가 페인 포인트를 종합해 intent.md로 캡처
- 전통 방식(백로그→유저 스토리→스토리 포인트→소유권 이전→핸드오프) vs AI-Native(**발안자(originator)가 Claude와 브레인스토밍 후 결과를 intent.md로 기록**)
- **아티팩트 체인**: intent.md → spec.md → plan.md … 단계마다 산출물이 쌓임. 프로젝트에 `intent/` 폴더를 만들어 저장
- **발안자는 누구나 가능**: 버그를 신고하는 고객, 기능 아이디어가 있는 PM, 프로세스 개선을 기록하려는 개발자 — 전문가일 필요 없음. 단, 작성 후 발안자가 에이전트가 쓴 내용을 재검토해 양쪽이 만족해야 함
- 운영 팁: intent 종류를 파일명 접두어로 구분. 백로그는 마크다운 정렬 파일·Notion·Linear로 관리하고 제품 오너가 검토 — 또는 **에이전트가 백로그를 트리아지**(frontend/규모/기능 여부/우선순위 태그 부여)
- 표준화 강조: "워크플로우를 너무 자주 바꾸지 말 것 — 팀·에이전트·스킬이 같은 워크플로우 위에서 성장"

#### 언급된 사례/에피소드
- **다크 모드 기능 추가**: 에이전트와 원하는 것·동작 방식을 대화 → intent.md 생성 → `intent/` 폴더에 저장하는 전체 흐름 시연

#### 주요 발언
> "에이전트가 여러분이 만드는 기능이나 해결하려는 버그를 완전히 이해할 때까지 반복해서 질문하게 하세요." (01:36)

> "AI 네이티브 세계에서는 이슈·기능·제품의 발안자가 Claude와 브레인스토밍하고 그 결과를 intent.md로 적습니다." (02:10)

### 3. 스펙 단계 — intent 승인 시 자동으로 spec 생성 (04:37–05:58)
[바로가기](https://www.youtube.com/watch?v=rGaSkBWjoHA&t=277s)

#### 핵심 메시지
intent가 커밋/승인되면 **hook이나 프로세스로 spec.md를 자동 생성**한다. 생성 방식엔 정답이 없고, 조직의 모범 사례(agents.md·스킬·스타일 가이드)가 거버넌스로 적용되게 하는 것이 핵심.

#### 상세 내용
- Anthropic 제공 샘플 프롬프트 요지: "첨부된 intent.md를 읽고 요구사항·설계 스펙을 작성하라. 사용 가능한 스킬을 적용해 계획하고 브랜드 가이드라인을 준수하며 spec.md에 완전히 문서화하라"
- 구현 선택지: Cursor/Claude Code/Codex의 기본 플랜 모드 사용, 또는 팀 방식에 맞춘 맞춤 스펙 생성 스킬 제작
- 스타일 가이드·정책·스킬 준수는 **체인의 모든 아티팩트에 적용**되어야 할 거버넌스 고려사항

### 4. 구축 단계 — plan.md는 단독으로 실행 가능해야 한다 (05:58–09:44)
[바로가기](https://www.youtube.com/watch?v=rGaSkBWjoHA&t=358s)

#### 핵심 메시지
intent+spec을 넣어 plan.md를 만들고, "**무엇이 바뀌면 깨질 수 있는가**"로 계획을 심문한다. 완성된 plan.md는 intent·spec 참조 없이도 엔지니어(또는 새 에이전트)가 그대로 구현할 수 있어야 한다 — **독립 에이전트 간 핸드오프**가 전제이기 때문.

#### 상세 내용
- 하나의 에이전트가 전 단계를 수행하지 않음 — 컨텍스트 윈도우가 분리된 독립 에이전트·서브에이전트들이 단계를 나눠 맡으므로, **이전 대화 이해 없이 처음부터 시작할 수 있도록 문서로 핸드오프**
- plan.md 구성: 변경할 파일 목록 / 작업 순서(할일 목록) / 리스크·제약 / **증명(proof)** — 성공 기준과 검증 체크(린트·테스트 같은 결정론적 형태 가능)
- **거버넌스**: plan·intent·spec의 버전, 누가 손댔는지, 어떻게 진화했는지 저장 — 기업들이 특히 어려워하지만 선행·후행 지표 추적, **DORA 메트릭 증명**, AI 효과 측정에 필수
- **auto 모드 가속 팁**: 잠긴 환경에서 권한을 하나씩 수락하며 정책(공정 사용 범위·접근 도구·웹 소스·패키지)을 축적 → Cursor/Claude 권한으로 잠그면 개입 없이 에이전트가 훨씬 빨라짐. "블래스트 래디어스(폭발 반경)를 좁게"
- **git worktree**: 여러 에이전트가 동시에 여러 작업 수행. 좋은 하네스는 플랜을 독립 태스크로 분할하고 병렬 가능하면 worktree 사용 (Cursor·Claude Code·Codex에 내장)
- **hook 활용 예**: 구현 완료 시 plan 자동 갱신 / 특정 폴더 작업 차단 / 승인 안 된 npm 패키지 업그레이드 방지
- 린팅 = 결정론적 검사 (통과/실패의 이진 결과)

#### 주요 발언
> "이 plan.md 파일만 엔지니어에게 넘겨도 intent나 spec 문서를 참조하지 않고 변경을 구현할 수 있는 수준까지 가야 합니다." (06:24)

> "'무엇이 바뀌면 깨질 수 있는가'를 물어 계획을 심문하라는 것이 Anthropic의 제안입니다." (06:19)

### 5. 테스트 단계 — 인간 QA 전에 에이전트가 최대한 검증 + 상시 eval (09:44–11:24)
[바로가기](https://www.youtube.com/watch?v=rGaSkBWjoHA&t=584s)

#### 핵심 메시지
전통 SDLC에서 며칠씩 기다리던 QA 사이클을, **에이전트가 먼저 테스트 작성·린트·빌드·E2E·스크린샷까지 끝내는** 방식으로 압축한다. 나아가 스킬 변경·모델 업그레이드마다 eval을 돌려 SDLC 자체의 회귀를 감지한다.

#### 상세 내용
- 에이전트 테스트 범위: 테스트 작성·통과 확인 → 린트·빌드로 오류 제거 → Playwright·TestSprite·Cursor Browser로 실제 소프트웨어 조작·스크린샷
- Cursor 클라우드 에이전트는 서버를 직접 띄워 테스트하고 **화면 녹화**까지 제공
- **연속 평가(continuous evals in CI)**: 과거에 해결한 이슈 ~20개 + 기대 결과 세트를 보관 → 새 모델·새 스킬·작업 방식의 근본 변경 시마다 실행해 **개발 수명 주기가 퇴보하는지 확인** (Anthropic 제안, 최적화 단계)

#### 주요 발언
> "AI SDLC에서는 인간 엔지니어나 QA가 접근하기 전에 에이전트가 가능한 한 많은 테스트를 하기를 원합니다." (10:04)

### 6. 배포 단계 — 비동기 PR 리뷰와 배포 차단 hook (11:24–12:51)
[바로가기](https://www.youtube.com/watch?v=rGaSkBWjoHA&t=684s)

#### 핵심 메시지
에이전트가 자기 브랜치/worktree에서 PR을 만들면, **별도의 Claude 인스턴스가 정책·보안 프로토콜에 비추어 비동기로 리뷰**한다. 거버넌스 hook으로 승인자·릴리스 날짜 조건 미충족 시 배포를 차단할 수 있다.

#### 상세 내용
- CI 일부로 PR 생성 시 Claude가 개입해 정책·보안 검토 — 에이전트가 PR에 수정 요구 코멘트를 달 수 있고, **그 코멘트를 또 다른 Claude Code 인스턴스가 검토** (각자 다른 agents.md·skills·hook·린트 정책 보유 가능)
- 거버넌스 hook 예: 특정 권한 부여·특정인 승인·릴리스 날짜 충족 전까지 배포 차단
- PR 완료 후 보안·CI 프리뷰 에이전트 실행: 결정론적 린트·게이트 체크 + Cursor Bugbot·Claude 보안 리뷰 같은 에이전트 검사 병행

### 7. 유지보수 단계 — 알림이 사람 대신 Claude를 깨운다 (12:51–15:11)
[바로가기](https://www.youtube.com/watch?v=rGaSkBWjoHA&t=771s)

#### 핵심 메시지
가장 야심찬(aspirational) 단계. 새벽 3시 알림·방치된 백로그 티켓 대신, **장애·티켓·Slack 메시지·스케줄이 사람 개입 없이 Claude를 호출**하고, Claude가 로그를 진단해 **스스로 intent.md를 생성**하며 순환이 다시 시작된다.

#### 상세 내용
- 전통 유지보수 = 반응적: 점심 중·온콜·새벽 3시 서버 다운 알림, 백로그 과다로 무시되는 티켓
- AI SDLC: 지켜야 할 메트릭을 정의(예: 페이지 다운, API rate limit 급증) → 트리거 시 에이전트가 진단하고 intent 생성 + 제안 세트 제시 — "컴퓨터 앞에 앉기도 전에"
- 문서 전체의 전제: **에이전트를 구축 단계에서만 쓰던 시대를 지나 SDLC 전체에 고용** — 각 단계의 인간 시간을 줄이되, 중요한 리뷰 단계에는 인간을 유지. 중요도가 낮으면 에이전트 단독 운영도 가능
- 강사의 균형 조언: "superpowers나 BMAD, 자체 개발 버전을 쓰고 있다면 Anthropic 방식을 채택하려고 전부 버리지 말 것" — 루프, 그래프 엔지니어링, 완전 자동 루프, 대규모 오케스트레이션까지 접근법은 다양하고 **만능 정답은 없음**

#### 주요 발언
> "장애, 새 티켓, Slack 채널 메시지, 또는 스케줄이 사람 개입 없이 Claude를 호출해 유지보수를 수행합니다." (13:26)

> "각 단계에 들어가는 인간의 시간을 어떻게 줄이되, 중요한 리뷰 단계에는 인간을 루프에 유지할 것인가." (14:17)

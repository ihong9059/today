## 한눈에 보는 핵심 요약

> **"각 요인이 10배씩 커지면 우리는 1만 배 커진 데이터를 핸들링해야 한다."**

- AI 시대에 메모리 수요가 폭증하는 이유는 **모델 크기 × 사용자 수 × 컨텍스트 길이 × 에이전트 개수**가 **곱하기(더하기 아님)**로 작용하기 때문. 각각 10배 → 총 1만 배.
- 그 폭증의 실체적 원인이 **KV캐시(KV Cache)**: 한 번 GPU로 연산한 결과를 다시 계산하지 않으려고 메모리에 계속 쌓아두는 임시저장. 대화가 길어질수록·정교해질수록 무한 누적.
- **HBM**은 대역폭(밴드위스)은 최고지만 GPU 패키지 안에 물리적으로 갇혀 용량 확장에 한계(발열·공간·수율). → HBM에는 가치 높은 데이터만, 나머지는 외부 메모리로.
- **CXL(Compute Express Link)**: 여러 서버가 하나의 "공유 메모리 풀(=공유 오피스/공용 도마)"을 **복사 없이 내 메모리처럼** 읽어 쓰는 차세대 연결 표준. 클라우드 메모리 실사용률 35% → 70~80%로 2배 개선 = 설비투자 절반.
- **엑시나의 차별화**: ① 메모리 근처에서 연산(Near-Data Processing) — RISC-V 코어 수천 개 탑재 ② SSD를 메모리처럼 보여주는 **인피닛 메모리(Infinite Memory)**. 목표는 전통 서버 10대 일을 1대로 = **10배 효율**.

### 3. 왜 메모리가 이렇게 중요해졌나 — 빅데이터에서 AI로 (03:35-08:20)
[바로가기](https://www.youtube.com/watch?v=5cOS2mK4l_M&t=215s)

#### 핵심 메시지
메모리는 폰노이만 컴퓨터의 CPU만큼 본질적 요소였고, AI 시대에 그 수요가 **곱셈적으로** 폭증한다.

#### 상세 내용
- 클라우드 시대 이후 모든 데이터가 메모리에 저장 → 10~15년 전 "빅데이터" 유행. 하지만 "쌓아둔 데이터로 어떻게 돈 벌 것인가?"라는 질문에 사그라듦.
- 그 답이 **AI**: "인류가 쌓아온 데이터에서 가치(돈 되는 데이터)를 찾아내는 것."
- AI가 스스로 데이터를 **생성(generation)**하기 시작 → 사람이 만든 데이터 + AI가 만든 중간 결과물이 메모리에 계속 누적.
- 카이스트 김정호 박사 인용: "앞으로 메모리가 천 배쯤 필요할지도 모른다."

#### 언급된 사례/에피소드
- **메모리 수요 1만 배 공식**: 4가지 요인이 각각 10배씩 커지면 곱셈으로 작용
  - ① 모델 사이즈 증가 ② 사용자(유료 구독자) 증가 ③ 컨텍스트(입력) 길이 증가 (1년에 10배) ④ 에이전틱 AI로 에이전트 개수 증가
  - 시사점: 10 × 10 × 10 × 10 = **10,000배**. "더하기가 아니고 곱하기."
- **입력 방식 변화**: 이제 사용자가 타이핑하지 않고 책·프로젝트 코드 전체를 통째로 밀어 넣음 → 입력도 기하급수적 증가.

#### 주요 발언
> "다 각각이 열 배씩 커지면 우리는 만 배 커진 데이터를 핸들링해야 되는 상황에 가는 겁니다."

> "AI가 뭐냐? 인류가 지금까지 쌓아왔던 데이터에서 가치를 찾아내는 거다. 돈 되는 데이터를 찾아내는 게 AI가 제일 잘하는 거다."

### 5. KV캐시 — 메모리 폭증의 진짜 원인 (09:38-14:03)
[바로가기](https://www.youtube.com/watch?v=5cOS2mK4l_M&t=578s)

#### 핵심 메시지
KV캐시는 "한 번 GPU로 계산한 것을 다시 계산하지 않게 만드는" 임시저장. AI 서비스의 실질적 병목.

#### 상세 내용
- GPU 연산은 매 토큰마다 이전 토큰까지 다시 연산해야 해서 비효율 → 이전 계산 결과를 메모리에 두고 참조 = **KV캐시**.
- GPU가 워낙 비싸므로 재연산 대신 메모리 저장이 훨씬 효율적 → 계산 결과가 계속 쌓임 → 쌓일수록 좋지만 그만큼 메모리 수요 증가.
- KV캐시가 클수록 인프라를 훨씬 효율적으로 구성 가능 → AI가 인퍼런스(inference) 스케일로 갈수록 메모리 중요.

#### 언급된 사례/에피소드
- **AI 대화창 경험**: 한 달째 이어지는 대화창에서 AI가 앞 내용을 다 기억하는 것이 KV캐시 덕분. 초기 질문은 응답이 느리지만 이후 빨라지는 것 = KV캐시 참조가 쌓였다는 신호.
  - "네가 지난번엔 그랬지 않니?" 하고 지적하는 것도 KV캐시 형태의 기억.
- **무식한 질문(진행자)**: "DRAM은 전원 끄면 사라진다는데 KV캐시도 끄면 사라지나?" → 답: 메모리 내용은 사라질 수 있으나 스토리지 백업 등 다양하게 가능. 핵심 논점은 아님.

#### 주요 발언
> "KV캐시가 뭐냐? 한 번 GPU로 계산했던 걸 다시 계산하지 않게 만드는 거예요. GPU는 워낙 비싸니까."

### 6. HBM의 한계 — 대역폭은 최고지만 용량은 갇혀 있다 (14:03-16:20)
[바로가기](https://www.youtube.com/watch?v=5cOS2mK4l_M&t=843s)

#### 핵심 메시지
HBM(High Bandwidth Memory)은 GPU 옆에 붙어 광대역으로 데이터를 주고받지만, 물리적으로 용량 확장이 어렵고 매우 비싸다.

#### 상세 내용
- HBM = 대역폭을 극단적으로 키운 메모리. 최근 GPU 혁신은 사실상 HBM의 대역폭·용량 확대에 기대고 있음.
- 한계: GPU와 같은 패키지 안에 들어가 있어 좁은 공간에 많이 못 넣음.
  - **쌓기(stacking)의 한계**: 발열·공간·**수율** 문제. 쌓다 문제 생기면 칩 전체(+GPU까지) 버려야 함.
- 결론: HBM은 가치 높은 데이터 전용으로 써야 하며, KV캐시를 전부 HBM에 넣으면 잘못된 사용 → GPU를 더 많이 사야 하는 비용 문제 발생.

#### 주요 발언
> "HBM에도 궁극적인 한계가 용량을 되게 키우기가 힘들어요… KV캐시만 HBM에 밀어넣어 놓으면 되게 HBM 잘못 쓰는 형태가 되는 거죠."

### 7. 멀티티어 메모리 & 네트워크 방식의 한계 (16:20-24:00)
[바로가기](https://www.youtube.com/watch?v=5cOS2mK4l_M&t=980s)

#### 핵심 메시지
데이터를 중요도에 따라 HBM→외부 DRAM→SSD로 계층(티어)화. 그러나 기존 네트워크 기반 공유는 "복사"에 의존해 비효율적.

#### 상세 내용
- **티어링(Tiering)**: 급한 데이터는 HBM, 자주 안 쓰는 건 옆 메모리, 가끔 쓰는 콜드 데이터는 SSD("지하 창고").
- 메모리 회사 실적에서 HBM보다 **DDR5(일반 DRAM)** 매출이 더 큰 경우도 → 일반 메모리도 폭발적 수요.
- **샌디스크 주가 50배 상승** — 콜드 데이터가 SSD 티어까지 확대돼 관리되기 때문.
- 기존 네트워크(스케일아웃) 공유의 문제: 서버 간 데이터를 **항상 복사(copy)**해야 함.
  - 데이터가 크니 복사 비용·시간 증가, 같은 데이터를 여러 벌 보유, 원격 서버에서 가져오며 GPU 대기 발생 → 인프라 병목.

#### 언급된 사례/에피소드
- **"보내고 내 건 지우면 안 되나?"(진행자)**: 나도 써야 하므로 불가 → 불필요한 복사본 계속 생성.

#### 주요 발언
> "사실 공유라고 하지만 엄밀히 공유가 아니고 그냥 내 거 한 벌 더 복사해서 저기다 주는 거죠."

### 8. CXL의 가치 — "내 것 같은 공유" (24:00-27:10)
[바로가기](https://www.youtube.com/watch?v=5cOS2mK4l_M&t=1440s)

#### 핵심 메시지
CXL은 큰 메모리 풀("호수"/"공유 오피스")을 만들어 여러 서버가 **복사 없이 내 메모리처럼** 읽어 쓰게 한다.

#### 상세 내용
- CXL의 두 가치: ① 메모리를 훨씬 많이 붙일 수 있게 함 ② 데이터를 복사하지 않고 공유 풀에서 직접 읽어감.
- 워크로드 증가 시 GPU 서버를 통째로 더 꽂는 대신 **메모리만 추가**하면 됨 → 비용 절감.
- 왜 과거엔 어려웠나: 스토리지는 원래 공유 개념이 있었으나, 메모리는 "CPU 옆에 있어야 한다"는 관념 + 데이터 변경 정보를 모든 서버가 알아야 하는 **코히런스(Coherence)** 기반기술 필요.
  - 스토리지는 수십 MB 단위 공유지만, 메모리는 **4바이트 단위**의 미세 공유가 필요 → 완전히 새로운 연결 표준 요구.
- 수십 년 노력의 결과물이 CXL. 2019년 표준 첫 등장 → 2023~24년 시제품 → 올해 말~내년 초 CXL 3.x로 본격 상용화. (그래서 대중에 덜 알려짐)

#### 언급된 사례/에피소드
- **비유 총정리**:
  - "큰 호수를 만들어서 각 시스템이 자기 메모리인 것처럼 본다"
  - "사무실이 모자라니까 공유 오피스를 만들자" / "공용 도마"
  - "멀리 있지만 내 건데, 나도 내 거라고 생각하고 얘도 내 거라고 생각한다"
- **자리 다툼 우려**: 공유 공간에서 데이터가 섞이거나 무단 접근하는 문제 → 코히런스 + 보안 프로토콜(SW+일부 HW)로 관리. "제일 어려운 기술 중 하나."

#### 주요 발언
> "복사 복사가 아니고 CXL은… 메모리가 연결되는 거예요. 내 메모리가 원래 100M밖에 없었는데 연결해서 몇 개 꽂아서 확장한."

> "사실은 내 거죠. 멀리 있지만 내 건데."

### 9. 메모리 낭비의 실태 — 35% 활용률 (27:10-33:00)
[바로가기](https://www.youtube.com/watch?v=5cOS2mK4l_M&t=1630s)

#### 핵심 메시지
클라우드 메모리는 실제로 35%만 활용된다. CXL 공유로 이를 70~80%까지 올릴 수 있다 = 설비투자 절반.

#### 상세 내용 — 35%가 나오는 계산
- 클라우드 사업자는 고객 수요를 몰라 서버에 **최대 용량 메모리를 과잉 공급(Over-provisioning)** — 전기처럼.
- 고객은 서버당 평균 **70%**만 대여.
- 고객도 자기 앱의 메모리 사용량을 몰라 필요량의 **2배**를 대여 → 절반은 라이프스팬 동안 한 번도 터치 안 됨.
- **결과: 70% × 50% = 실제 액티브 활용률 35%.**
- CXL 공유 시: 서버마다 100까지 쓰게 하되 남는 부분(30~50)을 공용 풀로 → **몇 시간 단위로 메모리 조절** 가능 → 활용률 70~80%.

#### 언급된 사례/에피소드
- **중고 DRAM 재활용(Retired DRAM)**: 클라우드 사업자는 5~7년 뒤 서버를 통째 폐기. 꺼낸 DRAM은 최신 시스템에 직접 못 꽂지만(속도 저하), **CXL에 꽂으면 재사용 가능** → 이미 수백만 대 규모로 쓰이거나 쓰일 예정. 큰 시장.

#### 주요 발언
> "클라우드의 액티브 메모리가 활용된 비율은 35%밖에 안 된다."

> "두 배 이상까지 올릴 수 있다는 뜻은 절반만 설비 투자를 하면 된다는 뜻이네요." (진행자)

> "메모리의 수요를 공급이 절대 따라갈 수 없는 위치에 있기 때문에… 이제는 완전히 새로운 세상에 왔다고 보면 되고 메모리가 인프라의 중심에 와 있다."

### 10. 데이터 그래비티 & Near-Data Processing (33:00-43:20)
[바로가기](https://www.youtube.com/watch?v=5cOS2mK4l_M&t=1980s)

#### 핵심 메시지
데이터가 너무 커져 "CPU로 데이터를 보내는" 대신 "데이터가 있는 곳(메모리 근처)으로 연산을 가져오는" 코페르니쿠스적 전환이 필요하다.

#### 상세 내용
- **데이터 그래비티(Data Gravity)**: 데이터가 중력을 가져 서비스가 데이터 근처로 모임.
  - 10년 전 멀티클라우드가 우아해 보였지만, 클라우드 간 데이터 복사 비용이 너무 커 비효율 → 데이터를 한곳에 모으고 서비스를 붙이는 방향으로.
- **사고 전환**: 과거엔 CPU/GPU(연산)가 컴퓨터 중심 → 이제는 **메모리·데이터가 중심**. "우주 중심이 지구인 줄 알았는데 태양이었다"처럼.
- **Near-Data Processing(니어 데이터 프로세싱)**: 모든 데이터를 CPU/GPU로 보내지 않고, 메모리 근처에서 **필터링·간단 연산** 후 필요한 것만 전송 → 데이터 이동·에너지·서버 대수 감소.

#### 언급된 사례/에피소드
- **신용카드 마케팅 예시**: "금요일 저녁 강남에서 소비하는 상위 10% 소비자"를 찾을 때, 전 세계 트랜잭션을 전부 GPU로 옮겨 분석하면 연산장치의 99%가 놀게 됨. 정렬·필터링 같은 간단 비교연산은 메모리 근처에서 처리하고 결과만 보내면 효율적.
- **비유**: "책을 통째로 들고 오지 말고 관련된 몇 페이지만 찾아 오면 분석은 내가 한다" / "수많은 데이터에서 판례를 찾아 대표 변호사에게 필요한 것만 준다."
- 시사점: 메모리는 "조금만 똑똑하면 된다"(간단한 연산 기능만 있어도 충분). 우리나라 관점에서 메모리가 더 큰 부가가치를 갖게 됨.

#### 주요 발언
> "데이터가 있는 곳으로 컴퓨팅을 갖다 놓으면 되는 거거든요."

> "사장(연산)이 움직이는 게 낫다. 직원(데이터) 천 명이 다 사장실로 올라갈 필요 없다."

### 11. 엑시나 제품의 실체 (43:20-47:00)
[바로가기](https://www.youtube.com/watch?v=5cOS2mK4l_M&t=2600s)

#### 핵심 메시지
엑시나는 삼성 파운드리 공정으로 이미 칩을 양산, 유수 CPU/GPU 벤더 및 미국 하이퍼스케일러와 검증 중.

#### 상세 내용 — 제품 스펙
- 가운데 **엑시나 칩** + 주변에 DRAM 슬롯(현재 4개 → 최대 8개). 삼성·하이닉스·마이크론 DRAM 꽂아 사용. 하단은 CXL로 서버 연결.
- **카드당 최대 2TB** 메모리 탑재 가능.
- **RISC-V 코어 수천 개** 직접 설계·탑재 → Near-Data Processing(메모리 근처 연산).
- 압축 기술 지원.
- **인피닛 메모리(Infinite Memory)**: 디바이스 뒤에 SSD를 붙여, SSD 용량(DRAM의 수백~1000배)을 **메모리인 것처럼** CPU/GPU에 보여줌 → 소프트웨어의 정교한 티어 관리 없이 초대형 KV캐시 확보. **전 세계에서 엑시나만 제품화**.
- 삼성 파운드리로 칩 이미 나와 있고, 올해 초부터 엔비디아 등 CPU·GPU 벤더 및 미국 빅테크 일부와 검증 진행.

#### 주요 발언
> "SSD 용량을 메모리인 것처럼 CPU나 GPU한테 보여주는 기능… 저희는 그걸 인피닛 메모리라고 이름 붙였는데."

### 12. 10배 효율의 근거 & 경쟁사 비교 (47:00-52:40)

#### 상세 내용 — "10배" 분해
- ① CXL만 잘 써도 메모리 2배 효율 (절반만 구매) + 중고 DRAM 재활용.
- ② 확장된 대용량 메모리를 누군가는 연산해야 하는데, 그 상당 부분을 엑시나 디바이스의 수천 코어가 처리 → 과거 CPU 10만 대가 하던 일을 대폭 축소.
- ③ 집적도 높은 메모리+컴퓨팅 통합 → 목표 **10배 효율**(응용마다 2~3배~그 이상). "지구를 위해서도 옳은 선택."

### 13. 대안 기술 비교 & 상용화 시점 (52:40-56:36)
[바로가기](https://www.youtube.com/watch?v=5cOS2mK4l_M&t=3160s)

#### 핵심 메시지
소프트웨어·광통신 방식과 방향은 같지만, 엑시나의 HW+SW 코디자인이 지금 당장 쓸 수 있는 해법이다.

#### 상세 내용
- **vs 소프트웨어 방식**: SW는 유연하나 확장성·효율 확보가 어려움. 엑시나는 HW 기반 + SW까지 통합(HW-SW co-architecting)해 레이턴시·효율 우위.
- **vs 광통신(포토닉스/실리콘 포토닉스)**: 더 먼 거리·높은 대역폭 접근이 목표. 중요하지만 변환 장치 등 해자(난제)가 남아 더 많은 시간 필요. **CXL(엑시나 기술)은 광통신 뒤에도 결합 가능** — 어차피 연결이 목적.
- **상용화**: 엑시나는 지금 당장 AI 인퍼런스 인프라의 가장 큰 병목을 공격. 내년부터 신규 투자되는 모든 서버에 바로 적용 가능 — "그냥 사서 꽂으면 동작". 미래 기술이 아니라 **현재의 기술**.

#### 주요 발언
> "미래 기술이라고 하긴 어렵고 이제는 현재에 와 있는 기술이다."

> "공유 외장하드에 가깝네요." (진행자의 마무리 비유)

### 2. 인터넷 vs 웹 — 결정적 구분 (0:30 ~ 1:45)
[바로가기](https://www.youtube.com/watch?v=wqzmZ97vAOY&t=30)

#### 핵심 메시지
인터넷과 웹은 다른 개념이다. 인터넷은 컴퓨터 연결 자체이고, 웹은 인터넷 위에서 동작하는 애플리케이션이다.

#### 상세 내용

| 용어 | 정의 |
|------|------|
| **인터넷 (Internet)** | "수많은 컴퓨터가 촘촘히 연결되어 있는 그 자체". 컴퓨터들의 연결망 |
| **웹 (Web)** | 인터넷 위에서 동작하는 **애플리케이션**. 브라우저로 도메인을 입력해 접근 |
| **네트워크 (Network)** | 서로 연결되는 기술 자체 — "어떻게 연결할지" |

- 우리가 마치 "인터넷 = 웹"인 것처럼 혼용하지만, 엄밀히 다름
- 브라우저에 도메인을 치고 서버 응답을 받기까지 — 그 사이를 매개하는 것이 네트워크 통신

#### 주요 발언
> "인터넷이라는 것은 수많은 컴퓨터가 연결되어 있는 그 자체가 인터넷입니다." (00:46)

> "웹은 어플리케이션입니다. 인터넷 기반으로 동작되는 어플리케이션이라고 하면 맞습니다." (01:21)

### 3. 3대 프로토콜 — IP / TCP / HTTP (1:45 ~ 4:40)
[바로가기](https://www.youtube.com/watch?v=wqzmZ97vAOY&t=105)

#### 핵심 메시지
클라이언트-서버 통신을 가능하게 하는 3대 프로토콜. **프로토콜 = 서로간의 약속·규약·규칙**.

#### 3.1 IP (Internet Protocol)
- 인터넷 프로토콜
- 웹 서버에도 IP가 설정되어 있고, 데이터들이 이 IP를 통해 서버를 찾아감
- 형태: `xxx.xxx.xxx.xxx`

#### 3.2 TCP (Transmission Control Protocol)
- 데이터를 한 번에 전달하지 않고 **작게 나누어 보냄**
- 인터넷 망은 다양한 경로로 갈 수 있는 그물망
- 데이터가 정상적으로 도착했는지 / 오류는 없는지 **체크하고 재전송**하는 역할
- IP만으로는 부족 — TCP가 신뢰성 있는 분할·재조립·오류제어를 담당

#### 3.3 HTTP (HyperText Transfer Protocol)
- HTML을 주고받는 규약
- 클라이언트(브라우저)가 서버에 요청 → 서버가 응답할 때 사용
- "P가 프로토콜이에요. 프로토콜은 서로 간의 약속, 규약, 규칙"

#### 주요 발언
> "프로토콜은 서로 간의 약속, 뭐 규약, 규칙 뭐 이렇게 표현할 수 있는데요." (02:50)

> "데이터를 한 번에 전달하고 한 번에 받는 것이 아니라 데이터를 작게 나누고 그 작은 데이터들을 서버로 보내게 되고…" (03:47)

### 4. 핵심 네트워크 장비 — 라우터 / 스위치 / 방화벽 / CDN / DMZ (4:40 ~ 7:50)
[바로가기](https://www.youtube.com/watch?v=wqzmZ97vAOY&t=280)

#### 핵심 메시지
클라이언트와 서버 사이에는 다양한 장비가 있다. 각 장비의 역할을 명확히 구분해야 구성도가 읽힌다.

#### 4.1 라우터 (Router)
- **WAN과 LAN 구간을 연결하는 장비**
- WAN (Wide Area Network) = 국가/지역 간 초고속 인터넷 광케이블 망
- LAN (Local Area Network) = 사무실·집 등 내부 네트워크
- "이기종간의 네트워크 연결" 시 사용

#### 4.2 스위치 (Switch)
- **LAN 내부 컴퓨터들을 서로 연결**해 주는 장비
- 라우터 "안쪽"의 기기들을 묶음
- 정리: 이기종간 = 라우터 / LAN 내부 = 스위치

#### 4.3 방화벽 (Firewall, 파이어월)
- 정말 "방화벽" — fire-wall
- 특정 IP나 프로토콜만 들어올 수 있게 **허용/차단 설정**
- 보통 "허용 정책" 구조 — 필요한 포트만 열고 나머지는 막음
- 예시: 21번(FTP)은 막고, 443번(HTTPS)은 열어둠

#### 4.4 CDN (Content Delivery Network)
- 컨텐츠 딜리버리 네트워크
- 사용자에게 이미지·영상을 **더 빠르게 제공**하는 분산 서버 망
- 작동: 한국 사용자가 미국 서비스 접속 시 → 한국에 캐시 서버를 두고 거기서 응답
- 캐시 미스 시 **오리진 서버(Origin Server)**에서 가져와 캐싱
- 주로 이미지·영상 등 정적 자원 대상

#### 4.5 DMZ (Demilitarized Zone)
- "Demilitarized" = 비무장지대
- **외부에서 접속이 가능한 서버 영역**
- 대표 예시: 웹 서버 (외부 접속 필수)
- 반대로 데이터베이스 서버는 외부 접속 차단 → 내부망에 위치
- 보안을 위해 영역을 분리하는 개념

#### 주요 발언
> "랜 내 어 기기들을 연결할 때 [스위치] 그리고 랜과 웬 같은 이기종간의 네트워크를 연결할 때는 라우터를 쓴다." (05:56)

> "방화벽이라는 것은 정말 방화벽이죠. 파이어월이에요." (06:08)

### 5. 포트(Port) — 서버 프로그램 식별 번호 (7:50 ~ 10:14)
[바로가기](https://www.youtube.com/watch?v=wqzmZ97vAOY&t=470)

#### 핵심 메시지
포트는 **서버 컴퓨터 내부에서 구동되고 있는 서버 프로그램들을 구분하기 위한 식별 번호**다. 물리 서버 1대에 웹 서버·DB 서버·메일 서버 등 여러 프로그램이 동시에 떠 있을 수 있다.

#### 5.1 포트의 정의
- 컴퓨터 내에 존재
- 서버 컴퓨터의 특정 포트로 접속 = 그 컴퓨터에서 구동 중인 특정 서버 프로그램으로 접속
- "물리 장비(서버)" vs "서버 프로그램(웹/DB/메일)" 구분 필수

#### 5.2 표준 포트 번호

| 포트 | 프로토콜 / 서비스 | 비고 |
|------|--------------|------|
| **22** | SSH | 원격 접속·관리 |
| **21** | FTP | 파일 전송 — 보통 차단 |
| **80** | HTTP | 웹 (비암호화) |
| **443** | HTTPS | 웹 (암호화) — 방화벽에서 보통 열어둠 |
| **3306** | MySQL DB | 기본 DB 포트 |
| **8080** | WAS | 웹 애플리케이션 서버 기본 포트 |

#### 5.3 포트 활용 예
- "특정 웹 서버가 구동되고 있는지 보려면 80포트로 접속해 본다"
- 방화벽 정책에서 21번 차단·443번 허용 식으로 운영

#### 주요 발언
> "포트라는 것은 이렇게 컴퓨터 서버의 어떤 특정 포트로 접속을 한다 했을 때는, 그 서버 컴퓨터 안에 구동되고 있는 서버 프로그램들을 구분하기 위한 그러한 식별 번호" (08:31)

### 6. 전체 네트워크 구성도 한눈에 (10:14 ~ 14:40)
[바로가기](https://www.youtube.com/watch?v=wqzmZ97vAOY&t=614)

#### 핵심 메시지
앞에서 본 요소들을 하나의 구성도에 합쳐서 본다. 클라이언트의 요청이 응답까지 도달하는 전체 흐름.

#### 6.1 데이터 흐름 전체 경로

```
[클라이언트(브라우저)]
   │ 도메인 입력
   ▼
[인터넷] (그물망 라우팅)
   │
   ▼
[CDN] ─ 캐시 히트 시 즉시 응답
   │ (캐시 미스)
   ▼
[ISP 라우터] ─ 인터넷 서비스 프로바이더의 라우터
   │
   ▼  WAN ↔ LAN 경계
[라우터] (회사 라우터)
   │
   ▼
[방화벽] ─ IP/포트 허용 검사
   │
   ▼
[로드밸런서/스위치]
   │  ┌─────┬─────┐
   ▼  ▼     ▼     ▼
[웹 서버 1]  [웹 서버 2]   ← DMZ 영역
   │  ╲    ╱  │
   │   ╲  ╱   │
   ▼   ╳    ▼
[WAS 1]   [WAS 2]   ← 내부망
   │  ╲    ╱  │
   │   ╲  ╱   │
   ▼   prim   ▼
[DB Primary] ←──[DB Standby] (리플리케이션)
```

#### 6.2 단계별 의미

| 위치 | 역할 |
|------|------|
| **인터넷** | "굉장히 다양한 망들의 연결 — 그물망 같은 구조" |
| **라우팅** | IP를 근거로 패킷이 목적지 서버를 찾아가는 과정 |
| **ISP 라우터** | 인터넷 서비스 프로바이더(KT/SK/LG 등)의 라우터 |
| **CDN 캐시 히트** | 이미지·영상이 CDN에 있으면 클라이언트로 즉시 전달 |
| **CDN 캐시 미스** | 없으면 오리진 서버에서 가져와 캐싱 |
| **회사 라우터** | WAN→LAN 진입 게이트 |
| **방화벽** | 허용된 IP·포트만 통과 |
| **로드밸런서/스위치** | 트래픽을 뒤쪽 서버들로 분산 |
| **웹 서버** | DMZ 영역. 정적 자원 제공·리버스 프록시 |
| **WAS** | 내부망. 백엔드 API·비즈니스 로직 실행 |
| **DB** | 내부망. 가장 보호되는 영역 |

#### 주요 발언
> "인터넷은 굉장히 다양한 망들의 어 연결이다라고 보시면 돼요. 뭐 하나의 선이라기보다는 그물만 같은 구조." (12:42)

> "그 라우팅을 거쳐서 실제 이제 접속을 찾아가는 거죠. 그 근거가 되는 것은 이제 IP예요." (12:59)

### 7. 웹 서버 vs WAS — 리버스 프록시 (14:40 ~ 17:50)
[바로가기](https://www.youtube.com/watch?v=wqzmZ97vAOY&t=880)

#### 핵심 메시지
웹 서버와 WAS는 다른 역할. 웹 서버는 정적 자원 제공 + 리버스 프록시, WAS는 애플리케이션 실행.

#### 7.1 차이점

| 구분 | 웹 서버 | WAS (Web Application Server) |
|------|---------|-------------------------------|
| 역할 | 이미지·HTML 등 **정적 자원** 제공 | **애플리케이션 탑재**, 백엔드 API 실행 |
| 위치 | DMZ | 내부망 |
| 기본 포트 | 80 (HTTP) / 443 (HTTPS) | **8080** |
| 대표 제품 | Nginx, Apache | Tomcat, JBoss |

#### 7.2 리버스 프록시 (Reverse Proxy)
- 웹 서버가 단순 정적 제공 외에 **WAS로 트래픽을 전달**해주는 역할
- 클라이언트 요청 중 동적 처리는 WAS로 포워딩
- **Nginx**가 웹 서버 + 리버스 프록시 양쪽 기능 모두 제공

#### 7.3 이중화 (Redundancy)
- 웹 서버 2대 + WAS 2대 (양측 모두 이중화)
- **웹 서버 1, 2 모두가 WAS 1, 2 양쪽을 바라봄** (서로 교차 연결)
- **목적**:
  1. **로드 분산** (Load Balancing)
  2. **장애 복구** — 한쪽이 죽어도 서비스 지속

#### 7.4 포트 흐름 예
- 클라이언트 → 웹서버 (443 HTTPS)
- 웹서버 → WAS (8080)
- WAS → DB (3306)

#### 주요 발언
> "웹 서버는 이미지나 뭐 HTML 이런 식으로 어, 웹을 제공하는 서버다." (15:57)

> "와스는 웹 어플리케이션 서버예요. 우리가 만들 백엔드 API 서버들이 여기에 들어가는 거예요." (16:08)

### 8. DB 이중화 — 프라이머리 / 스탠바이 (17:50 ~ 21:00)
[바로가기](https://www.youtube.com/watch?v=wqzmZ97vAOY&t=1070)

#### 핵심 메시지
DB는 웹·WAS와 다르게 이중화 한다. **양쪽이 아니라 한쪽(Primary)만 쓰고, 다른 한쪽(Standby)은 동기화 백업**으로 둔다.

#### 8.1 왜 DB는 양쪽에 동시 사용 안 하나?
- 데이터는 **쓰기·읽기가 빈번** → 양쪽에 동시 쓰면 **동기화 충돌 문제** 발생
- (예외: 솔루션·상황에 따라 양쪽 쓰기 가능 — 일반적이진 않음)

#### 8.2 일반 패턴

| 역할 | 동작 |
|------|------|
| **Primary DB** | 모든 WAS가 바라봄. 읽기·쓰기 모두 처리 |
| **Standby DB** | 평상시 **리플리케이션(Replication)**으로 데이터만 동기화하며 대기 |
| **장애 발생 시** | Primary 중단 → Standby가 새 Primary로 승격(failover) |
| **WAS 연결** | Primary가 바뀌면 WAS는 새 Primary로 자동 전환 |

#### 8.3 핵심 차이 도식

```
웹 서버:     양쪽 다 활성 + 양쪽 다 바라봄
WAS:        양쪽 다 활성 + 양쪽 다 바라봄
DB:         Primary만 활성 + Standby는 동기화 대기
            (장애 시 승격)
```

#### 주요 발언
> "데이터베이스 두 군데로 만약에 요렇게 쓰게 되면 이 데이터의 동기화 문제가 생길 수가 있습니다." (19:48)

> "프라이머리 DB로 두고 양쪽 다 여기에 쓰고 여기에는 이렇게 리플리케이션이라고 해서 일종의 백업 데이터만 동기화시켜 놓다가, 만약에 이 DB가 중단이 되면 이 DB가 스탠바이가 프라이머리로 되고…" (20:04)

## 관련 자료 및 참고

### 영상에서 직접 언급된 도구·기술
- **Nginx** — 웹 서버 + 리버스 프록시

### 추가 학습 권장 주제 (영상이 다루지 않은 영역)
1. **클라우드 네트워크 구성** — 다음 영상에서 다룰 예정 (VPC, Subnet, Security Group 등)
2. **OSI 7계층** vs **TCP/IP 4계층** — 본 영상은 응용 계층 위주, 이론은 별도 학습
3. **DNS** — 도메인을 IP로 변환하는 과정 (브라우저 요청 흐름의 첫 단계)
4. **TLS/SSL 핸드셰이크** — HTTPS의 443 포트 내부에서 일어나는 일
5. **WAF (Web Application Firewall)** — 일반 방화벽과 별도의 애플리케이션 계층 방어
6. **Active-Active vs Active-Standby** — 이중화의 다양한 패턴
7. **DB 샤딩 / 클러스터링** — Primary/Standby 외의 확장 패턴

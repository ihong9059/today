## 구간별 상세 내용

### 1. 파트 1: 하지 말 것 3가지 (00:00-02:43)
[바로가기](https://www.youtube.com/watch?v=hXlB1QstQ-Y&t=0s)

#### 핵심 메시지
클로드 코드를 잘되게 만드는 것보다 하지 말아야 할 것을 안 하는 게 먼저다. 풀 세팅, FOMO, 막연한 프롬프트 세 가지를 피해야 한다.

#### 상세 내용

**1-1. 처음부터 풀 세팅하지 마라 (00:32-01:35)**
- 스킬, 라이브러리 등 "이건 좋더라" 하는 걸 다 설치하는 분들이 많음
- Claude Code 창시자 보리스는 X에서 "내 세팅은 놀랍게도 바닐라다"라고 공개
- 본인이 만든 툴인데 거의 커스텀 안 하고 있는 그대로 사용
- 이유: 클로드 코드는 있는 그대로도 대부분의 분들에게 충분
- 추천 순서: 기본 Claude Code → 같은 실수/워크플로우 반복 패턴 발견 → 그 패턴 하나에 대해서만 스킬 생성
- "실제 니즈에 따라 자라나는 세팅이 가장 좋은 세팅. 좋은 걸 다 갖다 박는 게 결코 좋은 게 아닙니다."

**1-2. FOMO에 휩쓸리지 마라 (01:36-02:06)**
- 클로드의 업데이트 속도는 매우 빠름: 루틴, 데스크 맵 리디자인, 클로드 디자인 등 거의 매일 새 기능
- 새 기능들은 당장 내 워크플로우랑 안 맞거나 필요 없을 확률이 높음
- 새 기능을 무시하라는 게 아니라 "어떤 태도로 받아들이느냐"가 중요
- 다 따라가야 한다는 불안에 휩쓸리지 말 것

**1-3. 막연한 프롬프트 쓰지 마라 (02:06-02:43)**
- "이거 만들어 줘", "이 버그 알아서 고쳐 줘" 식의 프롬프트는 비효율적
- AI는 충분히 유능하지만 단번에 완성도 있는 결과물이 나오는 경우는 거의 없음
- Anthropic 공식 입장: AI가 혼자 알아서 다 하는 방향이 아니라, 인간이 이미 검증한 방식을 패키지로 만들어서 AI한테 시키는 방향이 맞음
- 비유: 자율주행 차를 타면서도 네비게이션은 직접 찍어야 함

#### 언급된 사례/에피소드
- **보리스의 바닐라 세팅**: Claude Code 창시자가 본인 툴을 거의 커스텀 없이 사용한다는 사실
  - 시사점: 기본 기능만으로도 충분하며, 과도한 세팅은 오히려 해가 됨

#### 주요 발언
> "클로드 코드가 잘되게 만드는 것보다 하지 말아야 할 걸 안 하는 게 먼저거든요."

> "보리스는 X에서 '내 세팅은 놀랍게도 바닐라다'라고 공개했습니다. 본인이 만든 툴인데 거의 커스텀 안 하고 있는 그대로 쓴다는 거죠."

> "자율주행 차를 타면서도 어디로 어떤 길로 가는지는 알아야 하고, 적어도 네비게이션 정도는 직접 찍어야 합니다. 어디로 갈지는 AI가 정하는 게 아니라 여러분이 정하는 겁니다."

### 2. 파트 2: 해야 할 것 3가지 (02:43-05:32)
[바로가기](https://www.youtube.com/watch?v=hXlB1QstQ-Y&t=163s)

#### 핵심 메시지
컨텍스트를 신선하게 유지하고, 진짜 계획을 세워서 명시적으로 지시하고, 검증 장치를 붙이되 그 장치 자체도 감시해야 한다.

#### 상세 내용

**2-1. 컨텍스트 관리 (02:47-03:30)**
- "신선한 컨텍스트가 비대한 컨텍스트를 이긴다" - 이 문장 하나만 기억하면 됨
- 메시지, 파일, 실행한 명령어 등 모든 게 컨텍스트에 쌓이고, 채워질수록 성능 떨어짐
- 정보를 최대한 많이 주는 게 아니라, 정말 필요한 정보만 남기고 나머지를 쳐내는 것
- LLM은 정보 많이 주면 잘하는 게 아님. 관련 없는 정보가 많을수록 잘못된 방향으로 빠짐
- CLAUDE.md도 마찬가지: 약 80%만 따름. 길수록 중요한 규칙이 무시될 가능성 높음
- CLAUDE.md는 150~200줄 이내 권장

**2-2. 계획 세우기 (03:32-04:07)**
- 플랜 모드 켜라는 게 아니라 진짜 계획
- 뭘 만들고 싶은지 명확히 알고 있어야 AI가 뭐라도 할 수 있음
- "대충 이 기능 추가해 줘"가 아니라 실제로 어떤 식으로 구현할 건지, 완료 기준이 뭔지 먼저 정리
- 플랜 모드의 진짜 좋은 점: 이 과정을 잘 몰라도 클로드와 같이 할 수 있다는 것
- 단, 플랜을 그냥 수락하지 말고 편집도 적극적으로 할 것
- 명시적으로 지시하는 게 AI를 잘 쓰는 것. AI가 여러분의 모든 생각을 알 수 없기에 원하는 게 있다면 명시적으로 전달

**2-3. 검증 장치 붙이기 (04:32-05:32)**
- 보리스가 "단 하나의 팁을 고르라면"이라고 했을 때 고른 것
- 클로드한테 자기 일을 스스로 검증할 수 있는 방법을 주기만 해도 결과물 품질이 2~3배 상승
- 검증 장치 없으면: 클로드가 만들고 → 사용자가 확인 → 피드백 → 다시 고침 (수동 사이클)
- 검증 장치 있으면: 클로드가 스스로 돌리고 → 실패하면 스스로 고치고 → 완성된 버전이 옴
- 주의: AI가 검증 장치를 "악용"할 수 있음. 테스트 실패 시 코드를 고치는 게 아니라 테스트 자체를 코드에 맞춰 수정해버림 → 통과는 되지만 의미 없는 테스트
- 따라서 검증 루프를 만들었다고 끝이 아니라, 테스트가 올바른 걸 검증하고 있는지 테스트 자체를 사용자가 봐야 함

#### 언급된 사례/에피소드
- **테스트 악용 사례**: AI가 테스트 실패 시 코드 대신 테스트를 수정해버리는 문제
  - 시사점: 검증 장치도 감시가 필요
- **Anthropic 공식 방향성**: AI가 혼자 다 하는 게 아니라 인간이 검증한 방식을 패키지로 만들어 시키는 것
  - 시사점: 인간의 역할은 방향 설정과 검증

#### 주요 발언
> "신선한 컨텍스트가 비대한 컨텍스트를 이긴다. 이 문장 하나만 기억하셔도 됩니다."

> "클로드는 CLAUDE.md의 한 80% 정도만 따른다고 알려져 있습니다. 길면 길수록 중요한 규칙이 무시될 가능성이 높다는 거죠."

> "클로드한테 자기 일을 스스로 검증할 수 있는 방법을 주기만 해도 결과물 품질이 두 세 배는 올라갑니다."

> "테스트가 실패하면 코드를 고치는 게 맞는데 AI가 테스트 자체를 코드에 맞춰서 수정해버립니다. 통과는 됐지만 의미가 없는 테스트죠."

### 3. 파트 3: 실전 꿀팁 3가지 (05:32-08:09)
[바로가기](https://www.youtube.com/watch?v=hXlB1QstQ-Y&t=332s)

#### 핵심 메시지
세션 관리(리와인드)가 컨텍스트 관리의 핵심이고, 스킬은 유지 비용 없는 자산이며, FOMO가 아닌 열린 사고로 새 기능을 이해해서 내 것으로 만드는 능력이 진짜 자산이다.

#### 상세 내용

**3-1. 세션 관리 - 리와인드 (05:35-06:33)**
- Claude Code 팀이 꼽은 "컨텍스트 관리 잘하는 사람의 단 하나의 습관" = 리와인드
- 리와인드: ESC 두 번 → 이전 메시지 지점으로 돌아가서 그 이후 기록을 싹 지움
- 예시: A 방식으로 시도 → 실패 → "B로 해 줘" 메시지 보내면 A 실패 기록이 컨텍스트에 남아 B에도 영향
- 리와인드하면: A 기록 없는 깨끗한 상태에서 B를 시도 → 결과물이 훨씬 깨끗
- /clear: 작업 끝났을 때 세션 완전 초기화
- /compact: 대화 요약. 단, "/compact 이번엔 A에 집중하고 B는 버려" 식으로 요약 방향을 직접 지시하면 훨씬 좋은 요약

**3-2. 스킬 활용 (06:33-07:10)**
- 현재 Claude 생태계는 스킬 방향으로 움직이고 있음
- CLAUDE.md는 세션 시작할 때 무조건 컨텍스트에 들어감 vs 스킬은 실제 필요할 때만 로드
- 우선 남이 만든 좋은 스킬을 가져다 쓰는 게 좋음 (GitHub에 유용한 스킬 많음)
- 반복하는 작업이 있다면 스킬로 저장
- 스킬은 유지 비용이 없으면서도 상당히 유용 → "자산"

**3-3. 열린 사고 vs FOMO (07:10-08:09)**
- FOMO = 불안. "이거 안 쓰면 뒤쳐지는 거 아닌가"에 쫓겨서 새 기능을 쓰지도 않을 거면서 일단 깔고 보는 것
- 열린 사고 = 사고. "이 기능은 왜 생겨난 건지, 내 프로젝트에 어떻게 적용할 수 있을지" 질문을 던지는 태도
- 이해하고 있으면 당장 안 써도 괜찮음. 필요해지면 그때 쓰면 됨
- 남의 워크플로우를 그대로 복사하는 게 아니라, 이해해서 내 상황에 맞게 번역해서 적용하는 능력이 진짜 자산
- 이건 자동화할 수 없는 부분이자 시간이 지날수록 자산이 되는 부분

#### 주요 발언
> "컨텍스트 관리 잘하는 사람을 가리는 단 하나의 습관을 꼽자면 그건 리와인드다."

> "CLAUDE.md는 세션 시작할 때 무조건 컨텍스트에 들어가는 반면 스킬은 실제 필요할 때만 로드됩니다."

> "스킬은 유지 비용이 없음에도 상당히 유용하기 때문에 어느 면에선 자산이라고도 할 수 있습니다."

> "포모는 불안이죠. 반면 열린 사고는 말 그대로 사고입니다. 이 기능은 왜 생겨난 건지, 내 프로젝트에 어떻게 적용할 수 있을지 질문을 던지는 태도죠."

> "진짜 좋은 건 남의 워크플로우를 그대로 복사하는 게 아니라 그걸 이해해서 내 상황에 맞게 번역해서 적용하는 능력입니다. 이건 자동화할 수 없는 부분이자 시간이 지날수록 자산이 되는 부분입니다."

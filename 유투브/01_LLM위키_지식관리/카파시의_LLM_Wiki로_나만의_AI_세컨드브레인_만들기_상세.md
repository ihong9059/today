### 2. CLAUDE.md만으로는 부족한 이유 (1:05-3:01)
[바로가기](https://www.youtube.com/watch?v=cNlvrU-KcRg&t=65s)

#### 핵심 메시지
CLAUDE.md/agent.md 세팅만으로는 AI 대화에서 지식이 휘발되고 재활용이 불가능하다.

- 세컨드 브레인이 필요하지만, CLAUDE.md만으로는 한계

#### 주요 발언
> "CLAUDE.md만으로는 부족합니다. 재활용이 가능한 나의 정보와 지식을 쌓아 나가기 쉽지 않아요."

### 3. 카파시가 옵시디언을 프론트엔드라 부른 이유 (3:01-4:49)

#### 상세 내용

#### 언급된 사례/에피소드
- **카파시의 "ideal frontend" 발언**: 옵시디언이 AI 활용 도구로서 급부상하는 계기

#### 주요 발언
> "안드레 카파시가 옵시디언이 'ideal frontend'라고 이야기를 했어요. 지식을 입력하기 위한, 조회하기 위한 인간을 위한 프론트엔드 입력 장치."

### 4. Gold In, Gold Out — 목적 있는 수집 (4:49-6:29)
[바로가기](https://www.youtube.com/watch?v=cNlvrU-KcRg&t=289s)

#### 핵심 메시지
수집한 정보가 "나의 지식"이 되려면 목적이 있어야 한다. 왜 수집했는지 적을 수 없으면 의도적 수집이 아니다.

#### 상세 내용
- 나의 지식 = 목적을 갖고, 가치를 느껴서, "진짜로 쓸모 있겠다"고 판단하여 수집한 것
- 의미(meaning)가 있어야 함 — 왜 수집했는지 적을 수 없으면 의도적 수집이 아님
- 목적 있는 수집 → AI가 활용할 수 있는 골드 데이터
- 목적 없는 수집 → 쓰레기 데이터 → 쓰레기 아웃풋
- "Garbage In, Garbage Out"을 "Gold In, Gold Out"으로 전환 (3년 전부터 사용하는 표현)

#### 주요 발언
> "왜 수집을 했는지 이것을 적을 수 없다면 이거는 진짜 의도적인 수집이 아닙니다."

> "Garbage In, Garbage Out. 저는 이것을 3년 전부터 Gold In, Gold Out이라고 부르고 있습니다."

### 5. LLM Wiki란 무엇인가 (6:29-9:44)
[바로가기](https://www.youtube.com/watch?v=cNlvrU-KcRg&t=389s)

#### 핵심 메시지
안드레 카파시가 제안한 LLM Wiki는 AI를 통해 수집한 지식을 체계적으로 소화하고 연결하는 프레임워크로, 큰 아이디어만 제시하고 각자 버전을 만들도록 열어두었다.

#### 상세 내용
- 카파시의 주요 트렌드 기여: 바이브 코딩(2025.2), 컨텍스트 엔지니어링(2025.6), LLM Wiki(2025.4.3)
- LLM Wiki = 클로드 코드 같은 도구로 지식을 소화하고 연결하는 프레임워크
- 완전하게 구조화된 것이 아닌 큰 아이디어만 제공 → 각자 자기 버전으로 발전

##### LLM Wiki 프로세스
1. 인터넷에서 목적 있는 수집 (논문, 영상, 이미지, 아티클 등)
2. Raw 폴더에 수집물 저장
3. LLM 기반 에이전트(클로드 코드)가 인제스트 — 연관성 확인, 링크 생성, 간극 채우기, 분해
4. Wiki 폴더에 정리 — 목차, 목록, 인덱스 생성 → 통합된 책처럼 계속 축적
5. 개념과 개체를 분리하여 특정 규칙에 따라 정리
6. 주기적으로 LLM에게 최신화 요청 → 기존 내용과 연결/업데이트 루프

##### 스키마의 역할
- LLM에게 랜덤으로 하지 말고 특정 방법을 따르라는 규칙
- 나의 기준과 목적도 포함 — 목적성 있는 수집의 핵심

#### 주요 발언
> "이 아저씨가 날렸으면 또 엄청 큰 파도가 옵니다."

> "특정한 프로세스와 원칙과 기준에 의해서 계속 일어나는 것이 매우 큰 포인트입니다."

### 6. LLM Wiki vs RAG (9:44-12:55)
[바로가기](https://www.youtube.com/watch?v=cNlvrU-KcRg&t=584s)

#### 핵심 메시지
LLM Wiki는 RAG와 비교하여 세팅이 간단하고, 인프라가 불필요하며, 지식이 복리로 축적된다.

#### 상세 내용

| 비교 항목 | RAG | LLM Wiki |
|-----------|-----|----------|
| 세팅 복잡도 | 높음 (임베딩 모델, 벡터DB) | 낮음 (마크다운 폴더) |
| 인프라 | 벡터DB 필요 | 로컬 파일/폴더만 필요 |
| 검색 신뢰도 | 불안정 (문서 품질에 따라 변동) | 높음 (목차/스키마 기반) |
| 지식 축적 | 선형 (새 문서마다 재업데이트 필요) | 복리 (연결 형태로 계속 활용) |
| 최신화 | 수동 업데이트 필요 | 자동 연결/업데이트 루프 |

- RAG의 한계: 문서가 잘못 정리되거나 의미가 덜한 문서가 들어오면 성능 저하
- LLM Wiki의 장점: AI와 함께 소화한 내용이라 신뢰도 높음, 그래프로 연결되어 복리 축적
- 다만 LLM Wiki가 100% 검색 신뢰도인지는 미확인 — 할루시네이션 가능성, 문서 증가 시 신뢰도 저하 가능

#### 주요 발언
> "LLM Wiki의 지식 축적은 복리라고 생각이 돼요. 쌓이고 쌓이면 연결을 해주는 형태로 유지되니까 복리 형태로 쌓입니다."

### 7. LLM Wiki 세팅 — 핵심 맥락 작성 (12:55-18:20)
[바로가기](https://www.youtube.com/watch?v=cNlvrU-KcRg&t=775s)

#### 핵심 메시지
LLM Wiki 세팅의 첫 단계는 "나의 핵심 맥락"을 작성하는 것. 3가지 질문에 답하여 AI에게 나의 기준과 목적을 제공한다.

#### 상세 내용

##### 세팅 준비
1. 새 옵시디언 볼트 생성 (예: "LLM Wiki Brain Trinity")
2. "나의 핵심 맥락" 노트 작성

##### 3가지 핵심 질문
1. **나는 누구인가**: 역할, 가치관, 브랜드
2. **왜 기록하고 싶은가**: 기록의 목적, 현재 안 되고 있는 것, 비전
3. **어떤 아웃풋을 만들고 싶은가**: 롱폼 영상, 캐러셀, 숏폼, 글 등

##### 브라이언의 핵심 맥락 예시
- 브레인 트리니티 브랜드의 브라이언, 개인 지식 관리와 AI로 사람들의 목표 성취를 돕고 싶음
- 일상에서 느끼는 생각/감정을 인사이트로 나누어 아웃풋 소재로 활용
- AI 시대 본질적 활용에 대한 인사이트를 전달하고 싶음
- 유튜브 롱폼, 인스타그램 캐러셀/숏폼, 스레드/링크인 숏폼 글쓰기

#### 언급된 사례/에피소드
- **STT 활용**: 키보드로 입력하지 않고 STT(음성 입력)로 자신의 바이브를 담아 핵심 맥락을 작성

#### 주요 발언
> "핵심 맥락이라는 게 결국에는 AI한테 지금 이 순간에 내가 AI를 활용해서 뭔가 하려고 하는데, 무엇이 관련이 있고 어떤 게 중요한지에 대한 내용입니다."

### 8. AI 인터뷰로 깊이 파악 & CLAUDE.md 생성 (18:20-24:20)
[바로가기](https://www.youtube.com/watch?v=cNlvrU-KcRg&t=1100s)

#### 핵심 메시지
사전 작성한 핵심 맥락을 바탕으로 AI가 인터뷰를 진행하여 더 깊은 맥락을 추출하고, 이를 기반으로 CLAUDE.md를 자동 생성한다.

#### 상세 내용

##### 인터뷰 프롬프트
"우리는 지금 AI 세컨드 브레인을 만들고 있어. 나의 핵심 맥락은 내가 사전에 작성한 자기 소개이고, 이걸 읽고 나를 더 깊이 이해하기 위해 인터뷰해 줘."

##### 인터뷰 진행
1. 질문 1: "나는 누구인가" — 역할, 핵심, 감정, 강점
2. 질문 2: "왜 기록하고 싶은가" — 잘 안 되는 것, 비전
3. 질문 3: "어떤 아웃풋을 만들고 싶은가" — 오디언스, 형태

##### CLAUDE.md 생성 프롬프트
"내 볼트에 '나의 핵심 맥락' 파일이 있는데, 이걸 가지고 CLAUDE.md를 만들어 줘. 포함할 섹션: 작업 규칙, 역할, 기대 등"

##### 결과
- 나는 누구인가, 역할, AI에게 기대하는 것, 작업 규칙 등이 포함된 CLAUDE.md 자동 생성
- 기본적인 기준이 되며, 나중에 계속 업데이트하고 구체화 가능

#### 주요 발언
> "조금만 인터뷰를 하고, 몇 가지 프롬프트, 그리고 LLM Wiki 아이디어를 넣었을 뿐인데 이렇게 폴더가 뿅하고 만들어졌어요."

### 9. 폴더 구조 & 위키 스키마 세팅 (24:20-26:28)
[바로가기](https://www.youtube.com/watch?v=cNlvrU-KcRg&t=1460s)

#### 핵심 메시지
카파시의 LLM Wiki 원문을 클로드 코드에 제공하면 폴더 구조와 위키 스키마가 자동 생성되며, 각 폴더마다 하위 CLAUDE.md가 추가되어 맥락이 풍부해진다.

#### 상세 내용
- 카파시 LLM Wiki 전문을 복사 → 클로드 코드에 붙여넣기 → "이 패턴에 맞게 세팅해 줘"
- 생성된 구조: Raw, Wiki, Output 등 폴더
- Raw 폴더: 어떻게 작동하는지, 어떤 것들이 들어가는지에 대한 룰
- Wiki 폴더: 인덱스, 로그, CLAUDE.md (규칙/스키마)
- 각 폴더마다 하위 CLAUDE.md 추가 → 해당 폴더에 대한 맥락을 AI가 추가로 참고

#### 주요 발언
> "각 폴더마다도 CLAUDE.md를 추가하면 되게 좋은 것이, 해당 폴더 안에 내용들을 파악할 때 얘도 읽어서 그 폴더에 대한 맥락도 추가적으로 가지고 오게 됩니다."

### 10. 옵시디언 웹 클리퍼 활용 & 템플릿 커스텀 (26:28-32:35)
[바로가기](https://www.youtube.com/watch?v=cNlvrU-KcRg&t=1588s)

#### 핵심 메시지
옵시디언 웹 클리퍼의 기본 템플릿을 AI로 커스텀하여 LLM Wiki의 Raw 폴더 구조에 맞는 5가지 수집 템플릿을 생성한다.

#### 상세 내용

##### 웹 클리퍼 기본 사용법
- 크롬 웹스토어에서 Obsidian Web Clipper 설치
- 익스텐션 고정 → 클릭으로 웹 페이지를 마크다운으로 옵시디언에 저장
- 메타데이터 자동 입력, 본문 마크다운 변환

##### 템플릿 커스텀 과정
1. 기본 템플릿을 JSON으로 내보내기
2. JSON 파일을 클로드 코드에 제공: "이 기본 템플릿을 참고해서 Raw 파일에 맞는 템플릿들을 만들어 줘"
3. AI가 5가지 템플릿 생성: 아티클, 유튜브, 팟캐스트, 책, 연구(리서치)
4. 생성된 JSON을 웹 클리퍼 설정에서 임포트
5. 각 템플릿은 특정 사이트에 자동 트리거 (예: YouTube 사이트 → 유튜브 템플릿)

##### 실습
- 아티클 수집: LLM Wiki 관련 기사를 아티클 템플릿으로 클리핑
- 유튜브 수집: 유튜브 영상을 유튜브 템플릿으로 클리핑 (트랜스크립트 포함)

#### 주요 발언
> "유튜브 채널이다 보니까 유튜브 템플릿이 자동으로 작동이 됐겠죠? 트랜스크립트까지 가져와요."

### 11. 인제스트 — 목적성 있는 지식 소화 (32:35-36:20)
[바로가기](https://www.youtube.com/watch?v=cNlvrU-KcRg&t=1955s)

#### 핵심 메시지
인제스트 프롬프트로 수집한 자료를 위키에 반영하되, 반드시 "나의 관점/코멘트"를 입력하여 목적성 있는 수집을 완성해야 한다.

#### 상세 내용

##### 인제스트 프롬프트
"방금 웹클리퍼로 Raw에 저장한 글들이 있고, 파일들을 읽어주고, 나에게 질문한 후에 위키에 반영해 줘"

##### 핵심 프로세스
1. AI가 소스를 읽고 요약
2. 엔티티 분리 (LLM, RAG, 코덱스 등)
3. **AI가 질문**: "이 소스를 왜 수집했는가?" → 사용자가 관점/코멘트 입력
4. 코멘트를 반영하여 위키 페이지 생성 및 기존 페이지 업데이트

##### 관점 입력의 중요성
- 소스를 반영하기 전에 나의 관점을 넣는 것이 "너무 중요"
- 관점에 대해 대답할 수 없으면 → 목적성 없는 수집
- AI가 CLAUDE.md의 기준도 알지만, 수집 시점의 관점이 있어야 맥락을 더 잘 이해

#### 언급된 사례/에피소드
- **아티클 인제스트**: LLM Wiki 관련 기사를 수집 후 "LLM Wiki를 더 잘 공부하기 위해 수집했고, 브레인 트리니티 프로그램을 만들고 싶다"는 관점 입력
- **비디오 인제스트**: 자신의 유튜브 영상을 수집 후 "LLM Wiki와 브레인 트리니티 개념을 연결시켜 발전시키고 싶다"는 관점 입력

#### 주요 발언
> "제일 중요한 것은 내가 이 소스를 반영하기 전에 나의 관점을 넣는 것이 너무 중요합니다. 이 관점에 대해서 내가 대답할 수 없으면 이게 목적성 없는 수집이에요."

### 12. 스킬 생성 & 워크플로우 자동화 (36:20-43:17)
[바로가기](https://www.youtube.com/watch?v=cNlvrU-KcRg&t=2180s)

#### 핵심 메시지
대화를 통해 확인한 패턴을 스킬로 만들어 Ingest/Query/Lint 워크플로우를 자동화하고, 대량의 소스도 효율적으로 처리한다.

#### 상세 내용

##### 스킬 생성 전략
- 2~3번 대화를 통해 패턴을 확인한 후 스킬 생성 요청
- "지금까지 대화한 내용을 바탕으로 스킬을 만들어 줘" → AI가 맥락을 이해하고 스킬 크리에이터로 생성

##### 3가지 핵심 스킬

1. **/ingest (인제스트)**
   - 새 파일들 확인 → 내용 읽기 → 질문 → 위키 반영
   - 자동으로 하나하나 효율적 정리

2. **/query (쿼리)**
   - 위키 내 문서들을 기반으로 질문 답변
   - RAG와 유사하나 벡터DB 대신 위키 문서 기반
   - 답변 중 유용한 것은 Synthesis 페이지에 저장 가능

3. **/lint (린트)**
   - 위키 전체의 깨진 링크, 최신화 안 된 내용, 누락된 연결 수정
   - "도서관을 업데이트시키는" 정리 스킬

##### 대량 인제스트 테스트
- 유튜브 트랜스크립트 3개 + 회의 노트를 한꺼번에 인제스트
- AI가 시리즈는 묶어서 소스 페이지로 생성
- PKM, 목적 있는 수집, 무의식의 의식화, 노트의 복리 효과 등 개념 자동 생성
- 주의: 토큰 소모가 매우 큼 (클로드 프로 플랜 사용자 기준)

##### Synthesis (통합 보고서)
- Query 결과 중 유용한 것을 Synthesis 페이지에 저장
- 위키 내 여러 소스를 통합한 보고서 형태
- 직접 활용하기보다 참고하여 새로운 지식을 만들어 나가는 재료

#### 언급된 사례/에피소드
- **Synthesis 예시**: "브레인 트리니티와 LLM Wiki의 상관성"을 쿼리 → 여러 소스 기반 통합 보고서 생성 → 시사점과 실행 방향 포함

#### 주요 발언
> "제가 두 번을 하고 스킬을 만든 것은, 얘가 한 번만 하는 게 아니라 두 번, 세 번 정도 진행해야 패턴을 발견하고 스킬을 더 잘 만들어 주기 때문입니다."

### 13. LLM Wiki의 한계와 Graphify (43:17-47:28)
[바로가기](https://www.youtube.com/watch?v=cNlvrU-KcRg&t=2597s)

#### 핵심 메시지
소스가 많아지면 텍스트 키워드 검색만으로는 비효율적이며, Graphify를 통해 그래프 DB 기반 검색으로 연결 관계 중심의 답변이 가능해진다.

#### 상세 내용

##### LLM Wiki의 한계
- 현재 소스가 적을 때는 충분하지만, 많아질 경우 비효율적
- 기존 Query는 grep으로 키워드 검색 → 그래프 관계를 활용하지 않음
- 옵시디언에 그래프 뷰가 있지만, AI가 그래프 정보를 기반으로 답변하지는 않음

##### Graphify의 탄생
- 카파시 LLM Wiki 트윗에 누군가 "그래프로 작동되면 좋겠다" 코멘트
- 48시간 이내에 누군가 Graphify 개발
- "Knowledge graphs for AI coding assistants"

##### Graphify 작동 방식
1. `graphify wiki` → 위키 폴더의 마크다운 문서를 그래프로 변환
2. 결과물:
   - `graph.json`: AI가 활용하는 그래프 데이터
   - `graph.html`: 시각화된 그래프 (노드/엣지, 클러스터, 커뮤니티)
   - `graph_report.md`: 사람이 읽을 수 있는 마크다운 리포트
3. `graphify query "질문"` → 그래프 노드/엣지 탐색 기반 답변
4. `graphify wiki update` → 변경된 부분만 재추출하여 업데이트

#### 언급된 사례/에피소드
- **48시간 개발**: 카파시 트윗 → 48시간 이내 Graphify 탄생
- **그래프 시각화**: HTML 파일에서 노드 연결, 커뮤니티(유사 개념 클러스터) 확인 가능

#### 주요 발언
> "안드레 카파시가 외쳤는데, 48시간 이내로 누가 만들었습니다."

### 14. 지식 그래프 쿼리 & 마무리 (47:28-52:32)
[바로가기](https://www.youtube.com/watch?v=cNlvrU-KcRg&t=2848s)

#### 핵심 메시지
Graphify의 그래프 기반 쿼리는 텍스트 기반 쿼리와 달리 연결 관계를 탐색하여 더 풍부한 답변을 제공하며, 궁극적으로 가장 중요한 것은 "나의 목적"이다.

#### 상세 내용

##### Graphify Query 실행
- `graphify query "브레인 트리니티와 LLM Wiki의 근본적인 차이"` 실행
- 결과: "그래프에서 N개의 노드와 N개의 엣지를 탐색한 결과" 형태로 답변
- 기존 Query(텍스트 기반 인덱스/로그 검색)와 달리 그래프 탐색 결과 기반

##### 기존 Query vs Graphify Query
| 구분 | 기존 /query | Graphify query |
|------|-------------|----------------|
| 검색 방식 | 텍스트 기반 (grep, 인덱스) | 그래프 노드/엣지 탐색 |
| 관계 활용 | 제한적 | 연결 관계 중심 |
| 결과 형태 | 관련 문서 기반 답변 | 그래프 탐색 결과 기반 답변 |

##### 마무리 핵심 메시지
- 앞으로 옵시디언 + 클로드 코드 사용이 메타가 될 것
- **가장 중요한 것은 나의 목적** — "왜 수집했는지"에 답할 수 없으면 제대로 활용하는 것이 아님
- LLM Wiki + Graphify를 자신의 워크플로우에 어떻게 적용할지 고민 중

#### 주요 발언
> "제일 중요한 건 나의 목적입니다. 목적 없이 단순히 '이걸 왜 수집했지'를 답변할 수 없으면 LLM Wiki를 제대로 활용하는 게 아닙니다."

## 한 줄 요약

LLM Wiki 업무 자동화의 핵심 3요소 = ① **AI가 읽기 좋은 저장 형식** (마크다운 본문 + YAML 메타데이터), ② **자료가 흐르는 번호 폴더 구조** (00_system → 01_inbox → 10_source → 20_extracts → 30_wiki → 40_projects → 50_output → 60_workflow → 90_archive), ③ **사람의 검토 병목을 줄이는 출력 5장치** (요약 / 추론 시각화 / 출처 링크 / 표·좌표 시각화 / 사실·추정·의견 분리).

## 구간별 상세 내용

### 1. 도입 — 보고서 작성 과정의 재설계 (00:00 - 00:48)
[바로가기](https://www.youtube.com/watch?v=nupjGb-wcxw&t=0s)

#### 핵심 메시지
보고서 하나에 회의록·작년 분석·스크랩을 찾아 머릿속에서 연결하는 과정 — 업무 산출물은 4단계를 거치며, **가장 시간을 잡아먹는 것은 자료 조사와 자료의 이해·통합**. 이 부분을 옵시디언+LLM으로 재설계한다.

#### 상세 내용
- 옵시디언 = 단순 메모 앱이 아니라 "노트를 마크다운 파일로 저장하고 노트끼리 연결하는 저장소"
- LLM = 텍스트를 읽고·요약하고·연결하고·재구성하는 데 강함
- 조합: 옵시디언에 쌓은 자료를 LLM이 읽고 연결 → 기획서·사업 보고서·경쟁사 분석 산출

### 2. 저장 형식 — 마크다운 + YAML (00:48 - 02:08)
[바로가기](https://www.youtube.com/watch?v=nupjGb-wcxw&t=48s)

#### 핵심 메시지
자료를 아무렇게나 저장하면 AI가 활용하지 못한다 — **마크다운(본문 구조) + YAML(메타데이터)을 함께** 써야 LLM이 읽기 좋은 노트가 된다.

#### 상세 내용
- **마크다운 본문 구성 예**: 자료 제목 / 핵심 요약 / 핵심 주장 / 근거 / 자기 해석 / 활용 가능성
- **YAML(노트 상단 메타데이터) 구성 예**: 제목(title) / 타입(type) / 소스(source) / 상태(status) / 태그(tags)
- YAML = "노트의 역할에 대한 설명" — LLM이 노트의 성격을 즉시 파악

---

### 3. 폴더 구조 — 자료가 흐르는 번호 체계 (02:08 - 03:32)
[바로가기](https://www.youtube.com/watch?v=nupjGb-wcxw&t=128s)

#### 핵심 메시지
추천 기본 구조 = 번호 폴더 9개. 자료가 수집(01) → 원본(10) → 추출(20) → 지식(30) → 프로젝트(40) → 결과물(50)로 **흐르는** 파이프라인.

#### 상세 내용

| 폴더 | 역할 | 내용물 |
|---|---|---|
| `00_system` | 규칙·도구 | 노트 작성 규칙, 템플릿, 프롬프트 |
| `01_inbox` | 임시 수집함 | 미정리 웹 클리핑, PDF, 아이디어 |
| `10_source` | 원본 자료 | 기사, 보고서, 유튜브 요약, 내부 문서 |
| `20_extracts` | 추출물 | 원본에서 뽑은 핵심 주장·근거·데이터 |
| `30_wiki` | LLM이 정리한 지식 | 개념, 회사, 시장, 업무 프로세스 노트 |
| `40_projects` | 진행 중 업무 | 현재 프로젝트 |
| `50_output` | 최종 결과물 | 기획서, 분기 보고서, 경쟁사 분석 초안 |
| `60_workflow` | 반복 절차 | 반복 업무 절차, 체크리스트 |
| `90_archive` | 보관 | 완료·오래된 자료 |

- **30_wiki의 5분류**: 개념(concept) / 개체(entity) / 사실(fact) / 분석(analysis) / 의사결정(decision)
- 5분류 이유: LLM에게 **정밀한 지시**를 내리기 위해 — "사실만 가져와" / "이전 의사결정과 충돌되는지 확인해 봐"

#### 주요 발언
> "30번 위키를 다섯 개로 나누는 이유는, LLM에게 '사실만 가져와' 혹은 '이전 의사결정과 충돌되는지 확인해 봐' 같은 정밀한 지시를 내리기 위해서입니다." (03:20)

### 4. 검토 병목 — 사람의 검토 부담을 줄이는 5장치 (03:32 - 05:01)
[바로가기](https://www.youtube.com/watch?v=nupjGb-wcxw&t=212s)

#### 핵심 메시지
LLM이 결과물을 빨리 만들어도 **검증은 사람**이 하므로 병목이 생긴다 → 매뉴얼(agent 규칙)에 검토 부담을 줄이는 5장치를 미리 넣는다.

#### 상세 내용
1. **결과물 요약**: 맨 위부터 "세 문장 요약 → 핵심 5개 → 본문 → 의사결정 포인트" 순서로 작성하게 함 — 요약만 읽고 필요한 자료인지 판단
2. **추론 단계 시각화**: LLM이 결론에 도달한 단계를 함께 적게 함 — 결론을 의심하는 게 아니라 **연결 고리만 확인**
3. **출처 표시**: 모든 주장에 위키 노트 링크 — 의심스러우면 원본 즉시 확인
4. **시각화**: 비교는 표로, 포지셔닝은 좌표로
5. **사실·의견 분리**: 결과물 안에서 사실/추정/의견을 라벨로 구분 — **검토 시간을 추정·의견에만 집중**

#### 주요 발언
> "이렇게 요청하면 우리는 긴 보고서를 처음부터 끝까지 읽는 사람이 아니라, 결론과 근거를 빠르게 검토하는 사람이 되는 거죠." (04:54)

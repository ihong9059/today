### 1. Claude Code가 멍청해지는 경험 (0:00-0:21)
[바로가기](https://www.youtube.com/watch?v=oU-BbX0Om4I&t=0s)

#### 핵심 메시지
Claude Code를 사용하는 사람들이 공통적으로 경험하는 현상 - 처음에는 뛰어나다가 시간이 지나면 점점 품질이 떨어짐

#### 상세 내용
- 처음 사용할 때: 파일 구조 파악, 코드 작성, 테스트까지 알아서 처리하는 "천재"
- 1시간 정도 지나면 발생하는 문제들:
  - 아까 만든 파일을 까먹음
  - 방금 정한 규칙을 무시함
  - 심하면 본인이 짠 코드를 덮어씀

#### 주요 발언
> "클로드 코드 쓰시는 분들이 경험 있으실 거예요. 처음엔 천재예요. 파일 구조 파악하고 코드 짜고 테스트까지 알아서 해요. 근데 한 시간쯤 지나면 갑자기 아까 만든 파일을 까먹어요. 방금 정한 규칙을 무시해요. 심하면 본인이 짠 코드를 덮었어요."

### 2. Context Rot이란? (0:21-0:38)
[바로가기](https://www.youtube.com/watch?v=oU-BbX0Om4I&t=21s)

#### 핵심 메시지
이 현상은 사용자 잘못이 아닌 Claude Code의 구조적 한계이며, "Context Rot(컨텍스트 부패)"라는 이름이 있음

#### 상세 내용
- Claude Code의 "컨텍스트 윈도우" = 작업 기억 = 메모장과 같음
- 대화할수록 이 메모장이 채워짐
- 문제는 메모장에 한계가 있다는 것 (100만 토큰이든 200만 토큰이든)
- 메모장이 차기 시작하면 품질 저하 발생:
  - 앞에서 정한 것을 잊어버림
  - 같은 실수를 반복
  - 코드 스타일이 중구난방

#### 언급된 개념
- **컨텍스트 윈도우**: AI가 한 번에 처리할 수 있는 정보의 양, 대화 내용이 쌓이는 메모장
- **Context Rot**: 컨텍스트가 "썩는" 현상, 작업할수록 품질이 저하되는 문제

#### 주요 발언
> "이거 여러분 잘못이 아닙니다. 클로드 코드의 구조적 한계예요. 이름이 있어요. 컨텍스트 롯이라고 합니다."

> "컨텍스트가 썩는 거예요. 작업할수록 클로드 코드가 점점 멍청해지는 현상."

### 3. 바이브코딩의 한계 (0:38-0:59)
[바로가기](https://www.youtube.com/watch?v=oU-BbX0Om4I&t=38s)

#### 핵심 메시지
바이브코딩(AI에게 자연어로 코딩 지시)이 프로젝트 규모가 커지면 한계에 부딪히는 이유

#### 상세 내용
- 바이브코딩의 악순환:
  1. 처음엔 되니까 신나서 계속 시킴
  2. 프로젝트가 커지면 컨텍스트가 터지면서 버그 쏟아짐
  3. 버그 고치려고 또 시키면 더 꼬임
- 이 악순환 때문에 "AI 코딩은 프로토타입까지만"이라는 인식 형성

#### 언급된 사례
- **바이브코딩의 함정**: 초기 성공 경험이 과신으로 이어지고, 프로젝트 복잡도 증가와 함께 문제 발생

#### 주요 발언
> "처음엔 되니까 신나서 계속 시키잖아요. 근데 프로젝트가 커지면 컨텍스트가 터지면서 버그가 쏟아지고 그걸 고치려고 또 시키면 더 꼬이고 이 악순환 때문에 AI 코딩은 프로토타입까지만이라는 인식이 생긴 거거든요."

### 4. GSD 소개 (0:59-1:42)
[바로가기](https://www.youtube.com/watch?v=oU-BbX0Om4I&t=59s)

#### 핵심 메시지
Context Rot 문제를 정면으로 해결하려는 시스템 GSD(Get Shit Done) 소개

#### 상세 내용
- **GSD란**: Claude Code 위에 설치하는 메타프롬프팅 시스템
- **설치 방법**: 터미널에서 `npx gsd-init` 한 줄로 완료
- **동작 방식**: Claude Code 안에 슬래시 커맨드들이 추가됨
- **제작자 철학**:
  - "나는 솔로 개발자다. 코드를 안 짠다. 클로드 코드가 짠다"
  - 스프린트, 스토리, 레트로스펙티브 같은 엔터프라이즈 방법론 불필요
- **신뢰성**: GitHub 스타가 빠르게 증가 중, Amazon/Google/Shopify 엔지니어들이 사용

#### 핵심 구분점
- GSD ≠ 코드를 대신 짜 주는 도구
- GSD = Claude Code가 잘 짜게 만드는 도구 (컨텍스트 관리 시스템)

#### 주요 발언
> "GSD는 코드를 대신 짜 주는 도구가 아니에요. 클로드 코드가 코드를 짜잖아요. GSD는 클로드 코드가 잘 짜게 만드는 도구예요. 컨텍스트를 관리해 주는 거예요."

### 5. 5단계 워크플로우 (1:42-3:25)
[바로가기](https://www.youtube.com/watch?v=oU-BbX0Om4I&t=102s)

#### 핵심 메시지
GSD는 질문→논의→계획→실행→검증의 5단계 사이클을 통해 체계적으로 작업을 진행

#### 상세 내용

**1단계: 질문 (New Project)**
- 명령어: `/gsd new-project`
- GSD가 질문을 쏟아냄: 뭘 만들 거야? 기술 스택은? 제약 조건은? 엣지 케이스는?
- 머릿속의 애매한 기획을 시스템이 강제로 구체화
- 결과물: project.md, requirements.md, roadmap.md 등 자동 생성

**2단계: 논의 (Discuss Phase)**
- 명령어: `/gsd discuss-phase`
- 해당 단계의 모호한 부분을 찾아냄
- 구체적 질문들: 레이아웃은 카드로? 테이블로? 에러 처리는 토스트로? 인라인으로?
- 이 단계를 건너뛰면 Claude Code가 알아서 결정 → 원치 않는 방향으로 갈 수 있음

**3단계: 계획 (Plan Phase)**
- 명령어: `/gsd plan-phase`
- GSD가 먼저 리서치 수행 (라이브러리, 패턴 등)
- XML 형식 계획서 생성: 태스크 이름, 수정할 파일, 구체적 행동, 검증 방법
- 자체 검증: "이 계획대로 하면 목표 달성 되나?" → 안 되면 다시 작성

**4단계: 실행 (Execute Phase)**
- 명령어: `/gsd execute-phase`
- Wave(웨이브) 기반 병렬 실행:
  - 서로 의존성이 없는 계획서들 → 같은 웨이브에서 동시 실행
  - 의존성이 있는 것 → 다음 웨이브에서 순차 실행
- **핵심**: 각 계획서 실행 시 새로운 서브 에이전트가 뜸
  - 프레시한 20만 토큰 컨텍스트
  - 오로지 그 하나의 계획서 실행에만 사용
  - 메인 컨텍스트는 30~40%만 차 있음 → Context Rot 방지
- 태스크 완료 시마다 자동 git commit

**5단계: 검증 (Verify Work)**
- 명령어: `/gsd verify-work`
- 자동 검증: 코드 존재 여부, 테스트 통과 여부
- 사용자 직접 확인: "로그인이 되나? 버튼 누르면 동작하나?"
- 문제 발생 시: 디버그 에이전트 → 원인 분석 → 수정 계획서 생성 → 다시 실행

#### 주요 발언
> "여기서 가장 중요한 건 이거예요. 각 계획서가 실행될 때 새로운 서브 에이전트가 뜨거든요. 프레시한 컨텍스트로 20만 토큰이 오로지 그 하나의 계획서를 실행하는데만 쓰여요."

> "문제가 생기면 git bisect로 정확히 어느 태스크에서 터졌는지 찾을 수 있어요."

### 6. 핵심 1: 컨텍스트 격리 (3:25-3:55)
[바로가기](https://www.youtube.com/watch?v=oU-BbX0Om4I&t=205s)

#### 핵심 메시지
서브 에이전트 구조를 통해 각 에이전트의 컨텍스트를 격리하여 Context Rot 방지

#### 상세 내용
- **팀장-팀원 비유**:
  - 팀장(오케스트레이터): 교통 정리만 담당 ("이거 먼저 해. 이거 끝나면 저거 해.")
  - 팀원(서브 에이전트): 전체 프로젝트 알 필요 없이 담당 부분만 처리
- **기획서 역할**: 3단계에서 만든 plan.md가 팀원에게 전달되는 기획서
- **결과**: 아무도 컨텍스트가 가득 차지 않음
  - 팀장 컨텍스트: 30~40%만 사용
  - 팀원 컨텍스트: 각각 프레시한 상태 유지

#### 주요 발언
> "팀원들한테 전체 프로젝트 다 알 필요 없어. 네 담당 부분만 알면 돼. 대신 이 기획서 보고 해라고 하는 거예요. 각 팀원은 기획서만 읽으면 되니까 머리가 깨끗해요. 컨텍스트가 신선한 거예요."

### 7. 핵심 2: 구조화된 전달 (3:55-4:21)
[바로가기](https://www.youtube.com/watch?v=oU-BbX0Om4I&t=235s)

#### 핵심 메시지
채팅 히스토리 대신 구조화된 마크다운 문서만 전달하여 컨텍스트 품질 향상

#### 상세 내용
- 기존 방식의 문제:
  - 채팅으로 이것저것 시킴 ("이거 만들어 줘", "아 그거 말고 이렇게", "아까 그 파일 다시 수정해 줘")
  - 이 대화 히스토리가 전부 컨텍스트에 쌓임
  - 진짜 필요한 정보는 극히 일부
- GSD의 해결책:
  - 각 단계의 산출물을 구조화된 마크다운 파일로 저장
  - project.md: 프로젝트 비전
  - requirements.md: 요구 사항
  - state.md: 현재 상태와 결정사항
  - 서브 에이전트에게는 이 파일들만 전달 (채팅 히스토리 없이)
- **핵심 인사이트**: 잡다 섞인 10만 토큰 < 핵심만 정리된 2만 토큰

#### 주요 발언
> "이게 왜 중요하냐면 컨텍스트의 질이 달라지거든요. 잡다 섞인 10만 토큰보다 핵심만 정리된 2만 토큰이 훨씬 나은 거예요."

### 8. 핵심 3: 원자적 계획 (4:21-4:53)
[바로가기](https://www.youtube.com/watch?v=oU-BbX0Om4I&t=261s)

#### 핵심 메시지
하나의 계획서가 하나의 서브 에이전트 컨텍스트 안에서 완결될 수 있는 크기로 분할

#### 상세 내용
- **원자적(Atomic) 계획 원칙**:
  - 너무 크면 쪼개고
  - 너무 작으면 합침
- **검증 단계 포함**: 각 계획서 안에 자체 검증 방법이 명시됨
  - "이 커맨드를 쳤을 때 200이 나와야 한다"
  - "이 테스트를 돌렸을 때 통과해야 한다"
- **자기 검증 구조**: 실행하는 에이전트가 스스로 검증 가능
- **비유**: 팀원에게 일 시킬 때 "다 하면 이거 확인해 봐"까지 적어주는 것

#### 주요 발언
> "GSD가 계획서를 만들 때 하나의 계획서가 하나의 서브 에이전트 컨텍스트 안에서 완결될 수 있는 크기로 쪼개요."

> "팀원한테 일시킬 때 다 하면 이거 확인해 봐까지 적어 주는 거예요. 팀장한테 다 했어요 하기 전에 본인이 먼저 체크하는 구조."

### 9. 컨텍스트 엔지니어링 개념 (4:53-6:00)
[바로가기](https://www.youtube.com/watch?v=oU-BbX0Om4I&t=293s)

#### 핵심 메시지
GSD가 해결하는 진짜 문제는 AI와 인간 사이의 커뮤니케이션 문제이며, 이것이 "컨텍스트 엔지니어링"

#### 상세 내용
- **본질적 문제**: 우리가 Claude Code에게 일을 잘 못 시키는 이유
  - 머릿속에 있는 것을 정확하게 전달하지 못함
  - "대충 이런 느낌으로 만들어 줘" → "대충 이런 느낌"으로 결과물 나옴
- **GSD의 역할**: 전달 과정의 시스템화
  - 질문으로 애매한 것 구체화
  - 문서로 정리
  - 구조화된 형태로 전달
- **컨텍스트 엔지니어링 정의**: AI에게 올바른 컨텍스트를 올바른 타이밍에 올바른 형태로 전달하는 기술
- **프롬프트 엔지니어링 vs 컨텍스트 엔지니어링**:
  - 프롬프트 엔지니어링: "어떻게 말하냐"의 문제
  - 컨텍스트 엔지니어링: "무엇을, 언제, 얼마나 보여주냐"의 문제 → 차원이 다름
- **GSD의 모든 기능 설명**:
  - 왜 질문을 많이 하냐? → 올바른 컨텍스트 추출
  - 왜 문서를 만드냐? → 컨텍스트 구조화
  - 왜 서브 에이전트를 쓰냐? → 필요한 컨텍스트만 전달

#### 주요 발언
> "프롬프트 엔지니어링은 어떻게 말하냐의 문제였잖아요. 컨텍스트 엔지니어링은 무엇을 언제 얼마나 보여주냐의 문제예요. 차원이 다른 거예요."

> "결국 GSD의 핵심은 커맨드 몇 개가 아니에요. AI한테 일을 제대로 시키려면 컨텍스트를 설계해야 한다는 원칙이에요."

### 10. GSD 없이도 가져갈 3가지 원칙 (6:00-6:43)
[바로가기](https://www.youtube.com/watch?v=oU-BbX0Om4I&t=360s)

#### 핵심 메시지
GSD를 설치하지 않더라도 이 시스템에서 배울 수 있는 실질적인 3가지 원칙

#### 상세 내용

**원칙 1: 대화를 줄이고 문서를 늘리세요**
- Claude Code에게 채팅으로 이것저것 시키지 말 것
- CLAUDE.md에 프로젝트 구조 정리
- 스킬 파일에 반복되는 지시 정리
- 핵심: 컨텍스트의 질이 올라가면 결과의 질이 올라감

**원칙 2: 큰 작업은 쪼개서 시키세요**
- 최악: "이 앱 전체를 만들어 줘"
- 올바른 방식: "로그인 API부터 만들어 줘. 스펙은 이거야. 끝나면 이 테스트로 확인해 줘."
- 원자적으로 시키면 컨텍스트가 넘칠 일이 없음

**원칙 3: 검증을 자동화하세요**
- 테스트 코드를 먼저 작성
- Claude Code에게 구현 맡기기
- 테스트 통과 = 완료, 실패 = 다시 시키기
- 안전망이 있으면 맘 놓고 맡길 수 있음

#### 주요 발언
> "이 세 가지만 해도 여러분의 클로드 코드 경험은 완전히 달라질 거예요. 컨텍스트롯 문제의 상당 부분이 해결돼요."

- **미래 전망**: 컨텍스트 엔지니어링이 AI를 다루는 사람의 핵심 역량이 될 것

## 전체 인용구 모음

### Context Rot 관련
> "클로드 코드 쓰시는 분들이 경험 있으실 거예요. 처음엔 천재예요. 파일 구조 파악하고 코드 짜고 테스트까지 알아서 해요. 근데 한 시간쯤 지나면 갑자기 아까 만든 파일을 까먹어요."

> "이거 여러분 잘못이 아닙니다. 클로드 코드의 구조적 한계예요. 이름이 있어요. 컨텍스트 롯이라고 합니다."

> "컨텍스트가 썩는 거예요. 작업할수록 클로드 코드가 점점 멍청해지는 현상."

### GSD 역할 관련
> "GSD는 코드를 대신 짜 주는 도구가 아니에요. 클로드 코드가 코드를 짜잖아요. GSD는 클로드 코드가 잘 짜게 만드는 도구예요. 컨텍스트를 관리해 주는 거예요."

> "여기서 가장 중요한 건 이거예요. 각 계획서가 실행될 때 새로운 서브 에이전트가 뜨거든요. 프레시한 컨텍스트로 20만 토큰이 오로지 그 하나의 계획서를 실행하는데만 쓰여요."

### 컨텍스트 엔지니어링 관련
> "프롬프트 엔지니어링은 어떻게 말하냐의 문제였잖아요. 컨텍스트 엔지니어링은 무엇을 언제 얼마나 보여주냐의 문제예요. 차원이 다른 거예요."

> "결국 GSD의 핵심은 커맨드 몇 개가 아니에요. AI한테 일을 제대로 시키려면 컨텍스트를 설계해야 한다는 원칙이에요."

> "이게 왜 중요하냐면 컨텍스트의 질이 달라지거든요. 잡다 섞인 10만 토큰보다 핵심만 정리된 2만 토큰이 훨씬 나은 거예요."

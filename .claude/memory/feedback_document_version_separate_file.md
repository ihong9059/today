문서 버전 업데이트 시 원본을 in-place 수정하지 말고 **별도 파일로 분리** 생성한다.

**Why**: 2026-05-30 DGIST ESCO 운영제안서 v2.0 → v3.0 통합 시 원본 `운영제안서.md`를 직접 수정 → v2.0 별도 파일 부재 상태 발생. 사용자가 이전 단계에서 v2.0 검토본을 별도 파일로 명시적으로 요청했던 패턴을 무시한 실수. 같은 사용자가 v3.0도 별도 파일을 원할 것으로 추론 가능했음에도 in-place 수정함. 버전 추적·발송 이력·롤백 모두 불가능해짐.

**How to apply**:
1. **명명 규칙**: `{문서명}_v{버전}_{YYYY-MM-DD}.md` (예: `운영제안서_v3.0_2026-05-30.md`)
2. **원본 파일**: `{문서명}.md` = latest 심볼릭 (현재 발송본). 항상 가장 최신 버전과 동일 내용 유지
3. **버전 업데이트 절차**:
   - Step 1: 새 버전 파일 별도 생성 (`Copy-Item 원본 → {문서명}_v{새버전}_{날짜}.md`)
   - Step 2: 원본(`{문서명}.md`)도 같은 내용으로 갱신 (latest 발송본 유지)
   - 즉 한 번의 버전 업데이트로 2개 파일이 동시 생성/수정됨
4. **적용 대상**:
   - ESCO/위시캣/외부 발송 제안서
   - 기술자료·보고서·견적서
   - 시방서·계약서·NDA
   - 버전 관리가 중요한 모든 문서 (의심되면 별도 파일 생성이 default)
5. **적용 제외**:
   - 단순 작업 노트·메모
   - 작업보고서 (날짜 자체가 버전 역할)
   - git으로 변경 추적이 충분한 코드/설정 파일

**판단 기준**: 외부에 발송하거나, 사용자가 "이게 v2.0이었나 v3.0이었나" 물을 가능성이 있는 문서면 별도 파일 분리. 회의 시 "그때 보낸 v2.0 좀 보여줘"가 가능해야 함.

**관련 기존 패턴**: 사용자는 검토본도 `운영제안서_검토본_2026-05-30.md`로 별도 파일 패턴 명시적으로 요청. 같은 사용자의 버전 관리 철학이 일관됨.

# 제조업 제품 개발 프로젝트 — 부서간 자료 정리 기준 (옵시디언 적용)

> 작성일: 2026-05-06
> 작성자: 홍광선 (UTTEC) — Claude Code 협업
> 적용 사례: REVITA Dongle V1.0 (IoT 펌웨어 + 하드웨어)
> 핵심 질문: **여러 부서 자료를 어떤 기준으로 넣어야 결과를 확보하기 쉬운가**

---

## 0. 한 줄 요약

제조업 제품 개발 자료의 옵시디언 정리는 "**4축 분류 + 단일 진실 소스(SSoT) + 의사결정 로그(ADR) + 게이트 체크리스트**"로 결과를 확보한다. 폴더는 **제품 단위**, 링크는 **부서·단계·컴포넌트**, 시간은 **로그·게이트**로 분리한다.

---

## 1. 제조업 제품 개발의 본질적 어려움

### 1.1 4가지 갭(Gap)

제조업 자료는 본질적으로 4가지 단절을 안고 시작:

| 갭 | 증상 | 예시 (REVITA) |
|----|------|--------------|
| **부서 사일로** | 영업이 약속한 사양을 개발이 모름 | "장당 1만원 미만" 약속 vs BOM 1.2만원 |
| **시간 차이** | 6개월 전 결정의 근거가 휘발됨 | "왜 buck을 LDO로 안 갔지?" 회의록 분실 |
| **공식 vs 비공식** | 회의록에 없는 메신저 결정이 진실 | 카톡으로 합의된 단가 변경이 ERP에 누락 |
| **외부 vs 내부** | 협력사 자료를 제때 못 받음 | 부품 단종 통지가 배송지에만 옴 |

**결과**: 같은 질문이 매 회의마다 다시 나옴. 의사결정의 근거가 휘발됨. 다음 모델 개발 시 같은 시행착오 반복.

### 1.2 옵시디언이 해결할 수 있는 것 / 없는 것

| 가능 | 불가능 |
|------|--------|
| 의사결정 추적 (ADR) | 실시간 ERP/MES 대체 |
| 부서 자료 단일 색인 | BOM 자동 계산·재고 관리 |
| 시간 흐름 복원 | 도면 CAD 협업 |
| 협력사·고객 컨텍스트 누적 | 정식 ISO 문서 인증 |
| 다음 프로젝트 자산 재활용 | 양산 트래커빌리티(LOT 단위) |

→ **옵시디언 = 의사결정·맥락·연결의 두뇌**. ERP·PLM·MES와 **공존**하며 보완.

## 2. 결과 확보의 정의 (Output ≠ Storage)

### 2.1 "결과 확보가 쉽다"의 4가지 의미

자료를 단순히 모으는 것은 결과가 아니다. 진짜 결과는:

1. **의사결정 재현 가능** — 6개월 후 "왜 이렇게 결정했는지" 5분 안에 답변
2. **이슈 추적 가능** — 이번 주 unresolved 항목과 책임자가 한 페이지에서 보임
3. **양산 이행 빠름** — 다음 게이트(샘플→파일럿→양산) 이행 체크리스트 자동
4. **다음 프로젝트 자산 재사용** — V1 학습이 V2에 자동 상속

### 2.2 KPI (정원사 점검 항목)

| KPI | 목표 | 점검 |
|-----|------|------|
| 의사결정 노트(ADR) 수 | 프로젝트당 10+ | 매월 |
| 미결 이슈 처리율 | 90%/2주 | 주간 |
| 회의록 → ADR 전환율 | 80%+ | 월간 |
| 게이트 체크리스트 통과율 | 95%+ | 게이트별 |
| 외부 자료(협력사) 누락 | 0 | 부품 단종 알림 도달 시 |

## 3. 4축 분류 기준 (Choosing Folders vs Links)

### 3.1 분류 후보 4축

같은 자료를 서로 다른 4가지 방식으로 묶을 수 있다:

| 축 | 예시 | 특성 |
|----|------|------|
| **A. 제품(Product)** | REVITA, AI FanStick, Compressor | 개발의 단위, 가장 안정적 |
| **B. 단계(Stage)** | 기획→설계→시제→파일럿→양산→AS | 시간축, 게이트로 끊김 |
| **C. 부서(Department)** | 영업/구매/생산/개발/품질/서비스 | 작성자 기준, 사일로 위험 |
| **D. 컴포넌트(Component)** | LDO, MCU, 케이스, 펌웨어, BOM | 명사형 엔티티 |

### 3.2 ⭐ 핵심 결정: 무엇을 폴더로, 무엇을 링크로?

**원칙**: 
- 가장 **안정적인 축 1개**를 폴더(물리 위치)로
- 나머지 3개는 **링크·태그·프론트매터**로

**권장 매핑 (제조업 제품 개발 프로젝트)**:

| 축 | 표현 | 사유 |
|----|------|------|
| **A. 제품** | **폴더** (`revita/`, `aiFanStick/`) | 6개월~3년 안정, 모든 자료의 기본 컨테이너 |
| **B. 단계** | **태그·프론트매터** (`#stage/시제`, `stage: pilot`) | 시간 흐름, 자료가 단계 사이를 이동 |
| **C. 부서** | **태그·프론트매터** (`#dept/개발`, `dept: 구매`) | 한 자료가 여러 부서 관련 |
| **D. 컴포넌트** | **엔티티 노트 + 링크** (`[[LDO_MCP1755]]`) | 재사용·검색 단위 |

→ **한 노트 = 한 폴더(제품) + 다중 태그(단계·부서) + 다중 링크(컴포넌트·사람·결정)**

### 3.3 왜 부서를 폴더로 하면 망하는가?

❌ 부서 폴더 트리 (안티패턴):
```
revita/
├── 영업/
├── 구매/
├── 생산/
├── 개발/
└── 품질/
```

**문제**:
1. 한 회의록에 영업+개발+구매 3개 부서 동시 등장 → 어느 폴더에 둘까?
2. 한 부품(LDO)에 대한 결정이 4개 부서에 흩어짐 → 검색 시 4번 따라다녀야
3. 부서 조직이 바뀌면(예: 구매팀 분리) 폴더 구조 전체 재정리 필요

✅ 제품 폴더 + 부서 태그 (권장):
```
revita/
├── 00_허브.md (#product/revita)
├── 회의/2026-05-06_LDO_검토.md (#dept/개발 #dept/구매 #stage/시제)
├── 결정/ADR-007_MCP1755_채택.md (#decision)
├── 컴포넌트 링크 → entities/LDO_MCP1755.md
└── BOM/v1.2_BOM.xlsx (#dept/구매 #stage/양산)
```

→ Dataview로 "**구매 관련 자료만**" 보고 싶으면 `WHERE contains(tags, "dept/구매")` 한 줄로 끝.

## 4. 결과 확보 5대 원칙

### 원칙 1. **단일 진실 소스 (Single Source of Truth, SSoT)**

같은 사실이 여러 노트에 **사본**으로 존재하면 100% 충돌. 사실은 **한 곳에만**, 다른 곳은 **링크 또는 임베드**로 참조.

**예시 (REVITA BOM 단가)**:
```
❌ 영업 견적서.md 안에: "MCP1755 단가 200원"
❌ 회의록.md 안에:    "MCP1755 단가 220원"  ← 충돌
❌ BOM v1.0.md 안에:  "MCP1755 단가 215원"  ← 어느 게 진짜?

✅ entities/LDO_MCP1755.md (진실의 소스):
   - 단가: 215원 (2026-05-06 기준, 디지키 100ea MOQ)
   
✅ 다른 노트들은 임베드:
   ![[LDO_MCP1755#단가]]
   → 단가 변경 시 한 곳만 고치면 모든 곳 반영
```

### 원칙 2. **결정은 ADR (Architecture Decision Record)로**

회의록에 결정이 묻히면 6개월 후 못 찾는다. **결정 1개 = ADR 노트 1개**.

**ADR 템플릿**:
```markdown
---
title: ADR-007 REVITA LDO MP2338GTL→MCP1755 교체
type: decision
status: accepted | proposed | superseded | deprecated
created: 2026-05-06
updated: 2026-05-06
deciders: [홍광선, 회로담당]
tags: [#product/revita, #dept/개발, #stage/시제, #decision]
links: [revita, LDO_MCP1755, MP2338GTL_buck, REVITA_LDO_교체_검토]
---

# ADR-007 REVITA 동글 LDO 교체 결정

## 컨텍스트 (Context)
- 기존 buck(MP2338GTL) standby 전류 과대 (~수십μA)
- 동글은 99% 시간 standby, 1% active 사용 패턴
- 5μA 이하 standby 요구 (코인셀 2년 수명 목표)

## 검토 옵션
1. A안: 펌웨어 EN 제어 (회로 변경 X)
2. B안: 2단 변환 (12V→5V buck → 3.3V LDO)
3. C안: 단순 LDO 교체 (MCP1755-3302E)

## 결정 (Decision)
- **C안 채택** — MCP1755-3302E/MC (Iq 1.6μA, SOT-89, Iout 300mA)
- A안은 후속 펌웨어 단계에서 추가 적용 검토

## 근거 (Rationale)
- 발열 검산: 35°C 상승, SOT-89 패키지로 안전
- 단가 영향: +15원/대 (BOM 1.2% 증가)
- 리드타임: 디지키 재고 충분 (즉시 입수 가능)

## 결과 영향 (Consequences)
- ✅ Standby 5μA 달성 가능
- ⚠️ 회로도 변경 필요 (R&D 1주, PCB rev 1회)
- ⚠️ 영업: 단가 +15원 고객 협상 필요

## 검증 계획
- 시제품 5대 측정 (2026-05-15 목표)
- Active duty cycle 1% 가정 검증
```

**효과**:
- 6개월 후 "왜 MCP1755로 갔지?" → ADR-007 5분 안에 답
- 다음 모델(REVITA V2) 개발 시 ADR-007 참조하여 결정 단축
- 영업이 고객에게 "이 부품 왜 채택?" 질문 받을 때 즉시 근거 제공

### 원칙 3. **회의록에서 ADR을 추출하라**

회의록은 시간순 기록(`log.md` 같은 역할). 하지만 **결정은 ADR로 별도 분리**.

**회의록 처리 패턴**:
```
회의록.md (raw 기록)
  ↓
회의록 안에서 결정 사항 식별
  ↓
ADR 노트 신설 + 회의록에서 ADR로 링크
  ↓
회의록은 컨텍스트 보존, ADR은 결정 추적
```

**REVITA 실례**:
- `회의/2026-05-06_LDO_검토.md` (회의록, 1시간 토론 전체)
- → 추출된 결정: `결정/ADR-007_MCP1755_채택.md`
- → 추출된 액션: `이슈/ISS-023_시제품5대_측정.md`

### 원칙 4. **이슈 트래커는 옵시디언 안에**

GitHub Issues 흉내. **미결 항목 = 별도 노트 + 상태 필드**.

```yaml
---
title: ISS-023 REVITA LDO 시제품 5대 측정
type: issue
status: open | in_progress | blocked | done | wont_fix
priority: P0 | P1 | P2
assignee: 홍광선
due: 2026-05-15
created: 2026-05-06
tags: [#product/revita, #dept/개발, #dept/품질, #stage/시제]
links: [ADR-007_MCP1755_채택, REVITA_시제품_빌드_2026-05]
---
```

**Dataview 한 줄로 미결 이슈 자동 모음**:
```dataview
TABLE status, priority, assignee, due
FROM "revita/이슈"
WHERE status != "done" AND status != "wont_fix"
SORT priority ASC, due ASC
```
→ 매주 월요일 회의에 이 표 1장이면 모든 미결 가시화.

### 원칙 5. **외부 자료는 raw/, 가공물은 별도**

협력사 견적서, 데이터시트, 인증서, 도면 → `raw/`에 **불변** 보관. 내가 가공한 요약·해석은 별도.

```
revita/
├── raw/                          # 불변, 외부 진실
│   ├── 데이터시트/
│   │   ├── MCP1755_datasheet.pdf
│   │   └── MP2338GTL_datasheet.pdf
│   ├── 협력사_견적/
│   │   └── 디지키_2026-05-06_quote.pdf
│   ├── 인증/
│   │   └── KC_인증_REVITA_V1.0.pdf
│   └── 도면/
│       └── REVITA_DONGLE_V1.0_schematic.pdf
└── (가공물은 raw 밖에 위치)
```

→ 협력사가 새 견적 보내도 raw에 추가만 하면 끝. 내 가공물은 안 깨짐.

## 6. 부서별 입력 가이드

각 부서가 옵시디언에 무엇을 어떻게 넣을지 표준화. **한 부서 = 한 가이드**.

### 6.1 영업 부서

**핵심 입력**:
- 고객 요구사항 (Voice of Customer, VoC)
- 견적·계약·납기
- 고객 미팅·전시회 컨텍스트
- 시장·경쟁사 정보

**필수 위치**:
- 고객 정보 → `entities/고객_{이름}.md`
- VoC → `{제품}/사양/고객요구사항_v{N}.md`
- 견적 → `{제품}/영업/견적서_{고객}_{날짜}.md`

**ADR 트리거**:
- 고객 요구 변경 → ADR 작성 (사양 변경 영향)
- 단가 협상 결과 → ADR (BOM 영향)
- 납기 약속 → ADR (생산 영향)

```markdown
2. 동글 단가: 1만원 이하/대

## 변경 이력
- 2026-04-15 v1: 초안
- 2026-05-06 v2: standby 5μA 명시 (이전 "낮을수록 좋음" → 정량화)

## 영향 받는 결정
- ADR-007 LDO 교체 (standby 5μA 만족 위해)
- ADR-005 납기 (시제 50대 6/15 출하)
```

**핵심 입력**:

## 7. 단계 게이트 체크리스트 (Stage-Gate)

### 7.1 5단계 게이트 모델

```
G1 기획 → G2 설계 → G3 시제 → G4 파일럿 → G5 양산
   ↓        ↓        ↓         ↓          ↓
 사양 확정  도면 확정 시작품   소량 양산   본 양산
```

각 게이트 = **체크리스트 노트 1개**. 통과 못하면 다음 단계 진행 X.

### 7.2 게이트 체크리스트 템플릿 (예: G3 시제완료)

```markdown

type: gate
project: revita
status: in_review | passed | failed
gate_date: 2026-05-30
links: [revita, ADR-007_MCP1755_채택, BOM_v1.2, 시험_standby전류_2026-05-15]
tags: [#product/revita, #stage/시제, #gate]
---

## 통과 조건 (모두 ✅ 시 PASS)

### 영업
- [ ] 고객 요구사항 v{N} 확정 (변경 freeze) — VoC v2 (2026-05-06)
- [ ] 단가 목표 BOM 대비 검증

### 개발
- [x] 사양서 v{N} 발행
- [x] 회로도 rev{N} 발행
- [x] 펌웨어 v{N}.{N} 빌드
- [ ] 시험 standby 전류 PASS (5대 모두)
- [ ] EMC 사전 시험 (의무 X, 선택)

### 구매

- [x] EOL 위험 부품 0
- [ ] MOQ 양산 수량 대비 검증

### 생산
- [ ] 공정도 초안
- [ ] 시제 5대 빌드 완료

### 품질
```

### 7.3 게이트의 효과

- 누락 방지: 영업이 단가 목표 검증 안 했으면 다음 단계 X
- 책임 분산: 부서별 체크 항목 명시 → 누가 무엇을 해야 하는지 명확

## 10. 안티패턴 (제조업 특화)

### ❌ 10.1 부서 폴더 트리
- 한 자료가 여러 부서에 걸침 → 분류 마비
- 해결: 제품 폴더 + 부서 태그

### ❌ 10.2 회의록을 결정의 마지막 자리로
- 회의록은 시간 기록일 뿐, 6개월 후 검색 어려움
- 해결: 결정 사항을 ADR로 별도 추출

### ❌ 10.3 BOM을 본문에 풀텍스트로
- 단가 변경 시 모든 노트 갱신 필요
- 해결: BOM 노트는 1개, 다른 곳은 임베드 또는 링크

### ❌ 10.4 영업이 약속한 사양이 개발에 도착 안 함
- 카톡으로 합의된 변경이 사양서에 미반영
- 해결: VoC 노트 1개를 SSoT로, 변경 이력 명시

### ❌ 10.5 협력사 자료를 가공물에 흡수
- 협력사가 새 견적 보내면 가공물 충돌
- 해결: raw/ 불변 보관 + 가공물 별도

### ❌ 10.6 부품 엔티티 없이 노트마다 부품 정보 반복
- "MCP1755 단가 215원, SOT-89, Iq 1.6μA"가 5개 노트에 중복
- 해결: `entities/LDO_MCP1755.md` SSoT 1개 + 다른 곳은 링크·임베드

### ❌ 10.7 게이트 체크리스트 없이 다음 단계 진행
- "되겠지" 하고 양산 이행 → 사후 폭발
- 해결: 게이트 체크리스트 통과 의무화

### ❌ 10.8 변경 이력 없는 사양 v999
- "고객요구사항.md"가 100번 수정됐는데 변경 사유 없음
- 해결: 프론트매터 `revision: 1.2` + 본문 `## 변경 이력` 섹션

### ❌ 10.9 ADR을 만들고 갱신 안 함
- 6개월 후 결정이 뒤집혔는데 ADR은 그대로
- 해결: 새 ADR로 superseded 표시 (`ADR-007 superseded by ADR-015`)

### ❌ 10.10 옵시디언이 ERP를 흉내내려 함
- 재고·발주·LOT 추적까지 옵시디언으로 → 망함
- 해결: ERP는 ERP, 옵시디언은 의사결정·맥락. 두 시스템 공존.

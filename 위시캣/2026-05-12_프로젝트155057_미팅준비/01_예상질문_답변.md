## 🎯 A. AISG 직접 경험 관련 (가장 민감한 영역)

### Q1. AISG 3.0 직접 구현해보신 적 있나요?

**답변**:
> "**솔직히 직접 구현 경험은 없습니다.** 다만 위시캣 공고를 보고 사전 학습을 완료했고, AISG 3.0 스펙의 모든 구성 요소가 저희가 양산·실전 경험을 가진 패턴과 1:1로 대응됨을 확인했습니다."

**보강**:
- RS-485 PHY → Modbus RTU 양산 (KC 인증)
- OOK PHY → CC1101 447.925MHz Replay 직접 구현 (REVITA, 2026-05)
- HDLC 프레임 + CRC-CCITT 16 → BLE Mesh / Modbus 다수
- AISG 3.0 변경점 4개 → BLE Mesh 3,800대 시스템에 모두 대응되는 패턴 보유

→ "**학습 비용은 거의 0**입니다. 90일 일정 중 절반 이상을 실제 포팅·테스트에 쓸 수 있습니다."

### Q2. AISG 2.0은 본 적 있나요?

**답변**:
> "스펙은 분석했지만 직접 구현은 없습니다. 다만 기존 C++ 소스를 받는 즉시 분석 가능합니다."

**보강**:
- 삼성전자/파나소닉에서 대규모 C/C++ 레거시 코드 분석 경험
- 최근에도 타사 펌웨어 분석·포팅 작업 다수
- 분석 → 구조 파악 → 변경점만 수정하는 패턴이 가장 익숙한 작업 방식

### Q3. OOK 변조 정말 직접 구현했나요? 어떤 식으로요?

**답변**:
> "네, **CC1101 트랜시버를 SPI로 직접 제어**해 447.925 MHz Sub-GHz OOK 송수신을 구현했습니다. Zephyr RTOS 공식 드라이버가 없어서 SPI 드라이버부터 직접 작성했습니다."

**보강 (시연 가능)**:
- GitHub: REVITA 프로젝트 remocon 폴더 코드
- 10버튼 OOK 코드 디코딩 + 재현 시스템 완성
- 양방향 송수신 (pca10056 보드 2대)
- "AISG는 캐리어 주파수가 2.176 MHz로 더 낮고, RF 피더 케이블에 Bias-T로 in-band 주입하는 점만 다릅니다. 변조 원리는 동일."

→ **이 답변에서 노트북으로 코드 보여주는 게 가장 강력.**

### Q4. AISG 인증은 받아보셨나요?

**답변**:
> "AISG 특화 인증은 처음입니다. 다만 통신 제품 인증 절차는 익숙합니다 — KC(한국), TELEC(일본), CE(유럽) 3개국 인증을 BLE Mesh 자전거주차장 양산 시 받았습니다."

**보강**:
- 인증 절차의 일반적 단계는 동일 (EMC, EMI, RF 측정, 프로토콜 적합성)
- AISG 인증을 위한 추가 학습은 사전 진행 가능

### Q5. 기지국 ALD 실장비 다뤄본 적 있나요?

**답변**:
> "기지국 ALD 자체는 다뤄본 적 없습니다. 그러나 일본 자전거주차장 3,800대 현장 설치·디버깅 경험으로 **현장 디버깅 능력은 충분히 입증**됐다고 봅니다. 실제 ALD 장비를 현장에서 처음 만나도 빠르게 적응 가능합니다."

## 🔧 B. 기술적 깊이 검증 질문

### Q6. 기존 C++ 소스 코드 분석 어떻게 접근하시나요?

**답변 (단계별)**:
1. **전체 구조 파악**: 디렉토리·파일 구조 → 빌드 시스템 (Makefile / CMake) → 컴파일러
2. **진입점 식별**: main / init → 콜백 흐름 파악
3. **레이어 분리**: PHY / DLL / Application 각 모듈 위치 확인
4. **state machine 매핑**: 통신 프로토콜은 보통 명시적 또는 암묵적 상태 머신 구조
5. **테스트 케이스 작성**: 기존 동작 검증 (회귀 테스트 베이스)
6. **변경점 적용**: AISG 2.0 → 3.0 변경점만 격리해서 수정

**보강**:
- "**기존 코드를 깨지 않고 점진적으로 진화**하는 접근을 선호합니다. 한꺼번에 큰 변경은 위험."

### Q7. Multi-Primary 어떻게 구현하실 건가요?

**답변**:
> "AISG 3.0 Multi-Primary는 한 ALD를 여러 컨트롤러가 동시 제어하는 구조입니다. 핵심은 **동시 접근 시 충돌 방지** + **각 컨트롤러별 독립 상태 관리**."

**보강 (BLE Mesh 패턴 매칭)**:
- BLE Mesh 3,800대 시스템에서 게이트웨이 N개가 하나의 노드를 동시 접근하는 케이스 처리
- mutex / 세마포어 + 트랜잭션 ID 기반 충돌 방지
- 컨트롤러별 세션 상태 분리 (struct array 또는 hash map)
- 우선순위·타임아웃 정책

### Q8. Device Discovery는 어떻게 구현하나요?

**답변**:
> "버스에 broadcast 명령 → 슬레이브 응답 수집 → 디바이스 목록 구성. 타임아웃과 재시도 정책이 핵심."

**보강**:
- BLE Mesh scan + advertising → 디바이스 발견과 구조 동일
- 일본 자전거 3,800대 시스템에서 검증된 패턴
- 응답 없는 디바이스 처리 / 새 디바이스 hot-plug 처리 둘 다 구현 경험

### Q9. Connection Mapping은요?

**답변**:
> "Ping 패킷을 각 RF 채널에 송신 → 어떤 ALD가 어떤 채널로 응답하는지 매핑. 이건 BLE Mesh의 routing table 구축과 같은 원리입니다."

### Q10. CRC-CCITT 16 직접 구현하실 수 있나요?

**답변**:
> "네. Modbus RTU 양산 제품에 CRC-16 (다항식 0xA001 reflected) 구현했고, AISG의 CRC-CCITT (다항식 0x1021)은 비슷한 패턴입니다. **테이블 룩업 방식**으로 구현하면 성능 좋고 안정적입니다."

**보강**: "지원서에 AISG 분석 노트가 있는데, CRC 부분도 사전 검토 완료했습니다."

### Q11. HDLC bit stuffing 처리는?

**답변**:
> "HDLC는 연속 5개 '1' 뒤에 '0'을 자동 삽입 (송신) / 제거 (수신). 비트 단위 처리지만 일반적으로 byte 단위 룩업 테이블로 최적화."

**보강**: "BLE 패킷에서도 유사한 동기화 패턴 처리 경험 있습니다."

## 🏗 E. 현장 테스트 관련

### Q21. 현장 테스트는 어떻게 진행하실 건가요?

**답변**:
> "**용인 기흥구**가 저희 사무실 위치이기도 합니다. **추가 출장비 없이 수시 방문 가능**. 일본 자전거주차장 현장 설치 경험으로 현장 디버깅에도 익숙합니다."

**보강 (단계별)**:
1. 현장 사전 답사 (장비 위치, 케이블, 전원 등 확인)
2. 자체 사무실에서 시뮬레이션 환경 구축 (모의 ALD)
3. 1차 현장 방문 — 통신 수립 확인
4. 2차 현장 방문 — 명령·응답 검증
5. 3차 현장 방문 — 부하·내구성 테스트
6. 최종 인계 시 함께 검증

## 1. 시스템 개요

### 1.1 목적

종량제봉투의 **승인된 수량만 생산되도록 현장에서 실시간 통제**하는 시스템이다.
사후 확인이 아니라 **사전 차단** 방식으로, 허가된 범위를 초과하면 물리적으로 인쇄가 중단된다.

### 1.2 핵심 원칙

```
QR 발급 수량 = 생산 가능한 총량 = 생산 한도
```

- QR은 위조방지 장치가 아니라 **승인 수량 소모 및 기록의 매개**
- 생산 중 모든 판단은 **라인 PC(로컬 DB)** 가 수행
- 서버는 승인 원장과 최종 결과 저장 주체일 뿐, 생산 중에 개입하지 않음

### 1.3 v1 범위

1개 지자체에서 실제 운영 가능한 **실증형 버전**을 목표로 한다.

```
┌─────────────────────────────────────────────────┐
│                  v1 전체 구성                      │
├─────────────┬───────────┬────────┬──────────────┤
│ ① 라인 PC   │ ② 지자체   │ ③ 시민  │ ④ 서버 내장   │
│   프로그램   │   서버     │ 스캔 웹 │  관리자 기능   │
├─────────────┴───────────┴────────┴──────────────┤
│  1차 검토 핵심: ① 라인 PC 프로그램                   │
└─────────────────────────────────────────────────┘
```

## 4. 전체 운영 Flow

### 4.1 생산 준비 Flow

```
[1] 프로그램 시작 (Windows 자동시작)
 │
 ▼
[2] 서버 확인 버튼
 │  GET /api/v1/ranges/line/{line_id}/work-info
 │  → 지자체명, 품목명, 목표수량 등 작업정보 수신
 │
 ▼
[3] Range 불러오기 버튼
 │  GET /api/v1/ranges/line/{line_id}
 │  → ACTIVE Range 수신 (QR_ID 시작~끝 범위)
 │  → 로컬 DB에 저장
 │
 │  ※ 서버 접속 불가 시: 관리자가 USB로 Range 로드 가능
 │     (USB는 반입 수단일 뿐, 자동 적용되지 않음)
 │
 ▼
[4] 마킹기 연결 확인
 │  RS-232 포트 열기 또는 TCP/IP 소켓 연결
 │  → UI에 마킹기 연결 상태 표시
 │
 ▼
[5] 작업 시작 버튼
 │  → 운영 상태: IDLE → RUNNING
 │  → 첫 번째 QR_ID를 ISSUED → SENDING 전환
 │  → 마킹기에 QR 데이터 전송
 │
 ▼
[생산 루프 진입] ──→ 4.2 참조
```

### 4.2 생산 루프 Flow (핵심)

```
┌─────────────────────────────────────────────────────────────┐
│                     생산 루프 (반복)                          │
│                                                             │
│  ┌─────────┐    ┌──────────┐    ┌──────────┐               │
│  │ QR_ID   │    │ QR_ID    │    │ Print    │               │
│  │ ISSUED  │───▶│ SENDING  │───▶│ Done     │               │
│  │ (발급됨) │    │ (전송중)  │    │ 신호수신  │               │
│  └─────────┘    └──────────┘    └────┬─────┘               │
│                                      │                      │
│                                      ▼                      │
│                              ┌──────────────┐               │
│                              │ print_count  │               │
│                              │ +1 즉시 커밋  │               │
│                              └──────┬───────┘               │
│                                     │                       │
│                          ┌──────────┴──────────┐            │
│                          │                     │            │
│                     count < 10            count = 10        │
│                          │                     │            │
│                          ▼                     ▼            │
│                   다음 Print Done        ┌──────────┐       │
│                   대기 (계속 루프)        │ NORMAL   │       │
│                                         │ (완료)    │       │
│                                         └────┬─────┘       │
│                                              │              │
│                                              ▼              │
│                                      다음 QR_ID로           │
│                                      자동 이동              │
│                                     (ISSUED→SENDING)        │
│                                              │              │
│                                              ▼              │
│                                      Range 내 QR_ID         │
│                                      남아있는가?             │
│                                       │          │          │
│                                      Yes         No         │
│                                       │          │          │
│                                  루프 계속    Range 종료     │
│                                              반납 처리      │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 QR_ID 1개의 상세 처리 Flow

```
QR_ID 1개 = 봉투 10장 묶음

  마킹기에 QR 데이터 전송
  │
  ▼
  봉투 #1 인쇄 → Print Done → count=1 → DB 즉시 커밋
  봉투 #2 인쇄 → Print Done → count=2 → DB 즉시 커밋
  봉투 #3 인쇄 → Print Done → count=3 → DB 즉시 커밋
   ...
  봉투 #9 인쇄 → Print Done → count=9 → DB 즉시 커밋
  봉투 #10 인쇄 → Print Done → count=10 → DB 즉시 커밋 → NORMAL 확정
  │
  ▼
  다음 QR_ID로 이동

  ※ 슬롯 번호(#1~#10)는 마킹기 내부 카운터가 처리
  ※ 라인 PC는 print_count만 관리
  ※ 낱장 단위 결과는 서버/라인PC 모두 저장하지 않음
```

## 5. QR 상태 전이도

### 5.1 QR_ID 상태 (단방향, 되돌림 불가)

```
                          ┌─────────────────┐
                          │                 │
                          ▼                 │
  ┌────────┐    ┌──────────┐    ┌──────────┐
  │ ISSUED │───▶│ SENDING  │───▶│ NORMAL   │  정상 완료 (count=10)
  │ (발급)  │    │ (전송중)  │    │ (완료)   │
  └────────┘    └──────────┘    └──────────┘
       │              │
       │              │         ┌───────────┐
       ├──────────────┼────────▶│ DISCARDED │  작업자 폐기
       │              │         │ (폐기)     │
       │              │         └───────────┘
       │              │
       │              │         ┌───────────┐
       ├──────────────┼────────▶│ SKIPPED   │  관리자 Skip
       │              │         │ (건너뜀)   │
       │              │         └───────────┘

  ※ NORMAL, DISCARDED, SKIPPED는 최종 상태 — 변경 불가
  ※ 폐기/Skip은 ISSUED 또는 SENDING 상태에서만 가능
```

### 5.2 라인 PC 운영 상태

```
  ┌──────┐   작업시작   ┌─────────┐
  │ IDLE │────────────▶│ RUNNING │◀──── 복구 성공
  │      │◀────────────│         │
  └──────┘   작업정지   └────┬────┘
                             │
                        에러 발생
                             │
                             ▼
                        ┌─────────┐
                        │  ERROR  │──── 복구 시도
                        └────┬────┘
                             │
                      Range 위반 등
                      심각한 오류
                             │
                             ▼
                       ┌───────────┐
                       │ HARD_LOCK │  즉시 인쇄 차단
                       │           │  관리자만 해제 가능
                       └───────────┘
```

## 6. 서버 연동 Flow

### 6.1 API 목록

| API | 메서드 | 용도 | 호출 시점 |
|-----|--------|------|----------|
| `/api/v1/ranges/line/{line_id}` | GET | ACTIVE Range 조회 | 생산 준비 시 |
| `/api/v1/ranges/line/{line_id}/work-info` | GET | 작업 정보 조회 | 서버 확인 시 |
| `/api/v1/production/sync` | POST | 생산 결과 동기화 | 주기적/재연결 시 |
| `/api/v1/line-heartbeat` | POST | 라인 상태 전송 | 주기적 |
| `/api/v1/ranges/{range_id}/return-unused` | POST | 미사용 Range 반납 | 작업 종료 시 |

### 6.2 온라인/오프라인 동기화 Flow

```
[온라인 상태]
  라인 PC ──── production/sync (최대 100건, FIFO) ────▶ 서버
  라인 PC ──── line-heartbeat ────────────────────────▶ 서버

[네트워크 단절 발생]
  │
  ▼
  라인 PC: 생산 판단은 계속 로컬 DB 기준으로 수행 (중단 없음)
  라인 PC: production_logs를 로컬에 누적 저장
  │
  ▼
[네트워크 복구]
  │
  ▼
  라인 PC: 누적된 production_logs를 FIFO 순서로 순차 동기화
           최대 100건씩 전송, 부분 성공 허용
```

**핵심:** 서버가 죽어도 생산은 멈추지 않는다. 모든 판단은 로컬 DB 기준.

## 7. Range 관리

### 7.1 Range 개념

```
Range = QR_ID의 연속 범위 (시작ID ~ 끝ID)
      = 지자체가 승인한 생산 가능 수량 단위

예시: Range #001 = QR_ID 0001 ~ QR_ID 1000 (봉투 10,000장분)
```

### 7.2 Range 입력 경로

```
경로 1: 서버에서 조회 (기본)
  서버 확인 → Range 불러오기 → 로컬 DB 저장 → 생산 시작

경로 2: USB 로드 (보조, 관리자 전용)
  USB 삽입 → 관리자 인증 → USB 로드 버튼 → 검증 → 로컬 DB 저장

  ※ USB만 꽂는다고 자동 적용되지 않음
  ※ 서버 Range와 USB Range는 동시 병렬 사용 불가
```

### 7.3 Range 운영 규칙

```
┌──────────────────────────────────────────────────┐
│  현재 ACTIVE Range    │   다음 대기 Range          │
│  (사용 중, 1건)       │   (최대 1건만 유지)         │
├──────────────────────┼───────────────────────────┤
│  QR_ID 순차 소모 중   │   현재 Range 종료 후 전환   │
└──────────────────────┴───────────────────────────┘

  - 현재 사용 중인 Range를 항상 우선
  - 생산 중 서버 polling 하지 않음
  - Range 소진 시 → 다음 대기 Range로 전환 또는 반납
```

## 8. HARD_LOCK (안전 차단)

### 8.1 발동 조건 (5가지)

| # | 조건 | 설명 |
|---|------|------|
| 1 | Range 이탈 | 현재 QR_ID가 할당 Range를 벗어남 |
| 2 | 최종상태 재사용 | 이미 NORMAL/DISCARDED/SKIPPED인 QR_ID를 다시 사용 시도 |
| 3 | Range 없이 생산 | ACTIVE Range 없이 생산 시작 또는 QR_ID 전송 시도 |
| 4 | 초과 인쇄 | print_count=10인 QR_ID를 다시 전송/SENDING 진입 시도 |
| 5 | QR_ID 불일치 | 로컬 DB 기준 현재 QR_ID와 다른 ID를 강제 송신 시도 |

### 8.2 HARD_LOCK 처리

```
HARD_LOCK 발생
  │
  ├─▶ 즉시 인쇄 차단 (마킹기 전송 중단)
  ├─▶ 자동 해제 불가
  ├─▶ UI에 HARD_LOCK 상태 표시 + 원인 표시
  │
  ▼
해제 절차:
  관리자 인증 → 시스템 복구 버튼 → 원인 확인/조치 → 해제
```

## 9. Print Done 처리 규칙 (가장 중요)

### 9.1 처리 원칙

```
┌───────────────────────────────────────────────────────────┐
│                    Print Done 처리 규칙                     │
├───────────────────────────────────────────────────────────┤
│                                                           │
│  1. 1회 단위로 처리 (배치 커밋 금지)                         │
│  2. DB 커밋이 끝난 뒤에만 print_count 증가 인정              │
│  3. SENDING 상태가 아니면 Print Done 무시                    │
│  4. 100ms 이내 동일 QR_ID 중복 신호 → 무시                  │
│  5. SUCCESS일 때만 count +1                                │
│  6. count = 10 → NORMAL 확정                               │
│                                                           │
└───────────────────────────────────────────────────────────┘
```

### 9.2 처리 시퀀스

```
마킹기 ──Print Done 신호──▶ 라인 PC

  [검증 1] 현재 상태가 SENDING인가?
     No → 무시
     Yes ↓

  [검증 2] 100ms 이내 동일 QR_ID 중복인가?
     Yes → 무시
     No ↓

  [검증 3] 결과가 SUCCESS인가?
     No → 에러 처리
     Yes ↓

  [처리] print_count += 1
         즉시 DB 커밋 (WAL 모드)
         │
         ├── count < 10 → 다음 Print Done 대기
         └── count = 10 → NORMAL 확정 → 다음 QR_ID 이동
```

## 10. 복구 및 작업 재개

### 10.1 작업 정지

```
작업 정지 버튼
  │
  ├─▶ 새로운 QR_ID 전송 중단
  ├─▶ 현재 SENDING 중인 QR_ID의 상태/print_count는 유지
  └─▶ 운영 상태: RUNNING → IDLE
```

### 10.2 작업 재개

```
작업 시작 버튼
  │
  ▼
[1] Buffer Flush (마킹기 내부 버퍼 비우기) ← 반드시 선행
  │
  ▼
[2] 같은 QR_ID를 기존 print_count 기준으로 이어서 진행
    (예: count=7에서 정지 → 재개 시 count=7부터 계속)
```

### 10.3 시스템 복구 (에러/HARD_LOCK 후)

```
시스템 복구 버튼 (관리자)
  │
  ▼
[1] check_connection        ← 마킹기 연결 상태 확인
  │
  ▼
[2] 필요 시 재연결           ← RS-232 포트 재열기 / TCP 재연결
  │
  ▼
[3] 필요 시 recover_device_state  ← 마킹기 상태 복구
  │
  ▼
[4] Buffer Flush             ← 마킹기 내부 버퍼 비우기
  │
  ▼
[5] 현재 QR_ID 재전송        ← 로컬 DB 기준 마지막 QR_ID
  │
  ▼
[6] wait_print_done 워커 재시작  ← Print Done 수신 루프 재개
  │
  ▼
[7] 로컬 DB의 print_count 기준으로 이어서 진행
```

### 10.4 강제종료 복구 (WAL 모드)

```
[정상 운영 중]
  QR #050: count=7 → DB 커밋 완료
  QR #050: count=8 → DB 커밋 중... ← 여기서 정전

[프로그램 재시작]
  SQLite WAL 자동 복구
  → count=7까지 복원 (마지막 성공 커밋)
  → count=8은 미완료이므로 자동 롤백
  → QR #050, count=7부터 재개
```

## 11. 컨트롤러 전환

타 제품 생산이 필요한 경우의 전환 절차:

```
[전환 조건]
  현재 QR_ID가 최종 상태여야 함:
  NORMAL(완료), DISCARDED(폐기), SKIPPED(건너뜀) 중 하나
  ※ SENDING 상태에서는 전환 불가

[전환 절차]
  1. 작업 정지 버튼
  2. 현재 QR_ID 최종 상태 확인
  3. 마킹기 제어 연결 해제
     - RS-232: 포트 닫기
     - TCP/IP: 세션 종료
  4. 기존 컨트롤러 방식으로 전환

  ※ 라인프로그램은 별도 "외부 작업 모드"를 제공하지 않음
```

### 13.3 공통 드라이버 인터페이스

```python
class MarkerDriver(ABC):
    """3개 브랜드 공통 인터페이스"""
    def connect()           # 연결
    def disconnect()        # 해제
    def send_qr_data()      # QR 데이터 전송
    def wait_print_done()   # Print Done 신호 대기
    def flush_buffer()      # 버퍼 비우기
    def get_status()        # 상태 조회
    def recover_state()     # 상태 복구
```

## 15. 핵심 설계 원칙 요약

```
┌────────────────────────────────────────────────────────────┐
│                      5대 핵심 원칙                           │
├────────────────────────────────────────────────────────────┤
│                                                            │
│  1. 로컬 자율 판단                                          │
│     생산 가능 여부, QR_ID 선택, count 누적, 상태 확정,        │
│     Hard Lock 판정, 복구 재개 → 모두 로컬 DB 기준            │
│                                                            │
│  2. 즉시 커밋                                               │
│     Print Done 1회마다 즉시 DB 커밋, 배치 커밋 금지           │
│     DB 커밋 완료 후에만 count 증가 인정                       │
│                                                            │
│  3. 단방향 상태 전이                                         │
│     ISSUED → SENDING → NORMAL (되돌림 불가)                  │
│     최종 상태(NORMAL/DISCARDED/SKIPPED)는 변경 불가           │
│                                                            │
│  4. 안전 우선 차단                                           │
│     의심스러운 상황 → HARD_LOCK → 관리자만 해제               │
│     자동 해제 없음, 자동 무한 재시도 없음                      │
│                                                            │
│  5. 오프라인 생산 연속성                                      │
│     서버 단절 시에도 생산 계속, 재연결 후 FIFO 동기화          │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

## 16. 1차 회신 요청 사항

발주자가 요청한 회신 항목:

1. 라인 PC 중심으로 **구현 가능 여부** (큰 방향)

3. 서버 및 전체 v1 구조까지 포함 시 **직접 대응 가능한 범위**
4. 문서 기준 **예상 개발 기간**

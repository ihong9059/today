============================================================
질문: 이미 구현되어 있는 시스템에 새로운 기능을 추가하거나
기존 기능을 변경할 때, 전체 구조를 이해하고 안전하게 반영하기
위해 어떤 방식으로 작업하시는지 설명해주세요.
============================================================

답변:

양산 제품을 수년간 유지보수한 경험에서 "이미 동작하는 시스템을
건드리는 일"이 가장 위험하다는 것을 잘 알고 있습니다. 한 줄의
변경이 현장에서 수십 대의 장비를 멈추게 할 수 있기 때문입니다.

당사가 양산 제품(EtherCAT 컨트롤러, V-Cut 컨트롤러, 컴프레샤
컨트롤러 등) 유지보수에서 실제로 적용하고 있는 작업 절차를
5단계로 설명드립니다.

------------------------------------------------------------
【1단계】 변경 영향도 분석 (Impact Analysis) — 코드를 손대기 전
------------------------------------------------------------

"어디를 바꿔야 하는가"보다 "바꾸면 어디까지 영향을 받는가"를
먼저 파악합니다.

작업 순서:

(1) 요구사항을 명확한 문장으로 재기술
- 고객 요구사항을 "~를 바꾼다"가 아니라
  "입력 X가 들어오면 출력 Y가 바뀐다" 형태로 변환
- 변경 전/후 동작을 2열 표로 정리
- 변경되지 않아야 할 항목도 명시적으로 기록

(2) 변경 대상 모듈 식별
- grep/ripgrep으로 관련 함수/변수를 전수 검색
- 함수 호출 관계를 역방향으로 따라가며 영향 범위 탐색
- "이 함수를 호출하는 곳은 어디인가?" (caller tree)
- "이 변수에 의존하는 다른 로직은?" (data flow)

(3) 영향도 매트릭스 작성
- 변경되는 파일 / 함수 / 데이터 구조를 표로 나열
- 각 항목에 대해 "직접 변경", "간접 영향", "영향 없음"
  3단계로 분류
- 간접 영향 항목은 반드시 회귀 테스트 대상으로 포함

(4) 하드웨어 영향 검토 (임베디드 특화)
- 변경되는 GPIO/SPI/I2C 핀 확인
- 타이밍/주기에 영향이 있는지 회로도와 교차 검토
- 메모리 사용량/인터럽트 우선순위 변화 여부
- 회로설계 25년 배경으로 S/W 변경이 H/W에 미치는
  영향을 기본적으로 검증

(5) 위험도 평가
- High: 통신 프로토콜/상태 머신/타이밍 변경
- Mid: 로직 변경, 데이터 구조 변경
- Low: UI 문구, 로그 메시지, 상수값

→ High 등급 변경은 별도 설계 리뷰 진행 후 착수

------------------------------------------------------------
【2단계】 최소 변경 원칙으로 설계
------------------------------------------------------------

"동작하는 코드를 가능한 한 건드리지 않는다"가 원칙입니다.

(1) 변경을 추가(Addition)로 바꿀 수 있으면 추가로 한다
- 기존 함수를 수정하지 말고 새 함수를 만들어 호출 경로만 전환
- Feature Flag로 구/신 로직을 동시에 유지 → 문제 발생 시
  즉시 구 로직으로 복귀 가능

(2) 기존 인터페이스는 유지
- 함수 시그니처를 바꾸지 않고 기본값을 가진 인자 추가
- 클래스 상속/데코레이터로 기능 확장
- 기존 호출부의 수정 최소화

(3) 변경 크기를 작게 쪼갠다
- 한 번의 커밋 = 한 가지 의도
- "기능 추가 + 리팩토링 + 버그 수정"을 한 PR에 섞지 않음
- 문제 발생 시 bisect로 원인 커밋 추적 가능

(4) 롤백 경로를 먼저 설계
- "이 변경을 되돌리려면 어떻게 해야 하는가?"를 먼저 답한 후
  착수
- DB 스키마는 마이그레이션 + 역방향 마이그레이션 동시 작성
- 설정 변경은 이전 값 백업

------------------------------------------------------------
【3단계】 격리된 환경에서 구현 (Isolated Development)
------------------------------------------------------------

(1) Feature Branch에서만 작업
- main/production 브랜치는 항상 배포 가능 상태 유지
- feature/<이슈번호>-<간단설명> 네이밍 규칙
- 장기 브랜치는 정기적으로 main을 rebase/merge하여
  충돌 선제 해결

(2) Mock / 시뮬레이터 환경에서 1차 검증
- 실제 하드웨어 없이 동작 가능한 mock 드라이버 준비
- GPIO/SPI/I2C 호출을 mock으로 대체하여 로직만 검증
- 상위 서버/GUI와의 통신은 mock server로 대체
- 이 단계에서 unit test + 통합 테스트 자동화

(3) 개발 보드에서 2차 검증
- 실제 CM4/STM32 보드에 flash 후 단독 시나리오 실행
- logic analyzer 또는 oscilloscope로 신호 타이밍 측정
- 기존 동작과 신규 동작의 waveform 비교

(4) 기존 기능 회귀 테스트 (Regression Test)
- 변경 전 환경에서 수집한 "정상 동작 로그"와 변경 후
  로그를 비교
- pytest 기반 자동화 테스트 스위트 수행
- 영향도 매트릭스의 "간접 영향" 항목 전부 실행

------------------------------------------------------------
【4단계】 단계적 배포 (Gradual Rollout)
------------------------------------------------------------

특히 이미 현장에서 운영 중인 시스템은 한 번에 배포하지
않습니다.

(1) 스테이징 환경 검증
- 사무실 내 동일 하드웨어 구성의 스테이징 장비에서 먼저 동작
- 현장과 동일한 상위 서버/GUI 연동 시뮬레이션
- 최소 24시간 연속 동작 시험

(2) 카나리 배포 (Canary Deployment)
- 전체 장비 중 1~2대에 먼저 신규 버전 배포
- 일정 기간(보통 1주) 모니터링
- 이상 없으면 전체 배포

(3) 원격 업데이트 구조 활용
- 양산 제품은 OTA 업데이트 구조를 기본 탑재
- A/B 파티션 구조로 실패 시 자동 이전 버전 복귀
- systemd의 Restart=on-failure + 재시도 제한으로
  boot loop 방지

(4) 배포 직후 모니터링 강화
- 로그 수집 주기를 일시적으로 높임
- 주요 메트릭(CPU, 메모리, 통신 성공률)을 실시간 감시
- 임계치 초과 시 알림 + 자동 롤백

------------------------------------------------------------
【5단계】 변경 기록 및 인수인계
------------------------------------------------------------

"이 변경을 왜, 어떻게 했는가"를 코드에 남기지 않으면
6개월 뒤 자기 자신도 잊습니다.

(1) 커밋 메시지 규칙
- 제목: 변경 의도 한 줄
- 본문: "왜" (요구사항/버그 배경), "어떻게" (접근 방법),
       "검증" (테스트 결과)
- 관련 이슈 번호 / 장비 시리얼 / 현장 정보 포함

(2) CHANGELOG 및 문서 업데이트
- 사용자 가시적 변경은 CHANGELOG.md에 기록
- 내부 구조 변경은 ARCHITECTURE.md 갱신
- 핀맵이나 프로토콜 변경은 해당 스펙 문서 동시 수정

(3) 현장 설명서 작성
- 설치/담당자가 변경 사항을 이해할 수 있는 한국어 요약
- 변경 전/후 동작 비교
- 이상 동작 시 확인 사항 체크리스트

(4) 회귀 테스트 케이스 추가
- 이번에 발견한 엣지 케이스를 테스트 스위트에 영구 추가
- 다음 변경 시 동일 문제가 재발하지 않도록 방지망 구축

------------------------------------------------------------
【실제 적용 사례 요약】
------------------------------------------------------------

사례 1) EtherCAT 컨트롤러 양산 중 프로토콜 확장
- 운영 중인 양산 제품에 신규 슬레이브 장치 지원 추가
- 접근: 기존 드라이버를 수정하지 않고 신규 Driver 클래스 추가
       + Factory 패턴으로 타입별 분기
- Feature Flag로 신규 장치는 선택적으로 활성화
- 3대 카나리 배포 → 2주 관찰 → 전체 배포
- 결과: 기존 고객사 장비 무중단으로 확장 완료

사례 2) 컴프레샤 컨트롤러 Modbus 레지스터 맵 변경
- 고객 요구로 Modbus 주소 체계 일부 변경 필요
- 접근: 구 주소 + 신규 주소를 동시에 응답하도록 구현
       (호환 모드 1년간 유지 후 구 주소 제거 예정)
- 기존 HMI 수정 없이 신규 HMI 추가 지원
- A/B 테스트 없이 펌웨어 단일 배포로 양측 지원

사례 3) 스마트팩토리 데이터 수집 시스템 신규 설비 타입 추가
- Strategy 패턴 기반 Driver 추상화 덕분에
  기존 코드 0줄 수정하고 신규 Driver 클래스만 추가
- pytest 회귀 테스트 전체 통과 확인 후 배포
- 설비 추가 공수 5일 → 반나절로 단축

------------------------------------------------------------
【핵심 원칙 요약】
------------------------------------------------------------

1. 바꾸기 전에 영향 범위를 먼저 파악한다
2. 가능하면 수정이 아니라 추가로 대응한다
3. 작게 쪼개고 하나씩 반영한다
4. 롤백 경로를 먼저 설계한다
5. Feature Flag로 구/신 로직을 병존시킨다
6. mock → 개발보드 → 스테이징 → 카나리 → 전체의 단계
7. 변경 의도와 검증 결과를 반드시 문서로 남긴다
8. 다음 담당자가 이해할 수 있는 상태로 항상 유지한다

------------------------------------------------------------
본 프로젝트에의 적용
------------------------------------------------------------

본 방송 시스템은 이미 1차 구현 완료 + 현장 일부 연동 상태로,
"동작하는 시스템을 건드리는" 작업 성격이 강합니다.

예상되는 접근:

- 기존 RF/오디오 제어 로직은 가능한 한 건드리지 않고
  신규 기능을 "추가" 형태로 구현
- 상위 GUI/서버와의 프로토콜 변경이 필요하면 구 프로토콜
  호환 모드를 유지한 채 신규 버전 추가
- 각 변경은 Feature Branch + Feature Flag로 격리
- systemd 기반 A/B 배포 구조를 도입하여 현장 업데이트 시
  문제 발생 즉시 자동 이전 버전 복귀
- 현장 배포 전 사무실 동일 하드웨어 스테이징 24시간 시험
- 지하차도/터널 특성상 현장 방문이 제한적이므로, 원격
  업데이트 + 자동 롤백 구조가 특히 중요

당사의 양산 제품 유지보수 경험이 본 프로젝트의 "기존 코드
분석 + 기능 개선 + 신규 기능 + 안정화" 요구사항과 직접
부합합니다.

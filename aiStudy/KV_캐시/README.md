# KV 캐시 (Key-Value Cache) 완전 정리

> 김정호 KAIST 교수 영상의 핵심 키워드 **"KV 캐시"** 를 깊이 이해하기 위한 학습 정리.
> AI 시대가 "지능"에서 "토큰"으로, GPU에서 메모리로 무게중심이 옮겨가는 본질이 여기에 있다.

---

## 1. KV 캐시란 무엇인가 — 한 줄 정의

**KV 캐시**는 Transformer 기반 LLM이 토큰을 한 개씩 생성(자기회귀, autoregressive)할 때, 이전 토큰들의 **Key 벡터(K)** 와 **Value 벡터(V)** 를 메모리에 저장해두고 재사용하는 캐시 메커니즘이다.

- **저장 대상**: 어텐션 레이어에서 계산된 K, V 행렬
- **재사용 대상**: 새 토큰 생성 시 모든 이전 토큰의 K, V를 다시 계산하지 않고 캐시에서 읽음
- **효과**: 디코딩 속도 **수십~수백 배** 향상 (O(N²) → O(N))
- **비용**: 메모리 사용량 증가 (이게 영상에서 말하는 "메모리 폭증"의 핵심)

---

## 2. 왜 필요한가 — Transformer 어텐션의 본질

### 어텐션 계산식

Transformer의 자기 어텐션(Self-Attention):

```
Attention(Q, K, V) = softmax(QKᵀ / √d_k) · V
```

- **Q (Query)**: 현재 토큰의 "질문"
- **K (Key)**: 모든 토큰의 "주소"
- **V (Value)**: 모든 토큰의 "내용"

### KV 캐시가 없으면

토큰 N개를 생성하려면, 매 토큰마다 **이전 1, 2, 3 … N개의 토큰 K/V를 매번 다시 계산**해야 한다.

- 토큰 1개 생성: K, V × 1번 계산
- 토큰 2개 생성: K, V × 2번 계산
- 토큰 N개 생성: K, V × **N(N+1)/2** ≈ **O(N²)** 계산

→ 8K 컨텍스트면 3,300만 번, 128K면 80억 번의 중복 계산.

### KV 캐시가 있으면

이전 토큰의 K, V를 **저장**해두고, 새 토큰 생성 시 **그것에 해당하는 K, V 1개만 추가 계산**:

- 토큰 N개 생성: K, V × **N번** 계산 = **O(N)**
- 중복 계산 제거로 디코딩 속도 폭발적으로 향상

> 💡 **핵심 트레이드오프**: 계산(GPU)을 메모리(HBM)로 바꿔치기한 것. 그래서 김정호 교수가 *"미분 시대가 아니라 메모리 시대"* 라고 한 것.

## 3. KV 캐시 메모리 크기 공식

### 기본 공식

```
KV Cache Memory = 2 × n_layers × n_heads × head_dim × seq_len × batch_size × dtype_bytes
```

- **`2`**: K와 V 두 행렬
- **`n_layers`**: Transformer 레이어 수 (GPT-3: 96, Llama-70B: 80)
- **`n_heads`**: 어텐션 헤드 수 (보통 32~128)
- **`head_dim`**: 헤드당 차원 (보통 64~128)
- **`seq_len`**: 현재 컨텍스트 길이 (토큰 수)
- **`batch_size`**: 동시 처리 사용자 수
- **`dtype_bytes`**: 데이터 타입 (FP16=2, BF16=2, FP8=1, INT4=0.5)

### 실제 모델 사례

| 모델 | 레이어 | 헤드×head_dim | 1토큰당 (FP16) | 128K 컨텍스트 |
|---|---:|---|---:|---:|
| GPT-3 175B | 96 | 96×128 | 4.5 MB | **576 GB** |
| Llama 3 70B | 80 | 64×128 | 2.5 MB | **320 GB** |
| Llama 3 8B | 32 | 32×128 | 0.5 MB | **64 GB** |
| Claude (추정 ~200B) | ~100 | ? | ~5 MB | **~640 GB** |

→ **1명의 사용자**가 128K 컨텍스트로 GPT-3급 모델을 쓰는 데 **576 GB의 HBM** 이 필요. H100 GPU 1장(80 GB) 7장 분량.

---

## 4. "컨텍스트 길이의 제곱" — 영상 발언의 정확한 의미

### 영상 발언

> "KV 캐시 사이즈가 **컨텍스트 길이의 제곱**에 비례해 증가한다."
> "컨텍스트가 KB → 100M 가면 10^18 = **1,000 PB**(페타바이트), 개인당 1,000PB 메모리 필요"

### 기술적으로 분해하면

| 단계 | 복잡도 | 누가 부담 |
|---|---|---|
| KV 캐시 자체 저장 | **O(N)** — 선형 | HBM (메모리) |
| 어텐션 계산 (QKᵀ) | **O(N²)** — 제곱 | GPU (연산) |
| 출력 토큰 생성 시 누적 메모리 접근 | **O(N²)** — 제곱 | HBM 대역폭 |

→ 김 교수가 말한 "제곱"은 **어텐션 메커니즘 전체의 비용**이지, KV 캐시 저장량 단독으로는 **선형(O(N))** 이다. 그러나 추론 시 매 토큰마다 누적된 KV를 모두 읽어야 하므로 **실효 메모리 대역폭 부담은 O(N²)** 로 작용한다.

### 1,000 PB 시나리오 풀이

영상에서 *"컨텍스트 100M 토큰 → 1,000 PB"* 는 다음을 가정한 추정:

- 컨텍스트 100M 토큰 × KV per token (5 MB 가정) = **500 TB / 사용자**
- 멀티 에이전트 8배 + 백그라운드 세션 8배 = **64배 증폭**
- 정밀도 + 배치 곱하면 **1,000 PB급** 도달

→ 즉 KV 캐시 자체보다는 **"많은 사용자 × 긴 컨텍스트 × 멀티 에이전트 × 백그라운드 세션"** 곱셈이 폭발의 본질.

## 5. 메모리 증가의 4대 변수 (영상 핵심)

영상에서 김 교수가 강조한 메모리 증가 변수:

| 변수 | 의미 | 증가 방식 |
|---|---|---|
| **Sequence Length (S)** | 컨텍스트 길이 | 선형 ∝ S |
| **Batch Size (B)** | 동시 사용자 수 | 선형 ∝ B |
| **Precision (P)** | 비트수 (FP16, FP8 등) | 선형 ∝ P |
| **Layers × Heads** | 모델 크기 고정 상수 | 고정 |

```
KV_Cache_Total ∝ S × B × P × (모델 상수)
```

영상 발언 분해:
> "시퀀스 랭스와 배치사이즈 B 곱하기. 저게 10배 10배 되면 100배가 되는 겁니다."

→ **S 10배 + B 10배 = 100배**, 정밀도까지 줄이지 못하면 메모리 1,000배.

## 6. 멀티 에이전트·백그라운드 세션 — 메모리 폭증의 진짜 원인

### (1) 멀티 에이전트 병렬 처리

영상 인용:
> "1개 에이전트로 보고서 X. 여러 개 에이전트가 병렬로 보고서를 작성하고 평가 에이전트가 베스트를 선택"
> "**KV 캐시 8배 폭증**"
> "클로드 코드 유출: 8배 더 메모리가 필요하다"

→ N개 에이전트가 각각 별도의 KV 캐시를 가지면 **N배**. Claude·GPT 같은 시스템이 내부에서 multi-agent로 동작하면 사용자 1명이 8명 분의 KV 캐시 사용.

### (2) 백그라운드 세션

영상 인용:
> "10분 전 ChatGPT 사용 후 10분 후 다시 사용 — 그 10분 동안 끄지 않고 살려둠"
> "클로드 + 퍼플렉시티 + 노트북 동시 사용 — 각각 KV 캐시 누적"
> "결과: 2배 × 2배 = **8배 메모리 폭증**"

→ 세션을 살려두는 이유: 디코딩 시 KV 캐시를 다시 만들면 첫 토큰까지 1~2분 걸림(컴퓨트 바운드). 세션 유지가 사용자 경험에 직결.

### (3) 오토드림 — KV → NAND 마이그레이션

영상 인용:
> "12시간 미사용 시 압축 후 **낸드 플래시로 저장**"
> "**NAND Flash 가격 상승 원인**"

→ HBM에 영원히 두기엔 비싸므로, 일정 시간 후 NAND Flash로 swap. 다음 세션 시작 시 HBM으로 다시 로드. 이게 김 교수가 말한 **HBF(High-Bandwidth Flash)** 의 필요성.

---

## 7. 컴퓨트 바운드 vs 메모리 바운드 — 두 가지 지연

LLM 추론은 두 단계로 나뉘고, 각각 병목이 다르다:

| 단계 | 영문 | 무엇 | 병목 | 지표 |
|---|---|---|---|---|
| **Prefill** | Prefill / Prompt Processing | 입력 프롬프트의 KV 캐시 초기화 | **GPU (Compute Bound)** | First Token Latency (1~2분) |
| **Decode** | Token-by-Token Generation | 다음 토큰 1개씩 생성 | **HBM (Memory Bound)** | Tokens/sec (Throughput) |

영상 인용:
> "첫 단어 출력 속도 (1~2분 걸림) = 레이턴시 = **GPU가 결정** (Compute Bound)"
> "단어 한 개씩 출력 속도 = 스루풋 = **HBM이 결정**"

### 왜 Decode가 메모리 바운드인가

- 매 토큰 생성 시: **누적된 모든 KV 캐시를 HBM에서 읽어야 함**
- 연산량은 적은데(O(N)) 대역폭 부담은 큼
- → HBM 대역폭이 곧 스루풋 한계

→ 이래서 HBM이 더 두꺼워지고(HBM3e, HBM4, HBM5) 빨라져야 토큰 생산량이 늘어남.

## 8. KV 캐시 최적화 기법

KV 캐시가 너무 커서 다양한 압축·최적화 기법이 연구되고 있다:

### (1) Multi-Query Attention (MQA) / Grouped-Query Attention (GQA)

- 어텐션 헤드들이 K, V를 **공유** (단일 또는 그룹으로)
- KV 캐시 크기 **8~16배 감소**
- Llama 2/3, Mistral, Gemini 등 광범위 채택
- 정확도 손실 거의 없음 ✅

### (2) Sliding Window Attention

- 최근 N개 토큰만 어텐션 계산
- Mistral 7B: 4K window
- 장기 의존성 손실 단점 ⚠️

### (3) Quantization (정밀도 압축)

- FP16 → INT8 → INT4 → INT2
- 메모리 절감 2~8배
- 영상의 "터보 어텐션 (16비트 → 3비트)" 시도

영상 평가:
> "그냥 논문에 불과", "정확도 떨어지면 환각 발생", **"부질없다"**

→ 김 교수는 KV 캐시 양자화에 회의적. 정확도 손실이 누적되면 환각·오류 폭증.

### (4) Paged Attention (vLLM)

- KV 캐시를 가상 메모리처럼 페이지 단위로 관리
- 메모리 단편화 해결, 동시 사용자 처리량 ↑
- 현재 추론 서빙의 표준

### (5) KV Cache Offloading

- 활성 토큰만 HBM, 나머지는 CPU RAM / NAND Flash로 오프로드
- 김 교수의 **HBF(High-Bandwidth Flash)** 가 이 방향
- 영상의 "오토드림" 메커니즘

### (6) Speculative Decoding

- 작은 draft 모델이 여러 토큰 미리 생성, 큰 모델이 검증
- KV 캐시 자체는 안 줄지만 디코딩 속도 ↑

## 9. 영상이 그리는 큰 그림 — KV 캐시가 반도체 산업을 바꾼다

### 사슬 구조

```
LLM 능력 향상
  └→ 컨텍스트 길이 증가 (8K → 128K → 1M → 100M)
       └→ KV 캐시 메모리 폭증
            └→ HBM 용량·대역폭 한계
                 └→ HBM4/5/HBF/HBM7 진화
                      └→ 메모리 센트릭 컴퓨팅
                           └→ 삼성·SK하이닉스 부상
```

### KV 캐시 → HBM 진화 로드맵 (영상 정리)

| 세대 | 아키텍처 | 핵심 변화 | 의미 |
|---|---|---|---|
| **HBM3/3e** | GPU + HBM 4~8개 부착 | 현재 표준 | KV 캐시 80~192 GB |
| **HBM4** | 베이스 다이에 GPU 일부 기능 통합 | 디코딩을 HBM 내부로 | 메모리·시스템 반도체 융합 시작 |
| **HBM5** | GPU를 HBM **위(옥상)** 로 이동 | 발열 분리 + 대역폭 2배 | KAIST 김정호 교수 아이디어 |
| **HBF** | HBM + NAND Flash 적층 | 100 TB 용량 | 오토드림 KV 저장 영역 |
| **HBM7** | HBM + HBF + 자체 메모리 네트워크 | 1,000 TB | 메모리가 직접 통신, CPU/GPU 보조 |

### 메모리 센트릭 컴퓨팅의 본질

- **현재**: CPU(왕) → GPU(왕자) → 메모리(하인)
- **미래**: 메모리(중심) ↔ GPU/CPU(보조), 메모리가 자체 네트워크 보유
- **이유**: KV 캐시가 너무 커서 더 이상 GPU 옆에서 시중들 수 없음

## 10. 실전 계산 예시

### 예시 1: 개인 사용자 1명, Claude로 코딩 작업

- 모델: ~200B 파라미터 추정
- 컨텍스트: 200K 토큰 (1M 컨텍스트 모드)
- 정밀도: BF16

```
KV per token ≈ 5 MB
200K 토큰 × 5 MB = 1 TB
+ 멀티 에이전트 8배 = 8 TB
+ 백그라운드 세션 4배 (다른 탭 유지) = 32 TB
```

→ **1명이 32 TB의 HBM/HBF가 필요**

### 예시 2: 기업 사용자 100명 동시

- 사용자당 32 TB × 100명 = **3.2 PB**
- 김 교수의 "1인당 1,000 PB" 주장의 근거:
  - 미래에 멀티 에이전트가 1,000개 단위로 늘면 사용자 1명도 PB급 필요

## 11. 핵심 요약 — 외워야 할 8가지

1. **KV 캐시**는 Transformer가 토큰을 빠르게 생성하기 위해 K, V 행렬을 저장하는 메커니즘
2. **계산을 메모리로 바꿔치기** — GPU 부담을 HBM으로 이전
3. **저장량 자체는 선형 O(N)**, 하지만 대역폭 부담은 **O(N²)**
4. **메모리 = S(컨텍스트) × B(배치) × P(정밀도) × 상수**
5. **멀티 에이전트 + 백그라운드 세션** = 실효 8~64배 증폭
6. **Prefill = Compute Bound (GPU)**, **Decode = Memory Bound (HBM)**
7. **양자화(터보 어텐션)** 는 정확도 손실로 김 교수 회의적
8. **HBM5 + HBF + 메모리 센트릭 컴퓨팅** 이 KV 캐시 문제의 본질적 해법

# AI FanStick 용도 분석 + 갭

## 1. 실제 사용 컨텍스트

### 1-1. 1차 사용 환경 (가장 중요): K-POP 콘서트장

| 특성 | 값 | 시사점 |
|---|---|---|
| 관객 수 | 10,000~50,000명 | 5만 명 동시 BLE/WiFi → 인프라 한계 |
| 인터넷 상태 | **불안정** (잠실주경기장 등) | **오프라인 폴백 가치 ↑** |
| 사용 시간 | 3시간 (콘서트 전·중·후) | 응원봉 배터리 800mAh 한계 |
| 응답 속도 요구 | 즉시감 (< 3초) | 클라우드 ~2초 OK, 8초는 UX 손상 |
| 노이즈 환경 | 매우 높음 (응원함성·음악) | 음성 인식 도전 (별개 이슈) |

### 1-2. 2차 사용 환경: 일상

| 특성 | 값 | 시사점 |
|---|---|---|
| 위치 | 집·외출·이동 중 | Wi-Fi/4G 상시 가능 → 클라우드 우선 |
| 사용 빈도 | 낮음 (주 1~3회) | 모델 다운로드 부담 감수 가능 |
| 응답 시간 요구 | < 5초 OK | 클라우드 권장 |

→ **콘서트장 ≠ 일상**. 두 환경의 요구가 다름. 단일 솔루션 어려움 → 하이브리드 필요.

## 2. 실제 음성 명령 카테고리 (응원봉 mvp 운영 데이터 기반)

### 2-1. 카테고리 A — 콘서트 정보 (가장 빈번)

| 명령 | AI 응답 (예시) | 필요 도메인 지식 |
|---|---|---|
| "다음 곡 뭐야?" | "다음은 '봄날'이야! 분홍색 준비!" | **셋리스트 순서** |
| "이 곡 응원법 알려줘" | "Dynamite는 'BTS! BTS!'로 외쳐!" | **곡별 팬챈트** |
| "지금 떼창 구간이야?" | "30초 후 떼창 시작!" | **곡 가사 타이밍** |
| "아카펠라 구간 언제?" | "곡 후반 30초" | **곡 구조** |

→ **데이터**: 셋리스트 (8곡) + 응원법 + 가사 타이밍 → JSON으로 충분.

### 2-2. 카테고리 B — 멤버 정보

| 명령 | AI 응답 | 필요 지식 |
|---|---|---|
| "RM 생일 언제야?" | "RM은 9월 12일!" | **멤버 프로필** |
| "정국 본명 뭐야?" | "전정국이야" | 멤버 별명·본명 |
| "지민 생일 색깔?" | "노란색!" | 멤버별 응원 색상 |

→ **데이터**: 멤버 7명 × 정보 10개 = 70개 사실.

### 2-3. 카테고리 C — 팬덤 용어

| 명령 | AI 응답 |
|---|---|
| "보라해가 뭐야?" | "보라색처럼 영원히 사랑해. BTS-아미 인사" |
| "아미가 뭐야?" | "BTS 공식 팬덤 이름" |

→ **데이터**: 팬덤 용어 사전 (50~200항목).

### 2-4. 카테고리 D — 자연스러운 대화 (어려운 카테고리)

| 명령 | AI 응답 (어려움) |
|---|---|
| "오늘 콘서트 어땠어?" | (사용자 감정 공감 + 일반 대화) |
| "내가 너무 울었어" | (위로 응답) |
| "내일도 콘서트 있어?" | (일정 + 자연 대화) |

→ **요구**: 일반 자연어 처리 능력 (작은 SLM 한계).

### 2-5. 카테고리 E — LED 색상 추출 (응답 구조화)

모든 응답에 `[LED:R,G,B]` 태그 자동 부착 필요:

```
"다음 곡은 '봄날'이야! 분홍색 준비! [LED:255,182,193]"
```

→ AI가 곡과 색상의 매핑을 학습해야 함 (셋리스트의 메타데이터).

## 3. microGPT 검증 결과와의 갭 4개

### 갭 1 — 학습 데이터 도메인 (영문 이름 vs 한국어 콘서트)

| 항목 | microGPT 검증 | AI FanStick 필요 |
|---|---|---|
| 데이터 | 영문 이름 32,033개 | 한국어 콘서트 QA 500~2000쌍 |
| 형태 | 한 줄에 한 단어 | 질문-응답 쌍 (대화 형식) |
| 언어 | 영어 char-level | 한국어 (자모 또는 BPE) |
| 도메인 | 일반적 이름 패턴 | K-POP 콘서트 도메인 매우 협소 |

→ **갭 메우기**: 콘서트 도메인 QA 데이터셋 구축 (수동 + ChatGPT 합성).

### 갭 2 — vocab 크기 (27 vs 1000~5000)

| 항목 | microGPT | AI FanStick |
|---|---|---|
| vocab | 27 (a~z + BOS) | 1,000~5,000 (한국어) |
| 토크나이저 | char-level | BPE (Byte Pair Encoding) 권장 |
| 한국어 처리 | 불가 | 자모 분리 + BPE |

→ **갭 메우기**: 한국어 BPE 토크나이저 (sentencepiece 또는 자체 구현).

### 갭 3 — 표현력 (4K params vs 자연어 응답)

| 모델 크기 | 표현력 한계 (Karpathy 시리즈 기준) |
|---|---|
| 4K (microGPT) | "이름 1개 생성" |
| 13K (Small-A) | 짧은 영어 단어 |
| 27K (Small-B) | 짧은 영어 문장 |
| 115K (Medium-A) | 짧은 단순 응답 (영어) |
| 240K (Medium-B) | 짧은 단락 (영어) |
| 1M | 짧은 단순 응답 (느슨한 문법) |
| 124M (GPT-2 small) | 실용 응답 가능 |
| 2B (Gemma) | 풍부한 자연어 QA |

→ **갭 메우기**: 단계적 결정
- ESP32-S3 직접 = 100K~500K (간단 응답 + LED 룩업)
- 폰 = 1B~2B (자연어 QA)

### 갭 4 — 응답 구조화 (단순 텍스트 vs JSON)

응원봉 시스템은 다음 응답 형태가 필요:

```json
{
  "response": "다음 곡은 '봄날'이야! 분홍색 준비!",
  "led_color": [255, 182, 193],
  "current_song": {"order": 3, "title": "봄날", ...}
}
```

microGPT는 **단순 토큰 시퀀스만 생성**. LED 추출은 응답 텍스트 후처리 (정규식)로 가능 (Karpathy 시스템 프롬프트 패턴).

→ **갭 메우기**: 학습 시 응답 끝에 `[LED:R,G,B]` 태그 포함 → 추론 시 정규식 파싱. (구현 단순.)

### 갭 5 (추가) — 실행 위치 불일치

응원봉 vault `온디바이스_AI_검토서.md` (2026-02-27)는 **스마트폰의 Gemma 2B (1.2GB)** 를 가정.
본 vault는 **응원봉 ESP32-S3 (520KB SRAM)** 를 검증.

| 위치 | 모델 크기 한계 | 응답 풍부도 | 인터넷 끊김 시 |
|---|---|---|---|
| 응원봉 ESP32-S3 | 4K~500K params | 짧은 응답 | **응원봉 단독 동작** ★ |
| 스마트폰 (폰 RAM 8GB) | 1B~7B params | 본격 자연어 | 폰만 있으면 동작 |
| 클라우드 (현재 운영) | 무제한 | 최고 품질 | **불가** ❌ |

→ **두 위치는 보완 관계, 경쟁 X**. 어느 것을 어디에 쓸지 결정만 필요.

| 5 | 실행 위치 결정 | 결정만 (ESP32 vs 폰) | ★★★★★ |

## 3. Phase 2 — MCU 핀 맵 추출

### 3-1. 목표

MCU의 **모든 핀**에 대해 회로도에서 어떤 네트(Net)에 연결되어 있는지 추출합니다.

### 3-2. 추출 절차

```
Step 1: MCU 심볼을 회로도에서 찾습니다.
        → 보통 가장 핀이 많은 IC입니다.

Step 2: 핀 번호 순서대로 하나씩 읽습니다.
        → 핀 번호, 핀 이름(GPIO), 연결된 네트 라벨을 기록합니다.

Step 3: 네트 라벨이 없는 핀은 "NC (미연결)" 또는 "내부 전용"으로 표기합니다.

Step 4: 전원 핀 (VCC, GND, 3V3, 5V)은 별도 그룹으로 분류합니다.

Step 5: 기능 고정 핀 (BOOT, RESET/EN, 내부 Flash 등)을 식별합니다.
```

### 3-3. 핀 맵 기록 양식

모든 핀을 빠짐없이 기록합니다.

```
| 핀 번호 | 핀 이름 | 네트 라벨 | 방향 | 기능 | 비고 |
|:-------:|---------|-----------|:----:|------|------|
| 1       | 3V3     | VCC       | PWR  | 전원 | 3.3V 출력 |
| 2       | EN      | -         | IN   | 리셋 | Active LOW |
| 3       | VP/IO36 | TP1       | IN   | 테스트포인트 | 입력전용, ADC1_CH0 |
| ...     | ...     | ...       | ...  | ...  | ... |
```

### 3-4. 핀 방향 판별 기준

| 기준 | 방향 | 예시 |
|------|:----:|------|
| LED, 부저, 릴레이 등 구동 | **OUT** | GPIO → 저항 → LED |
| 스위치, 센서 디지털 입력 | **IN** | 스위치 → GPIO |
| I2C SDA/SCL | **I/O** | 양방향 오픈드레인 |
| UART TX | **OUT** | MCU → 외부 |
| UART RX | **IN** | 외부 → MCU |
| SPI MOSI | **OUT** | Master → Slave |
| SPI MISO | **IN** | Slave → Master |
| ADC 입력 | **IN** | 아날로그 신호 → GPIO |
| PWM 출력 | **OUT** | GPIO → 부저/모터 |
| 전원 | **PWR** | VCC, GND |
| 미연결 | **NC** | 아무것도 없음 |

## 4. Phase 3 — 주변장치 회로 분석

### 4-1. 목표

MCU에 연결된 각 주변장치(LED, 부저, 스위치, 센서 등)의 **동작 원리**, **극성(Active HIGH/LOW)**, **부품 값**을 파악합니다.

### 4-2. 분석 순서

```
Step 1: 네트 라벨을 따라가며 MCU → 외부 소자까지의 경로를 추적합니다.

Step 2: 경로상의 모든 부품(저항, 캐패시터, 트랜지스터 등)의 값을 기록합니다.

Step 3: 전류 흐름 방향을 파악하여 Active HIGH / Active LOW를 판별합니다.

Step 4: 구동 전류를 계산합니다 (옴의 법칙).

Step 5: 특수 소자(트랜지스터, MOSFET, 옵토커플러)가 있으면 반전 여부를 확인합니다.
```

### 4-3. 주변장치 유형별 분석 방법

#### (A) LED

```
분석 항목:
  □ GPIO → LED까지의 경로 (직렬 저항 값)
  □ LED 소자 모델/색상
  □ 순방향 전압 (Vf) — 데이터시트에서 확인
  □ 구동 전류 계산: I = (Vcc - Vf) / R
  □ 극성 판별:

    패턴 1 (Active HIGH):
      GPIO ──[R]──▶|── GND
      → GPIO HIGH = LED ON

    패턴 2 (Active LOW):
      VCC ──▶|──[R]── GPIO
      → GPIO LOW = LED ON

  □ MCU의 GPIO 최대 소스/싱크 전류 초과 여부 확인
```

#### (B) 부저 (Buzzer)

```
분석 항목:
  □ 능동(Active) vs 수동(Passive) 부저 구분
    - 능동 부저: DC 전압만 인가하면 소리남 (내장 발진회로)
    - 수동 부저: PWM/교류 신호 필요 (주파수 = 음높이)
  □ 직접 구동 vs 트랜지스터 구동
  □ 트랜지스터 사용 시:
    - NPN: Base HIGH → 도통 → 부저 ON (Active HIGH)
    - PNP: Base LOW → 도통 → 부저 ON (Active LOW)
    - Base 저항 값 기록
    - 베이스 전류 계산: Ib = (Vgpio - Vbe) / Rb
  □ PWM 사용 가능 여부 (수동 부저일 때)
```

#### (C) 스위치 / 버튼

```
분석 항목:
  □ 풀업 vs 풀다운 구성
    - 풀업: 미누름=HIGH, 누름=LOW (Active LOW)
    - 풀다운: 미누름=LOW, 누름=HIGH (Active HIGH)
  □ 내부 풀업/풀다운 사용 vs 외부 저항
  □ 디바운스 회로 유무
    - 하드웨어: RC 필터 (캐패시터 값 기록)
    - 소프트웨어: 필요 시 디바운스 시간 결정 (20~50ms)
  □ GPIO가 입력전용 핀인지 확인
  □ 인터럽트 사용 가능 여부
```

#### (D) 센서 (디지털/아날로그)

```
분석 항목:
  □ 통신 방식 (I2C / SPI / 1-Wire / 아날로그 / 디지털)
  □ 동작 전압 확인 (레벨 시프터 필요 여부)
  □ I2C인 경우: 주소 확인 (데이터시트)
  □ 풀업/풀다운 저항 유무 및 값
  □ 전원 필터 캐패시터 유무
  □ 데이터시트에서 초기화 시퀀스 확인
```

#### (E) 모터 / 릴레이 / 고전류 부하

```
분석 항목:
  □ 구동 회로 (MOSFET / 릴레이 드라이버 / H-브릿지)
  □ 프리휠 다이오드 (역기전력 보호) 유무
  □ 최대 전류 및 전원 분리 여부
  □ PWM 제어 가능 여부
  □ Enable / Direction 핀 구분
```

### 4-4. 주변장치 분석 기록 양식

각 주변장치마다 아래 양식으로 기록합니다.


## 5. Phase 4 — 통신 버스 분석

### 5-1. 목표

I2C, SPI, UART, CAN 등 통신 버스의 핀 배치, 연결 디바이스, 설정값을 파악합니다.

### 5-2. 버스 유형별 분석 체크리스트

#### (A) I2C

```
□ SDA 핀 번호 / GPIO
□ SCL 핀 번호 / GPIO
□ 풀업 저항 값 (외부 / 내부)
□ 풀업 전원 전압 (3.3V / 5V)
□ I2C 포트 번호 (MCU에 여러 I2C가 있을 때)
□ 연결된 디바이스 목록:
  □ 디바이스명 / 모델
  □ I2C 주소 (7비트) — 데이터시트에서 확인
  □ 주소 핀(A0/A1/A2) 상태 (주소 변경 가능 여부)
  □ 동작 클럭 (100kHz / 400kHz / 1MHz)
□ 같은 버스의 디바이스 간 주소 충돌 여부 확인
□ 레벨 시프터 유무 (3.3V ↔ 5V 혼용 시)
```

#### (B) SPI

```
□ MOSI 핀 / GPIO
□ MISO 핀 / GPIO
□ SCK (SCLK) 핀 / GPIO
□ CS (SS) 핀 / GPIO — 디바이스별 개별 CS 확인
```

## 7. Phase 6 — 제약 조건 및 주의사항 도출

### 7-1. 목표

하드웨어 설계에서 비롯되는 **소프트웨어 레벨의 제약과 주의사항**을 사전에 도출합니다.
이것을 놓치면 보드 brick, 오동작, 하드웨어 손상의 원인이 됩니다.

### 7-2. 공통 체크리스트 (모든 MCU)

```
□ 부팅 관련 핀
  □ 부팅 모드 선택 핀 (예: ESP32 IO0, STM32 BOOT0)
  □ 부팅 시 해당 핀의 레벨 요구사항
  □ 부팅 핀에 주변장치가 연결된 경우 충돌 여부
    (예: ESP32 IO2에 LoRa M0 연결 → 부팅 시 LOW 필요)

□ 입력 전용 핀
  □ 출력으로 사용 불가한 핀 식별
  □ 내부 풀업/풀다운 사용 불가 여부 (MCU별 다름)
  □ 해당 핀에 연결된 주변장치의 입력 회로 확인

□ 핀 공유 / 다중 기능 충돌
  □ 동일 핀에 여러 기능이 할당된 경우 (예: SPI와 JTAG 공유)
  □ 런타임에 기능 전환이 필요한 핀
  □ ADC와 디지털 I/O 동시 사용 제한 (예: ESP32 ADC2 + WiFi)

□ 전압 레벨 불일치
  □ 5V 디바이스 ↔ 3.3V MCU 연결 시 레벨 시프터 필요 여부
  □ 5V tolerant 핀 여부 (데이터시트 확인)

□ 최대 전류 제한
  □ GPIO 개별 핀 최대 소스/싱크 전류
  □ GPIO 전체 합산 최대 전류
  □ 전류 초과 시 트랜지스터/MOSFET 구동 필요 여부

□ 고속 신호 주의
  □ SPI 클럭 최대 속도 제한
  □ 긴 배선에 의한 신호 무결성 문제
  □ 풀업/풀다운 저항 값의 적절성 (I2C 속도 vs 저항)

□ 미사용 핀 처리
  □ 미사용 입력 핀: 풀업/풀다운으로 고정 (플로팅 방지)
  □ 미사용 출력 핀: 별도 처리 불필요
```

## 8. Phase 7 — 핀 정의 헤더파일 작성

### 8-1. 목표

Phase 2~6의 분석 결과를 하나의 **board.h** 헤더파일로 통합합니다.
이 파일이 펌웨어 프로젝트 전체에서 하드웨어 의존성의 **단일 진실 원천(Single Source of Truth)**이 됩니다.

### 8-2. 헤더파일 구성 원칙

```
1. 파일 이름: [보드명]_board.h 또는 board.h
2. Include Guard 필수 (#ifndef / #define / #endif)
3. C++ 호환 (extern "C" 블록)
4. 섹션별 구분 (주석 배너로 구역 분리)
5. 모든 핀 정의에 Doxygen 스타일 주석
6. 극성(Active HIGH/LOW) 반드시 명시
7. 매크로로 ON/OFF 정의 (하드코딩 금지)
8. 전체 핀 맵 요약을 ASCII 아트로 포함
9. 회로 경로를 텍스트로 설명
10. GPIO 비트마스크 매크로 제공 (초기화 편의)
```

### 8-3. 헤더파일 작성 순서

```
Step 1: 파일 헤더 (파일명, 설명, 버전, 날짜, 회로도 참조)
Step 2: Include Guard + extern "C"
Step 3: 출력 장치 핀 정의 (LED, 부저, 릴레이 등)
        → 각각 회로 설명 + Active HIGH/LOW + 전류 계산
Step 4: 입력 장치 핀 정의 (스위치, 센서 디지털 입력)
        → 풀업/풀다운, 디바운스, 입력전용 여부
Step 5: I2C 버스 정의
        → SDA/SCL 핀 + 풀업 + 디바이스별 I2C 주소 + 주요 명령/상수
Step 6: SPI 버스 정의
        → MOSI/MISO/SCK/CS 핀 + 호스트 + 클럭
Step 7: UART 정의
        → TX/RX 핀 + 보레이트 + 추가 제어 핀
Step 8: 기타 핀 (테스트 포인트, 아날로그 입력 등)
Step 9: 전체 핀 맵 요약 (ASCII 아트 테이블)
Step 10: GPIO 비트마스크 / 초기화 도우미 매크로
Step 11: extern "C" 닫기 + #endif
```

### 8-4. 핀 정의 작성 규칙

```c
/* ═══ 작성 규칙 ═══ */

// 1. 핀 번호만 정의 (프레임워크 의존성 최소화)
#define PIN_LED_RED     33      // ✅ 좋음: 숫자만
#define PIN_LED_RED     GPIO_NUM_33  // ❌ 나쁨: ESP-IDF 의존

// 2. 극성을 매크로로 정의
#define LED_ON          1       // Active HIGH
#define LED_OFF         0
#define BEEP_ON         0       // Active LOW
#define BEEP_OFF        1

// 3. 디바이스 주소는 7비트로 통일
#define OLED_I2C_ADDR   0x3C    // ✅ 7비트
#define OLED_I2C_ADDR   0x78    // ❌ 8비트 (혼동 유발)

// 4. 통신 속도/버퍼 크기도 매크로로
#define LORA_UART_BAUD  9600
#define I2C_FREQ_HZ     100000

// 5. 비트마스크는 ULL 접미사 사용 (64비트 안전)
#define LED_MASK  ((1ULL << PIN_LED_RED) | (1ULL << PIN_LED_BLUE))
```

### 9-3. 드라이버 헤더 파일 템플릿

각 주변장치 드라이버의 헤더파일은 다음 패턴으로 작성합니다.

```c
/**
 * @file    led.h
 * @brief   LED 제어 드라이버 API
 */
#ifndef LED_H
#define LED_H

#include "board.h"    // ← 항상 board.h를 참조

/**
 * @brief LED 전체 초기화 (GPIO 출력 설정)
 */
void led_init(void);

/**
 * @brief 개별 LED ON/OFF
 * @param pin   GPIO 핀 번호 (PIN_LED_RED, PIN_LED_YELLOW, PIN_LED_BLUE)
 * @param state LED_ON 또는 LED_OFF
 */
void led_set(int pin, int state);

/**
 * @brief LED 토글
 * @param pin GPIO 핀 번호
 */
void led_toggle(int pin);

/**
 * @brief 전체 LED OFF
 */
void led_all_off(void);

#endif /* LED_H */
```

### 9-4. 드라이버 작성 원칙

```
1. board.h만 참조: 드라이버 코드에 GPIO 번호를 하드코딩하지 않습니다.
   → #include "board.h" 후 PIN_LED_RED 같은 매크로만 사용

2. 하드웨어 추상화: 드라이버 API는 핀 번호가 아닌 논리적 이름을 사용합니다.
   → led_set(PIN_LED_RED, LED_ON)  ← 핀 변경 시 board.h만 수정

3. 초기화 분리: xxx_init() 함수로 GPIO 설정을 분리합니다.
   → main()에서 각 드라이버의 init()을 순서대로 호출

4. 블로킹 최소화: delay가 필요한 경우 RTOS task로 분리합니다.

5. 에러 처리: 통신 드라이버(I2C, SPI, UART)는 반환값으로 성공/실패를 알립니다.
```

## 10. Phase 9 — 검증 및 테스트

### 10-1. 목표

헤더파일과 드라이버가 실제 하드웨어에서 정상 동작하는지 검증합니다.

### 10-2. 검증 순서 (안전한 것부터)

테스트는 반드시 **위험도가 낮은 것부터** 순서대로 진행합니다.

```
Level 1 — 전원 확인 (멀티미터)
   □ 보드 전원 인가 후 각 전원 레일 전압 측정
   □ 3.3V, 5V 레일 확인
   □ 비정상 발열 여부 확인

Level 2 — LED 점멸 (가장 안전한 출력 테스트)
   □ 각 LED 개별 ON/OFF
   □ 전체 LED 순차 점멸 (Chasing)
   □ 극성(Active HIGH/LOW) 실제 확인

Level 3 — 부저 테스트
   □ BEEP 부저 단순 ON/OFF
   □ MELODY 부저 PWM 음계 재생
   □ 극성 및 음량 확인

Level 4 — 스위치/버튼 입력 테스트
   □ 버튼 상태 읽기 (폴링)
   □ 디바운스 동작 확인
   □ 인터럽트 방식 테스트

Level 5 — I2C 스캔
   □ I2C 버스 스캔 → 응답하는 주소 목록 출력
   □ 예상 주소와 실제 응답 비교
   □ OLED 초기화 → 문자 표시
   □ AHT20 → 온도/습도 읽기

Level 6 — UART 통신 테스트
   □ LoRa 모듈 AT 명령 송수신 (설정 모드)
   □ LoRa 정상 모드에서 데이터 송신/수신

Level 7 — SPI 테스트 (디바이스가 있는 경우)
   □ SPI 초기화 → 디바이스 ID 읽기
   □ 데이터 쓰기/읽기 확인

Level 8 — 통합 테스트
   □ 모든 주변장치 동시 동작
   □ 전류 소비 측정 (전원 예산 대비)
```

## 14. 부록 C — 주변장치별 분석 체크리스트

새로운 하드웨어에서 해당 주변장치를 발견했을 때 확인할 항목 목록입니다.

### LED / 표시등

```
□ GPIO 핀 번호
□ 직렬 저항 값 (Ω)
□ LED 색상 / 모델
□ 순방향 전압 Vf (데이터시트)
□ 구동 전류 = (Vcc - Vf) / R
□ Active HIGH or LOW
□ MCU GPIO max current 초과 여부
□ PWM 제어 필요 여부 (밝기 조절)
```

### 부저

```
□ GPIO 핀 번호
□ 능동(Active) vs 수동(Passive)
□ 직접 구동 vs 트랜지스터 구동
□ 트랜지스터 종류 (NPN/PNP/MOSFET) 및 모델
□ 베이스/게이트 저항 값
□ Active HIGH or LOW
□ PWM 필요 여부 (수동 부저)
□ 공진 주파수 (데이터시트)
```

### 스위치 / 버튼

```
□ GPIO 핀 번호
□ 풀업 or 풀다운 (내부/외부)
□ Active HIGH or LOW
□ 디바운스 (하드웨어: RC 값 / 소프트웨어: 시간)
□ 입력전용 핀 여부
□ 인터럽트 지원 여부
□ 다중 버튼일 때 동시 입력 가능 여부
```

### 온습도 / 환경 센서

```
□ 통신 방식 (I2C/SPI/1-Wire/Analog)
□ I2C 주소 (7비트)
□ 동작 전압
□ 초기화 시퀀스 (데이터시트)
□ 측정 명령 및 대기 시간
□ 데이터 변환 공식
□ 정밀도 (±°C, ±%RH)
□ 측정 주기 권장값
```

### 디스플레이 (OLED / LCD)

```
□ 통신 방식 (I2C/SPI/Parallel)
□ 컨트롤러 IC (SSD1306, ST7789, ILI9341 등)
□ I2C 주소 or CS 핀
□ 해상도 (width x height)
□ 색상 (단색/컬러/비트수)
□ 동작 전압
□ 리셋 핀 유무
□ DC (Data/Command) 핀 유무 (SPI 방식)
□ 백라이트 제어 (LCD)
```

### 무선 모듈 (LoRa / BLE / WiFi / Zigbee)

```
□ 통신 인터페이스 (UART/SPI)
□ TX/RX or MOSI/MISO/SCK/CS 핀
□ 보레이트 or SPI 속도
□ 추가 제어 핀 (RESET, EN, AUX, MODE 등)
□ 모드 설정 방법 (M0/M1, AT 명령 등)
□ 상태 표시 핀 (AUX, BUSY, IRQ)
□ 안테나 연결 방식 (내장/외장/U.FL)
□ 동작 전압 및 송신 시 최대 전류
```

### 모터 / 액추에이터

```
□ 모터 종류 (DC/스테퍼/서보)
□ 드라이버 IC or 회로 (H-브릿지, DRV8833, A4988 등)
□ 제어 핀 (PWM, DIR, EN, STEP)
□ 전원 분리 여부
□ 프리휠 다이오드 유무
□ 최대 전류
□ PWM 주파수 권장값
```

### ADC / 아날로그 입력

```
□ GPIO 핀 번호 및 ADC 채널 번호
□ ADC 해상도 (비트)
□ 기준 전압 (Vref)
□ 입력 범위 (0~Vref, 감쇠 설정)
□ 분압 회로 유무 및 비율
□ 필터 캐패시터 유무
□ ADC2 + WiFi 충돌 여부 (ESP32)
```

## 절차서 사용 요약

```
새 하드웨어를 받았을 때:

1. 회로도 PDF를 hardware/ 폴더에 저장
2. 본 절차서의 Phase 1~6을 순서대로 수행 → 분석 워크시트 작성
3. Phase 7: 분석 결과를 board.h 헤더파일로 변환
4. Phase 8: 프로젝트 폴더 구조 생성 + 드라이버 스켈레톤
5. Phase 9: LED → 부저 → 스위치 → I2C → UART 순서로 검증
6. Phase 10: 문서화 + 버전 관리

→ 이 절차를 반복하면, 어떤 MCU/보드라도 체계적으로 프로젝트를 시작할 수 있습니다.
```

> **핵심 원칙**: board.h가 하드웨어와 소프트웨어 사이의 **유일한 계약서**입니다.
> 하드웨어가 바뀌면 board.h만 수정하고, 드라이버 코드는 board.h의 매크로만 참조합니다.
> 이렇게 하면 동일한 펌웨어를 다른 보드에 이식할 때 board.h 교체만으로 대응할 수 있습니다.

# Part 1 — 바이브 코딩 교육 플랫폼 개요

## 1-1. 바이브 코딩이란

```
기존 임베디드 개발:
  코드 작성 → 컴파일 → 케이블 연결 → 플래싱 → 테스트 → 수정 → 반복...
  (6개의 단계, 각각 전문 지식 필요)

바이브 코딩:
  "LED를 0.5초마다 깜빡여줘" → 30초 후 LED가 깜빡인다.
  (1개의 단계, 자연어만 필요)
```

바이브 코딩은 사용자가 코드를 직접 쓰지 않고, **자연어로 의도만 표현**하면
AI가 코드를 생성·빌드·배포까지 자동으로 수행하는 개발 방식입니다.

## 1-2. 교육 플랫폼으로서의 가치

| 기존 임베디드 교육 | 바이브 코딩 교육 |
|-------------------|-----------------|
| IDE 설치부터 시작 (3~6시간) | 앱 하나면 즉시 시작 |
| C/Python 문법 선행 필수 | 자연어로 시작, 코드는 나중에 |
| 컴파일 에러로 좌절 | AI가 에러 자동 수정 |
| 케이블 연결 필수 | 무선으로 배포 |
| 결과 확인까지 수 분 | 30초 이내 결과 확인 |
| "안 되는" 경험이 대부분 | "되는" 경험부터 시작 |

**교육적 핵심**: "되는 경험"을 먼저 하고, "어떻게 되는지"를 나중에 배운다.

## 1-3. 전체 시스템 구조

```
┌──────────────────────────────────────────────────────────────────────┐
│                     바이브 코딩 교육 시스템                          │
│                                                                      │
│  ┌──────────┐     ┌──────────────┐     ┌──────────────────────────┐  │
│  │ 학습자   │     │ 클라이언트   │     │ 클라우드 서버            │  │
│  │          │     │              │     │                          │  │
│  │ "LED를   │────▶│ 스마트폰 앱  │────▶│ Claude Code CLI          │  │
```

# Part 2 — 하드웨어 플랫폼 유형 분류

## 2-1. 3가지 플랫폼 유형

바이브 코딩 교육에 사용할 수 있는 하드웨어는 크게 3가지 유형으로 분류됩니다.

### Type A — MCU 단독형

```
┌───────────────────────────┐
│       MCU 보드 단독        │
│                           │
│  MCU가 직접 무선 통신     │
│  펌웨어를 직접 실행       │
│  컴파일은 클라우드에서    │
│                           │
│  ┌─────────────────────┐  │
│  │  ESP32-C3 SuperMini │  │
│  │  ┌───┐ ┌───┐ ┌───┐ │  │
│  │  │LED│ │BUZ│ │SW │ │  │
│  │  └───┘ └───┘ └───┘ │  │
│  │  ┌────┐ ┌────────┐ │  │
│  │  │I2C │ │BLE/WiFi│ │  │
│  │  │OLED│ │  OTA   │ │  │
│  │  │AHT │ │        │ │  │
│  │  └────┘ └────────┘ │  │
│  └─────────────────────┘  │
└───────────────────────────┘
```

| 항목 | 내용 |
|------|------|
| **대표 보드** | ESP32-C3 SuperMini, ESP32-WROOM DevKitC |
| **코드 언어** | C (ESP-IDF, Arduino) |
| **빌드 위치** | 클라우드 서버 (idf.py build) |
| **배포 방식** | BLE OTA 또는 WiFi OTA |
| **장점** | 저렴, 소형, 실제 임베디드 체험 |
| **단점** | 빌드 환경 필요, OTA 부트로더 사전 설치 |
| **해당 회로도** | esp32c3_ai_super.pdf, esp32Wroom_38.pdf |

### Type B — SBC + MCU 하이브리드형 (Shield 방식)

```
┌───────────────────────────────────────────┐
│    Raspberry Pi + MCU Shield              │
│                                           │
│  ┌─────────────────────────────────────┐  │
│  │  Raspberry Pi (호스트)              │  │
│  │  - WiFi/SSH로 코드 수신             │  │
│  │  - Python 스크립트 직접 실행        │  │
│  │  - UART로 MCU와 통신               │  │
│  │  - GPIO로 일부 직접 제어            │  │
│  │                                     │  │
│  │  ┌──── 40핀 GPIO 헤더 ────┐         │  │
│  │  │  SDA, SCL, UART, SPI  │         │  │
│  │  │  LED, SW, BUZZER 신호 │         │  │
│  │  └───────────┬───────────┘         │  │
│  └──────────────┼─────────────────────┘  │
│                 │ (40핀 연결)             │
│  ┌──────────────┼─────────────────────┐  │
│  │  Shield PCB (MCU + 주변장치)       │  │
│  │              ▼                     │  │
│  │  ┌──────────────────┐              │  │
│  │  │  ESP32-C3        │              │  │
│  │  │  (보조 MCU)      │              │  │
│  │  └──────────────────┘              │  │
│  │  ┌───┐ ┌───┐ ┌───┐ ┌────┐ ┌────┐ │  │
│  │  │LED│ │BUZ│ │SW │ │OLED│ │AHT │ │  │
│  │  └───┘ └───┘ └───┘ └────┘ └────┘ │  │
│  │  ┌──────┐ ┌──────┐ ┌──────────┐  │  │
│  │  │WS2812│ │SPI   │ │LoRa/UART │  │  │

└──────────────────────────────────────────┘
```

| 항목 | 내용 |
|------|------|
| **대표 보드** | Raspberry Pi + ESP32-C3 Shield (raspberry_esp32c3.pdf) |
| **코드 언어** | Python (Pi 직접) + C (MCU, 선택) |
| **빌드 위치** | Pi에서 직접 실행 (Python) 또는 클라우드 (C) |
| **배포 방식** | SSH/SCP (Pi) + UART (Pi→MCU) 또는 BLE OTA (MCU) |
| **장점** | Python으로 즉시 실행, 빌드 불필요, 풍부한 교육 자료 |
| **단점** | 가격 높음, 전력 소모 큼, Pi 설정 필요 |
| **해당 회로도** | raspberry_esp32c3.pdf |

### Type C — SBC 단독형

```
┌───────────────────────────────────────┐
│    Raspberry Pi + GPIO HAT           │
│                                       │
│  ┌─────────────────────────────────┐  │
│  │  Raspberry Pi                   │  │
│  │  - 코드 직접 실행 (Python)      │  │
│  │  - GPIO로 LED/부저/센서 제어    │  │
│  │  - WiFi/SSH로 코드 수신         │  │
│  │  - MCU 없음                     │  │
│  └─────────┬───────────────────────┘  │
│            │ GPIO                      │
│  ┌─────────▼───────────────────────┐  │
│  │  GPIO HAT / 브레드보드          │  │
│  │  ┌───┐ ┌───┐ ┌───┐ ┌────────┐ │  │
│  │  │LED│ │BUZ│ │SW │ │I2C센서 │ │  │
│  │  └───┘ └───┘ └───┘ └────────┘ │  │
│  └─────────────────────────────────┘  │
└───────────────────────────────────────┘
```

| 항목 | 내용 |
|------|------|
| **대표 보드** | Raspberry Pi + Sense HAT, Explorer HAT 등 |
| **코드 언어** | Python |
| **빌드 위치** | 디바이스에서 직접 실행 (인터프리터) |
| **배포 방식** | SSH + SCP (Python 스크립트 전송 → 실행) |
| **장점** | 빌드 불필요, Python 즉시 실행, 교육 자료 풍부 |
| **단점** | 실시간 제어 제한, GPIO 속도 한계, 가격 |
| **해당 회로도** | (별도 GPIO HAT 회로) |

## 2-2. 플랫폼 유형 선택 기준

| 기준 | Type A (MCU 단독) | Type B (SBC+MCU) | Type C (SBC 단독) |
|------|:-----------------:|:-----------------:|:-----------------:|
| 비용 | ★ ($5~15) | ★★★ ($50~80) | ★★ ($40~60) |
| 설정 난이도 | 중 (OTA 부트로더) | 높 (Pi+Shield+MCU) | 낮 (Pi+GPIO) |
| 교육 진입 장벽 | 중 | 중 | 낮 |
| 실시간 제어 | ★★★ | ★★★ | ★ |
| 배포 속도 | 30초 (빌드+OTA) | 5초 (Python) | 3초 (Python) |
| 실제 임베디드 체험 | ★★★ | ★★★ | ★ |
| 확장성 | 중 | 높 | 중 |

```
교육 목적별 권장:
  초등~중학생, 입문자          → Type C (Pi + GPIO HAT)
  고등~대학, 메이커             → Type A (ESP32-C3) 또는 Type B
  임베디드 전공, 프로토타이핑   → Type A (ESP32) 또는 Type B (Pi+Shield)
  IoT 프로젝트, 현장 배포       → Type A (ESP32 + BLE/WiFi OTA)
```

# Part 3 — 하드웨어가 반드시 갖추어야 할 통신 방식

## 3-1. 통신 채널의 3가지 역할

바이브 코딩 시스템에서 하드웨어는 **3가지 통신 채널**이 필요합니다.

```
┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│  채널 1: 배포 채널 (Deployment Channel) ─── [필수]                  │
│  ───────────────────────────────────                                │
│  AI가 생성한 코드/펌웨어를 디바이스에 전달하는 경로                 │
│  없으면 바이브 코딩 자체가 불가능                                   │
│                                                                     │
│  채널 2: 피드백 채널 (Feedback Channel) ─── [권장]                  │
│  ───────────────────────────────────                                │
│  디바이스의 실행 결과를 사용자에게 돌려주는 경로                    │
│  없으면 "됐는지" 눈으로만 확인해야 함                              │
│                                                                     │
│  채널 3: 초기 설정 채널 (Bootstrap Channel) ─── [필수, 1회]         │
│  ───────────────────────────────────                                │
│  최초 1회 부트로더/기본 펌웨어를 설치하는 경로                      │
│  이후로는 배포 채널만으로 운영                                      │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## 3-2. 채널 1 — 배포 채널 (Deployment Channel) [필수]

AI가 생성한 코드를 디바이스에 전달하여 실행시키는 통신 경로입니다.
**이것이 없으면 바이브 코딩이 불가능합니다.**

### 배포 채널 옵션별 상세 비교

```
┌────────────────────────────────────────────────────────────────────────┐
│                        배포 채널 옵션 6가지                            │
│                                                                        │
│  ① BLE OTA ─────── MCU가 BLE를 지원할 때 (ESP32, nRF52)               │
│  ② WiFi OTA ────── MCU가 WiFi를 지원할 때 (ESP32, RP2040W)            │
│  ③ SSH + SCP ───── Linux 기반 SBC (Raspberry Pi, Jetson)               │
│  ④ UART 브릿지 ── SBC가 MCU에 시리얼로 전송 (Pi→ESP32-C3)            │
│  ⑤ USB DFU ────── USB DFU 모드 지원 MCU (STM32, nRF52840)             │
│  ⑥ HTTP Push ──── WiFi 연결된 디바이스에 HTTP로 전송                   │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

### ① BLE OTA (Bluetooth Low Energy Over-The-Air)

```
[스마트폰 앱] ──BLE GATT Write──▶ [MCU OTA 파티션] → 재부팅 → 실행

필요 조건:
  □ MCU에 BLE 스택 내장 (ESP32, ESP32-C3, nRF52, STM32WB)
  □ OTA 부트로더 사전 설치 (최초 1회 USB)
  □ 듀얼 OTA 파티션 테이블
  □ 스마트폰 앱 (Flutter/Kotlin)

장점:
  + 스마트폰만 있으면 됨 (PC 불필요)
  + 근거리 직접 연결 (인터넷 불필요 for 전송)
  + 낮은 전력 소비
  + 교육 현장에서 WiFi 인프라 불필요

단점:
  - OTA 부트로더 사전 설치 필요 (최초 USB)
  - 전송 속도 제한 (1MB ≈ 30~60초)
  - 스마트폰 앱 개발 필요
  - .bin 바이너리 빌드를 클라우드에서 해야 함

적합한 플랫폼: Type A (MCU 단독)
적합한 MCU: ESP32-C3, ESP32, nRF52840, nRF52832
전송 속도: ~20KB/s (BLE 5.0, MTU 517)
최대 거리: ~10m (실내)
```

### ② WiFi OTA (WiFi Over-The-Air)

```
[클라우드 서버] ──HTTPS──▶ [MCU HTTP 클라이언트] → OTA 파티션 → 재부팅

필요 조건:
  □ MCU에 WiFi 스택 내장 (ESP32, ESP32-C3, RP2040W)
  □ WiFi AP 접속 설정 (SSID/Password)
  □ OTA 부트로더 + HTTP OTA 클라이언트
  □ 클라우드 서버에서 .bin 호스팅

장점:
  + 인터넷만 되면 전 세계 어디서든 업데이트
  + 스마트폰 앱 없이 가능 (디바이스가 직접 서버에서 다운로드)
  + BLE보다 빠른 전송 (1MB ≈ 5~10초)
  + 여러 디바이스 동시 업데이트 가능

단점:
  - WiFi 인프라 필요 (SSID/Password 사전 설정)
  - WiFi 전력 소비 높음
  - 보안 고려 필요 (HTTPS, 인증)
  - 교육 현장의 WiFi 제한 (학교 방화벽 등)

적합한 플랫폼: Type A (MCU 단독)
적합한 MCU: ESP32, ESP32-C3, ESP32-S3, RP2040W
전송 속도: ~100KB/s (WiFi)
최대 거리: WiFi AP 범위
```

### ③ SSH + SCP (Secure Shell)

```
[클라우드 서버] ──SSH/SCP──▶ [Raspberry Pi] → Python 스크립트 실행

필요 조건:
  □ Linux 기반 SBC (Raspberry Pi, Jetson Nano, BeagleBone)
  □ SSH 서버 활성화
  □ 네트워크 연결 (WiFi 또는 Ethernet)
  □ Python 인터프리터 설치

장점:
  + 빌드 불필요 (Python 직접 실행)
  + 배포 속도 최고 (스크립트 전송 ~1초)
  + 표준 Linux 도구 모두 사용 가능
  + 디버깅 용이 (SSH 접속 → 로그 확인)

단점:
  - SBC 가격 높음 ($40~80)
  - 네트워크 필수
  - 실시간 제어 제한 (Linux는 RTOS가 아님)
  - 전력 소비 높음 (Pi 4: ~3W idle)

적합한 플랫폼: Type B (SBC+MCU), Type C (SBC 단독)
적합한 SBC: Raspberry Pi 3/4/5, Jetson Nano, BeagleBone
전송 속도: 즉시 (~1초)
```

### ④ UART 브릿지 (SBC → MCU 시리얼 전송)

```
[Pi] ──UART(TX/RX)──▶ [ESP32-C3 부트로더] → Flash 기록 → 재부팅

필요 조건:
  □ SBC의 UART 핀과 MCU의 UART 핀이 물리적 연결
  □ MCU의 시리얼 부트로더 진입 방법 (BOOT+RESET 제어)
  □ 플래싱 도구 (esptool.py, stm32flash 등)
  □ SBC에서 빌드 환경 또는 클라우드에서 .bin 수신

장점:
  + MCU에 특별한 OTA 펌웨어 불필요
  + 빈 MCU에도 직접 플래싱 가능
  + SBC가 중계 역할 → 인터넷 연결은 SBC만 하면 됨

단점:
  - 물리적 UART 연결 필수 (Shield 형태 권장)
  - MCU 부트로더 진입을 위한 GPIO 제어 필요 (BOOT, RESET)
  - 플래싱 시간 (ESP32-C3: ~10초)
  - 전용 펌웨어 빌드 필요

적합한 플랫폼: Type B (SBC+MCU Shield)
GPIO 제어:
  Pi GPIO → MCU BOOT 핀 (LOW로 부트로더 진입)
  Pi GPIO → MCU RESET 핀 (LOW→HIGH 리셋)
  Pi UART TX → MCU RX
  Pi UART RX → MCU TX
```

### ⑤ USB DFU (Device Firmware Update)

```
[PC/SBC] ──USB──▶ [MCU DFU 모드] → Flash 기록 → 재부팅

필요 조건:
  □ MCU가 USB DFU 지원 (STM32, nRF52840, RP2040)
  □ DFU 도구 (dfu-util, UF2)
  □ USB 물리적 연결

장점:
  + 별도 프로그래머 불필요 (USB 직접)
  + 빠른 전송 (USB 2.0)
  + RP2040의 UF2는 드래그&드롭으로 가능

단점:
  - USB 물리적 연결 필수 (무선 아님)
  - 바이브 코딩의 "무선" 가치와 충돌
  - 초기 설정 채널로는 적합, 배포 채널로는 비권장

적합한 플랫폼: 초기 부트로더 설치 (Bootstrap)
적합한 MCU: RP2040, STM32, nRF52840
```

### ⑥ HTTP Push (디바이스 내장 웹서버)

```
[스마트폰 브라우저] ──HTTP POST──▶ [MCU 웹서버] → 코드 수신 → 실행

필요 조건:
  □ MCU에 WiFi + HTTP 서버 내장
  □ 같은 네트워크에 접속
  □ MicroPython 또는 Lua 인터프리터 (코드 직접 실행)

장점:
  + 별도 앱 설치 불필요 (웹 브라우저만)
  + MicroPython이면 빌드 불필요
  + 웹 UI로 코드 편집 + 실행 가능

단점:
  - WiFi 필수
  - MicroPython 성능 제한
  - MCU 리소스 많이 사용 (HTTP 서버 + WiFi)

적합한 플랫폼: Type A (MCU 단독, MicroPython)
적합한 MCU: ESP32 + MicroPython, ESP32-C3 + MicroPython
```

```
│  • OLED 디스플레이 → 텍스트/그래프 표시                        │

│                                                                 │

```

## 3-4. 채널 3 — 초기 설정 채널 (Bootstrap Channel) [필수, 1회]

최초 1회만 사용하는 채널입니다. 이후 배포 채널로 전환됩니다.

```
┌─────────────────────────────────────────────────────────────────┐
│  Bootstrap = 최초 1회 "배포 채널을 열어주는" 설정               │
│                                                                 │
│  Type A (MCU):                                                  │
│    USB 케이블 → OTA 부트로더 플래싱                             │
│    → 이후 BLE OTA 또는 WiFi OTA로 전환                         │
│                                                                 │
│  Type B (SBC+MCU Shield):                                       │
│    Pi에 OS 설치 → SSH 활성화 → WiFi 설정                       │
│    → Shield 장착 → UART/GPIO 핀 매핑 확인                      │
│    → 이후 SSH + SCP로 Python 배포                              │
│    → MCU 부분은 UART 브릿지 또는 BLE OTA                       │
│                                                                 │
│  Type C (SBC 단독):                                             │
│    Pi에 OS 설치 → SSH 활성화 → WiFi 설정                       │
│    → Python + GPIO 라이브러리 설치                              │
│    → 이후 SSH + SCP로 Python 배포                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 3-5. 플랫폼 유형별 필수 통신 방식 매트릭스

| 통신 방식 | Type A (MCU) | Type B (SBC+MCU) | Type C (SBC) |
|-----------|:------------:|:-----------------:|:------------:|
| **BLE** | ★★★ 필수 | ☆ 선택 (MCU측) | ✕ 불필요 |
| **WiFi** | ★★ 권장 | ★★★ 필수 (Pi) | ★★★ 필수 |
| **USB Serial** | ★★★ Bootstrap | ★ 디버그 | ★ 디버그 |
| **UART** | ☆ 외부통신 | ★★★ Pi↔MCU | ✕ 불필요 |
| **I2C** | ★★ 센서/디스플레이 | ★★ 센서/디스플레이 | ★★ 센서 |
| **SPI** | ★ 확장 | ★ 확장 | ★ 확장 |
| **SSH** | ✕ 불필요 | ★★★ 필수 | ★★★ 필수 |
| **GPIO** | ★★★ LED/SW/BUZ | ★★★ LED/SW/BUZ | ★★ LED/SW |

## 3-6. 하드웨어 통신 요구사항 체크리스트

```

    □ WiFi OTA 가능? (WiFi 스택 내장 여부)

    □ UART 브릿지 가능? (SBC에 연결 가능 여부)
  □ 초기 설정 방법이 존재하는가?

[필수 — 없으면 교육 효과 저하]

  □ 입력 수단이 있는가?
    □ 버튼/스위치 최소 1개

[권장 — 있으면 교육 내용 풍부]
  □ 청각 피드백 (부저/스피커)
  □ 환경 센서 (온도/습도/조도)
  □ 통신 모듈 (LoRa/GPS/RFID)
  □ 모터/서보 (물리적 동작)

  □ 확장 커넥터 (SPI/I2C/UART 헤더)
```

# Part 6 — 교육 커리큘럼 설계

## 6-1. 레벨별 교육 단계

```
Level 1 — 체험 (바이브 코딩만)
  "LED를 깜빡여줘"를 입력하고 결과를 본다.
  코드를 전혀 보지 않는다.
  → 목표: "나도 하드웨어를 제어할 수 있다"는 자신감

Level 2 — 관찰 (코드 읽기)
  AI가 생성한 코드를 함께 읽으며, "어떻게 동작하는지"를 이해한다.
  코드를 수정하지 않는다.
  → 목표: 코드와 하드웨어 동작의 관계 이해

Level 3 — 수정 (코드 일부 변경)
  AI가 생성한 코드에서 숫자/값을 직접 변경해 본다.
  (깜빡임 속도, LED 색상, 센서 읽기 주기 등)
  → 목표: 변수, 함수 호출의 개념 이해

Level 4 — 작성 (코드 직접 쓰기)
  AI 도움 없이 직접 코드를 작성한다.
  막히면 AI에게 질문한다.
  → 목표: 독립적 프로그래밍 능력

Level 5 — 설계 (시스템 설계)
  여러 주변장치를 조합한 프로젝트를 설계한다.
  회로도를 읽고, 새로운 센서를 추가한다.
  → 목표: 시스템 사고, 문제 해결 능력
```

## 7-2. 시스템 프롬프트 자동 생성

보드 프로파일(JSON)에서 시스템 프롬프트를 자동 생성합니다:

```python
def generate_system_prompt(profile: dict) -> str:
    """보드 프로파일에서 Claude 시스템 프롬프트를 자동 생성"""

    peripherals_desc = "\n".join([
        f"  - {p['name']}: GPIO{p['gpio']}, {p['type']}, "
        f"사용법: {p['driver']}"
        for p in profile['peripherals']
    ])

    constraints_desc = "\n".join([
        f"  - {c}" for c in profile['constraints']
    ])

    if profile['framework'] == 'python':
        return f"""
당신은 {profile['board_name']} 보드용 Python 코드 작성자입니다.

보드 정보:
  MCU/SBC: {profile['mcu']['model']}
  프레임워크: Python (RPi.GPIO, smbus2)

사용 가능한 주변장치:
{peripherals_desc}

제약 조건:
{constraints_desc}

규칙:
1. board_config.py에 정의된 핀 번호를 import하여 사용합니다.
2. 코드만 출력합니다 (설명 없이).
3. main() 함수에서 시작합니다.
4. GPIO.cleanup()을 finally 블록에 포함합니다.
"""
    else:  # C / ESP-IDF
        return f"""
당신은 {profile['framework']} v{profile['framework_version']} 기반
{profile['mcu']['model']} 펌웨어 작성자입니다.

보드 정보:
  MCU: {profile['mcu']['model']} ({profile['mcu']['core']})
  Flash: {profile['mcu']['flash']}, RAM: {profile['mcu']['ram']}

사용 가능한 주변장치:
{peripherals_desc}

제약 조건:
{constraints_desc}

규칙:
1. board.h에 정의된 핀 매크로를 #include하여 사용합니다.
2. app_main() 함수에서 시작합니다.
3. {profile['framework']} API만 사용합니다.
4. 코드만 출력합니다 (설명 없이).
"""
```

## C-1. ESP-IDF (C) 용

```
당신은 ESP-IDF v{version} 기반 {mcu_model} 펌웨어 작성자입니다.

보드: {board_name}
MCU: {mcu_model} ({core}, {clock}MHz, Flash {flash}, RAM {ram})

사용 가능한 주변장치:
{peripherals_list}

I2C 버스: SDA=GPIO{sda}, SCL=GPIO{scl}, 주소: {devices}
SPI 버스: MOSI=GPIO{mosi}, MISO=GPIO{miso}, SCK=GPIO{sck}, CS=GPIO{cs}
UART: TX=GPIO{tx}, RX=GPIO{rx}

제약 조건:
{constraints_list}

규칙:
1. board.h를 #include하여 핀 매크로를 사용합니다.
2. app_main()에서 시작합니다.
3. ESP-IDF v{version} API만 사용합니다.
4. deprecated 함수를 사용하지 않습니다.
5. 코드만 출력합니다 (설명 없이).
6. OTA 부트로더 코드는 수정하지 않습니다.
7. partitions.csv는 수정하지 않습니다.
```

## C-2. Python (Raspberry Pi) 용

```
당신은 Raspberry Pi용 Python GPIO 프로그래머입니다.

보드: {board_name}
SBC: {sbc_model}, OS: {os}
Python: {python_version}

사용 가능한 주변장치:
{peripherals_list}

I2C 버스: SDA=GPIO{sda}(Pin{pin}), SCL=GPIO{scl}(Pin{pin})
디바이스: {i2c_devices}

사용 라이브러리:
  - RPi.GPIO (LED, 버튼, 부저)
  - smbus2 (I2C 센서)
  - luma.oled (OLED 디스플레이)
  - neopixel / rpi_ws281x (WS2812)
  - spidev (SPI)

규칙:
1. board_config.py에서 핀 번호를 import합니다.
2. main() 함수에서 시작합니다.
3. try/finally로 GPIO.cleanup()을 보장합니다.
4. 코드만 출력합니다 (설명 없이).
5. BCM 핀 번호 체계를 사용합니다.
```

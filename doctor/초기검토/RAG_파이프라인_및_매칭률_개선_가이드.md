# Part 1 — RAG 파이프라인이란?

---

## 1. RAG의 정의

### 1.1 RAG란?

**RAG (Retrieval-Augmented Generation)**은 한국어로 **"검색 증강 생성"**이라고 번역합니다.

> **LLM(대규모 언어 모델)이 답변을 생성하기 전에, 외부 데이터베이스에서 관련 정보를 먼저 "검색"한 뒤, 그 정보를 "참고"하여 더 정확한 답변을 "생성"하는 기술**

```
RAG = Retrieval    + Augmented + Generation
      (검색)         (증강)      (생성)

      관련 자료를     검색 결과로   최종 답변을
      먼저 찾아온다   보강한다      만들어낸다
```

### 1.2 한 줄 비유

```
RAG가 없는 LLM = 교과서 없이 시험 보는 학생 (기억에만 의존)
RAG가 있는 LLM = 교과서를 펼쳐놓고 시험 보는 학생 (찾아보고 답변)
```

### 1.3 이 프로젝트에서 RAG의 역할

```
[판독문 → SNOMED CT 자동변환 시스템에서]

  판독문 입력:  "S8에 2.3cm 크기의 HCC 의심 소견"
       │
       ▼
  RAG 파이프라인:
  ┌──────────────────────────────────────────────────┐
  │                                                    │
  │  1. SNOMED CT DB에서 "HCC" 관련 코드를 검색       │
  │  2. 검색된 후보 코드들을 LLM에게 전달              │
  │  3. LLM이 후보 중 가장 적합한 코드를 선택          │
  │                                                    │
  └──────────────────────────────────────────────────┘
       │
       ▼
  결과: 254637007 | Hepatocellular carcinoma (간세포암)
```

## 2. 왜 RAG가 필요한가?

### 2.1 LLM 단독 사용의 문제점

LLM(GPT-4o, Claude 등)은 매우 똑똑하지만, **치명적인 약점**이 있습니다.

```
[문제 1: 환각 (Hallucination)]

  LLM에게: "HCC의 SNOMED CT 코드가 뭐야?"

  LLM 답변: "254637999입니다."

  → 이 코드는 실제로 존재하지 않습니다!
  → LLM이 패턴을 학습해서 "그럴듯한" 번호를 지어낸 것
  → 의료 시스템에서 이런 실수는 매우 위험합니다
```

```
[문제 2: 학습 데이터의 한계]

  LLM의 학습 데이터에는 SNOMED CT의 35만+ 코드가
  모두 포함되어 있지 않을 수 있습니다.

  특히:
  • 최신 업데이트된 코드 (학습 데이터 이후에 추가된 것)
  • 드문 질환의 코드
  • 한국어 에디션 특유의 코드

  → LLM의 "기억"만으로는 정확한 코드를 보장할 수 없음
```

```
[문제 3: 버전 불일치]

  SNOMED CT는 연 2회 업데이트됩니다.
  LLM의 학습 데이터는 특정 시점에 고정되어 있습니다.

  → 2026년 1월에 새로 추가된 코드를
     2025년 데이터로 학습한 LLM은 알 수 없음
```

### 2.2 RAG가 이 문제들을 해결하는 방법

```
[RAG의 해결 방식]

  LLM의 "기억"에 의존하지 않고,
  실제 SNOMED CT 데이터베이스를 "검색"하여 참고합니다.

  ┌─────────────────────────────────────────────────┐
  │                                                   │
  │  문제 1 (환각) → 실제 DB에 있는 코드만 후보로    │
  │                  제시하므로, 없는 코드 생성 방지   │
  │                                                   │
  │  문제 2 (학습 한계) → DB에 35만+ 코드가 전부     │
  │                       있으므로 누락 없음           │
  │                                                   │
  │  문제 3 (버전) → DB를 최신 버전으로 유지하면      │
  │                  항상 최신 코드 반영 가능           │
  │                                                   │
  └─────────────────────────────────────────────────┘
```

## 3. RAG의 3단계 작동 원리

### 3.1 전체 흐름

```
┌─────────────────────────────────────────────────────────────────┐
│                  RAG의 3단계 작동 원리                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │ Step 1: Retrieval (검색)                                 │    │
│  │                                                          │    │
│  │  입력: "HCC 의심 소견"                                   │    │
│  │        ↓                                                 │    │
│  │  "HCC"를 벡터로 변환 → SNOMED CT 벡터 DB에서 검색       │    │
│  │        ↓                                                 │    │
│  │  결과: 유사한 코드 10개 추출                             │    │
│  │   • 254637007 | Hepatocellular carcinoma                 │    │
│  │   • 363346000 | Malignant neoplasm of liver              │    │
│  │   • 300332007 | Mass of liver                            │    │
│  │   • ... (7개 더)                                         │    │
│  └──────────────────────────┬───────────────────────────────┘    │
│                              ↓                                    │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │ Step 2: Augmented (증강)                                 │    │
│  │                                                          │    │
│  │  LLM에게 전달하는 프롬프트:                              │    │
│  │                                                          │    │
│  │  "다음 판독문을 SNOMED CT 코드로 매핑해주세요.           │    │
│  │   판독문: 'S8에 2.3cm HCC 의심 소견'                    │    │
│  │                                                          │    │
│  │   참고할 SNOMED CT 후보 코드 목록:                       │    │
│  │   1. 254637007 | Hepatocellular carcinoma                │    │
│  │   2. 363346000 | Malignant neoplasm of liver             │    │
│  │   3. 300332007 | Mass of liver                           │    │
│  │   ... (이하 생략)                                        │    │
│  │                                                          │    │
│  │   가장 적합한 코드를 선택하고 이유를 설명해주세요."      │    │
│  └──────────────────────────┬───────────────────────────────┘    │
│                              ↓                                    │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │ Step 3: Generation (생성)                                │    │
│  │                                                          │    │
│  │  LLM의 응답:                                             │    │
│  │  "254637007 | Hepatocellular carcinoma가 가장 적합합니다.│    │
│  │   이유: 'HCC'는 Hepatocellular carcinoma의 약어이며,    │    │
│  │   S8은 간의 segment 8을 의미합니다."                     │    │
│  │                                                          │    │
│  │  → 후보 목록 안에서 선택하므로 환각(없는 코드) 방지     │    │
│  └─────────────────────────────────────────────────────────┘    │
│                                                                   │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 각 단계를 일상 비유로 이해하기

```
[비유: 도서관에서 리포트 쓰기]

  Step 1: Retrieval (검색)
  → 도서관에 가서 "간암" 관련 책을 10권 찾아온다
  → 이 단계는 "검색 엔진"이 담당 (SapBERT + FAISS)

  Step 2: Augmented (증강)
  → 찾아온 책 10권을 책상 위에 펼쳐놓는다
  → "이 책들을 참고해서 리포트를 써주세요"라고 요청

  Step 3: Generation (생성)
  → 학생(LLM)이 펼쳐놓은 책을 참고하여 리포트를 작성한다
  → 책에 있는 내용만 인용하므로, 지어내는 실수가 줄어든다
```

### 3.3 핵심: "검색 범위를 좁히는 것"이 RAG의 본질

```
[RAG 없이]

  LLM이 35만+ SNOMED CT 코드 중에서 하나를 "기억"으로 선택
  → 마치 35만 권의 책이 있는 도서관에서 눈 감고 책을 고르는 것

[RAG 사용]

  먼저 관련 코드 10~20개를 검색으로 추출
  → LLM은 이 10~20개 중에서만 선택
  → 마치 사서가 관련 책 10권을 추려준 것

  선택지가 35만 → 10~20개로 줄어드므로 정확도가 크게 향상됨
```

## 4. SNOMED CT 자동변환에서의 RAG 구현

### 4.1 전체 시스템 구조

```
┌─────────────────────────────────────────────────────────────────────┐
│                   SNOMED CT RAG 파이프라인 전체 구조                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  [사전 준비 — 1회성 작업]                                            │
│                                                                       │
│  SNOMED CT 35만+ 용어                                                │
│       │                                                               │
│       ▼                                                               │
│  SapBERT 임베딩 모델로 각 용어를 "벡터"로 변환                       │
│       │                                                               │
│       ▼                                                               │
│  ┌──────────────────────────────┐                                    │
│  │  FAISS 벡터 데이터베이스     │ ← 35만 개 벡터가 저장됨            │
│  │  (검색 엔진 역할)            │                                    │
│  └──────────────────────────────┘                                    │
│                                                                       │
│  ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─  │
│                                                                       │
│  [실시간 처리 — 판독문이 들어올 때마다]                              │
│                                                                       │
│  판독문: "S8에 2.3cm HCC 의심 소견"                                  │
│       │                                                               │
│       ▼                                                               │
│  [1단계] NER 엔진 (BioBERT/KoBERT)                                   │
│       │  → 엔티티 추출: "S8"(부위), "2.3cm"(크기), "HCC"(진단)      │
│       ▼                                                               │
│  [2단계] 벡터 검색 (SapBERT + FAISS)                                 │
│       │  → "HCC" 벡터와 가장 유사한 SNOMED CT 코드 10~20개 추출     │
│       ▼                                                               │
│  [3단계] LLM 판단 (GPT-4o / Claude API)                              │
│       │  → 후보 코드 목록 + 판독문 원문을 함께 전달                  │
│       │  → LLM이 가장 적합한 코드를 선택 + 이유 설명                 │
│       ▼                                                               │
│  [4단계] 온톨로지 검증 (SNOMED CT IS-A 그래프)                       │
│       │  → 선택된 코드가 논리적으로 유효한지 확인                    │
│       │  → 예: "HCC" 코드인데 위치가 "뇌"이면 → 차단               │
│       ▼                                                               │
│  [5단계] 신뢰도 스코어링                                             │
│       │  → 고신뢰(95%+): 자동 확정                                   │
│       │  → 저신뢰(<70%): 사람 검토로 전달                            │
│       ▼                                                               │
│  최종 출력: 254637007 | Hepatocellular carcinoma (신뢰도 96%)        │
│                                                                       │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 벡터(Vector)란? — 초보자를 위한 설명

```
"벡터"는 단어의 의미를 숫자 배열로 표현한 것입니다.

예시:
  "간세포암" → [0.82, 0.15, -0.34, 0.91, ..., 0.23]  (768개 숫자)
  "HCC"     → [0.80, 0.17, -0.31, 0.89, ..., 0.25]  (768개 숫자)
  "감기"    → [0.12, 0.65, 0.48, -0.22, ..., 0.67]  (768개 숫자)

  "간세포암"과 "HCC"의 숫자 배열이 매우 비슷함!
  → 컴퓨터가 "이 두 단어는 비슷한 의미구나"라고 판단 가능

  "간세포암"과 "감기"의 숫자 배열은 매우 다름
  → 컴퓨터가 "이 두 단어는 관련 없구나"라고 판단

비유:
  GPS 좌표처럼, 의미가 비슷한 단어들은
  "의미 공간"에서 가까운 곳에 위치합니다.

  [의미 공간 지도]

     간세포암 ●●HCC          ← 거의 같은 위치 (의미 유사)
              ●간암

                     ●간경변  ← 조금 떨어져 있음 (관련은 있음)


                                          ●감기  ← 멀리 있음 (관련 없음)
```

### 4.3 FAISS란?

```
FAISS (Facebook AI Similarity Search)

= Meta(구 Facebook)가 만든 초고속 벡터 검색 엔진

역할: 35만 개의 SNOMED CT 벡터 중에서
      입력 벡터와 가장 가까운(의미가 유사한) 것을 찾아줌

성능: 35만 개에서 가장 유사한 10개를 찾는 데 → 수 밀리초(0.00X초)

비유: 도서관에서 "간세포암"과 가장 관련 있는 책 10권을
      0.01초 만에 찾아주는 초고속 사서
```

## 5. RAG vs LLM 단독 — 성능 비교

### 5.1 수치 비교

| 방식 | 유효 매칭률 | 정확 매칭률 | 환각 위험 | 최신 코드 반영 |
|------|:---:|:---:|:---:|:---:|
| **LLM 단독** (GPT-4o만) | ~80% | ~35% | 높음 | 불가능 |
| **벡터 검색 단독** (SapBERT+FAISS만) | ~87% | ~45% | 없음 | 가능 |
| **RAG** (벡터 검색 + LLM) | **96.2%** | **57.6%** | 매우 낮음 | 가능 |

### 5.2 각 방식의 장단점

```
[LLM 단독]
  장점: 문맥 이해력 뛰어남, 약어 해석 잘함
  단점: 없는 코드를 지어냄(환각), 학습 데이터에 없는 코드 모름
        ↓
  "머리는 좋은데 교과서가 없는 학생"


[벡터 검색 단독]
  장점: 실제 존재하는 코드만 반환, 빠름
  단점: 문맥을 이해하지 못함, "가장 비슷한 단어"만 찾을 뿐
        ↓
  "교과서는 있는데 문제를 이해 못하는 학생"


[RAG = 벡터 검색 + LLM]
  장점: 실제 코드 기반 + 문맥 이해 = 최고 성능
  단점: 시스템 복잡도 증가, 비용 증가
        ↓
  "교과서를 펼쳐놓고 문제를 이해하며 푸는 우등생"
```

### 5.3 실제 예시로 비교

```
판독문: "Rt. lower lobe에 patch opacity. r/o pneumonia."

[LLM 단독]
  → "233604007 | Pneumonia"
  → 대략 맞지만, "r/o (rule out)"를 무시하고 확정 진단으로 처리
  → ❌ 실제로는 "의심"이지 "확정"이 아님

[벡터 검색 단독]
  → "pneumonia" 검색 → 233604007, 385093006, 233607000 등 반환
  → 어느 것이 맞는지 선택하지 못함 (유사도 점수만 제공)
  → △ 후보는 맞지만 최종 판단 불가

[RAG]
  → 벡터 검색으로 폐렴 관련 코드 10개 추출
  → LLM에게 "r/o = rule out, 즉 의심 단계"라는 맥락 해석 요청
  → LLM: "233604007 | Pneumonia + 확실성: 415684004 | Suspected"
  → ✅ 질환 코드 + "의심" 상태까지 정확히 매핑
```

## 7. 유효 매칭 vs 정확 매칭 — 차이 이해하기

### 7.1 두 수치의 의미

```
[유효 매칭 (Valid Match) — 96.2%]

  AI가 추천한 코드가 "의미적으로 관련이 있는" 코드인 경우

  판독문: "간세포암(HCC) 의심"
  AI 추천: 363346000 | Malignant neoplasm of liver (간의 악성 신생물)
  → 정확히 HCC 코드는 아니지만, "간 악성종양"이니까 관련은 있음
  → ✅ 유효 매칭으로 인정


[정확 매칭 (Exact Match) — 57.6%]

  AI가 추천한 코드가 "정확히 그 개념과 1:1 대응"하는 경우

  판독문: "간세포암(HCC) 의심"
  AI 추천: 254637007 | Hepatocellular carcinoma (간세포암)
  → 정확히 HCC를 가리키는 코드
  → ✅ 정확 매칭
```

### 7.2 과녁 비유

```
                 ┌──────────────────────────┐
                 │                          │
                 │    ┌──────────────┐      │
                 │    │              │      │
                 │    │   ┌──────┐  │      │
                 │    │   │  ◉   │  │      │
                 │    │   │ 정확 │  │      │
                 │    │   │매칭  │  │      │
                 │    │   └──────┘  │      │
                 │    │  유효 매칭   │      │
                 │    └──────────────┘      │
                 │      완전 빗나감          │
                 └──────────────────────────┘

  정확 매칭 (57.6%) = 정중앙을 맞춤 (정확한 코드)
  유효 매칭 (96.2%) = 빨간 원 안에 들어옴 (관련 있는 코드)
  나머지 (3.8%)    = 과녁을 완전히 빗나감 (관련 없는 코드)
```

### 7.3 의료 현장에서의 영향

```
[유효 매칭만 되고 정확 매칭이 안 된 경우]

  판독문: "좌하엽의 대엽성 폐렴"
  AI 추천: 233604007 | Pneumonia (일반 폐렴)
  정답:    278516003 | Lobar pneumonia (대엽성 폐렴)

  → "폐렴"이라는 큰 카테고리는 맞지만, "대엽성"이라는 세부 정보 손실
  → 유효 매칭 ✅ / 정확 매칭 ❌

  영향:
  • 통계: "대엽성 폐렴이 올해 몇 건?" → 집계 불가
  • 연구: 대엽성 폐렴 vs 기관지 폐렴 비교 연구 → 데이터 부정확
  • 청구: ICD-10 매핑 시 J18.1(대엽성) 대신 J18.9(상세불명) → 정보 손실

  → 유효 매칭만으로는 "대충 맞는" 수준이므로,
     정확 매칭률을 높이는 것이 시스템의 핵심 목표
```

## 8. 낮은 정확 매칭률의 5가지 원인

### 원인 1: SNOMED CT의 과도한 세분화 (Granularity 문제)

```
SNOMED CT에는 35만+ 개념이 있고, 비슷한 코드가 너무 많습니다.

예시: 의사가 "폐렴"이라고 썼을 때

  AI가 선택할 수 있는 후보 코드들:
  ┌──────────────────────────────────────────────────────┐
  │  233604007  Pneumonia (disorder)     ← 일반 폐렴     │
  │  385093006  Community-acquired pneumonia              │
  │  233607000  Bacterial pneumonia                       │
  │  75570004   Viral pneumonia                           │
  │  278516003  Lobar pneumonia                           │
  │  396286009  Bronchopneumonia                          │
  │  441590008  Hospital-acquired pneumonia               │
  │  422588002  Aspiration pneumonia                      │
  │  ...        (수십 개 더)                              │
  └──────────────────────────────────────────────────────┘

  의사의 의도: 233604007 (일반 폐렴)
  AI의 선택:   385093006 (지역사회 획득 폐렴)

  → "폐렴"이라는 의미에서 관련은 있음 → 유효 매칭 ✅
  → 하지만 정확히 의도한 코드는 아님 → 정확 매칭 ❌
```

**핵심 문제:**
판독문에 "폐렴"이라고만 적혀 있으면, AI는 수십 개의 폐렴 코드 중 **"어느 수준의 코드"**를 선택해야 하는지 판단할 근거가 부족합니다.

### 원인 2: 한국어 판독문의 모호성과 비표준 약어

```
한국어 판독문은 매우 축약적이고, 병원마다 스타일이 다릅니다.

실제 판독문 예시:
  "Rt. lower lung에 patch opacity. r/o pneumonia."

  AI가 해석해야 할 것:
  ├── "Rt."          → Right (오른쪽)
  ├── "lower lung"   → 하엽? 하폐야? (어느 엽(lobe)인지 불명확)
  ├── "patch opacity" → 반점형 음영 (SNOMED CT에 정확히 뭘로 매핑?)
  └── "r/o"          → Rule out (배제 필요) = "의심" 단계

  문제점들:
  ┌────────────────────────────────────────────────────────┐
  │                                                          │
  │  1. 한/영 혼용: "Rt. lower lung에 patch opacity"        │
  │     → 한국어와 영어가 섞여 있어 NER 모델 혼란           │
  │                                                          │
  │  2. 기관별 약어 차이:                                    │
  │     서울대: "r/o"                                        │
  │     삼성:   "S/O" (suggestive of)                        │
  │     세브란스: "c/w" (consistent with)                     │
  │     → 같은 "의심"인데 표현이 모두 다름                   │
  │                                                          │
  │  3. 동의 표현 다양성:                                    │
  │     opacity = haziness = infiltration = consolidation    │
  │     → 다 "폐에 뭔가 보인다"는 뜻인데 표현이 다름        │
  │                                                          │
  └────────────────────────────────────────────────────────┘
```

### 원인 3: 1:N 매핑 문제 (하나의 표현 → 여러 후보 코드)

```
판독문의 하나의 표현이 SNOMED CT에서 여러 코드에 대응될 수 있습니다.

예시: "간 종괴 (liver mass)"

  SNOMED CT 후보:
  ├── 300332007 | Mass of liver         (간 종괴)     ← finding
  ├── 254637007 | Hepatocellular carcinoma (간세포암)  ← disorder
  ├── 363346000 | Malignant neoplasm of liver (간 악성) ← disorder
  ├── 92546004  | Benign neoplasm of liver (간 양성)    ← disorder
  └── 119321005 | Lesion of liver       (간 병변)     ← finding

  어떤 것이 "정답"인가?

  • 영상에서 덩어리만 보인 단계 → 300332007 (Mass of liver)
  • 악성이 의심되는 단계       → 363346000 (Malignant neoplasm)
  • HCC로 확진된 단계         → 254637007 (Hepatocellular carcinoma)

  → 맥락(context)을 깊이 이해해야만 판단 가능
  → AI는 "대충 관련 있는 코드"를 찾는 것은 잘하지만
     "정확히 이 코드"를 고르는 것은 어려움
```

### 원인 4: 의미 유형(Semantic Type) 혼동

```
SNOMED CT에서 같은 질환이라도 다른 "관점"으로 코딩됩니다.

  (disorder)   233604007 | Pneumonia    — "질환"으로서의 폐렴
  (finding)    다른 코드  | Pneumonia    — "소견"으로서의 폐렴
  (situation)  다른 코드  | Hx of pneumonia — 폐렴 "병력"

판독문: "폐렴 소견 있음"

  → disorder로 코딩? (질환이 있다)
  → finding으로 코딩? (소견이 보인다)

  의사의 의도:
  "X-ray에서 폐렴처럼 보이는 소견이 있다"
  → finding이 더 적합할 수 있음

  하지만 AI는 가장 흔한 코드인 disorder 코드를 선택하는 경향
  → 유효 매칭 ✅ (폐렴 관련) / 정확 매칭 ❌ (semantic type 틀림)
```

### 원인 5: LLM의 환각 + 코드 혼동

```
LLM(GPT-4o 등)은 가끔 실제로 존재하지 않는 코드를 만들어냅니다.

예시 1 — 존재하지 않는 코드 생성:
  AI: "SNOMED CT 코드 233604999 — Severe bilateral pneumonia"
  → 233604999라는 코드는 SNOMED CT에 존재하지 않음!
  → LLM이 "그럴듯한" 번호를 생성한 것 (환각)

예시 2 — 비슷한 코드 혼동:
  정답:     233604007 | Pneumonia
  AI 선택:  233607000 | Bacterial pneumonia
  → 숫자가 비슷해서 혼동 (233604 vs 233607)
  → 유효 매칭 ✅ / 정확 매칭 ❌

  이것이 온톨로지 검증(IS-A 그래프 확인)이 필요한 이유:
  → 해당 코드가 실제 존재하는지 확인
  → 존재하지 않으면 차단
```

### 5가지 원인 요약표

| # | 원인 | 핵심 문제 | 비유 |
|---|------|----------|------|
| 1 | SNOMED CT 과도한 세분화 | 비슷한 코드가 너무 많음 (35만+) | 100종류의 비슷한 파란색 중 하나를 고르는 것 |
| 2 | 판독문 모호성/약어 | 한/영 혼용, 기관별 약어 차이 | 방언이 섞인 문서를 표준어로 번역하는 것 |
| 3 | 1:N 매핑 | 하나의 표현 → 여러 후보 코드 | "과일" → 사과? 배? 포도? 맥락 없이 선택 |
| 4 | 의미 유형 혼동 | disorder/finding/situation 구분 어려움 | "폐렴"이 질환인지 소견인지 병력인지 |
| 5 | LLM 환각/혼동 | 없는 코드 생성, 비슷한 코드 착각 | 기억에 의존해서 전화번호 한 자리 틀리는 것 |

## 9. 개선 방향 5가지

### 개선 1: 도메인 특화 + 범위 축소 전략

```
[현재: 전체 SNOMED CT 35만+ 코드 대상]

  35만 개 중에서 정확히 하나를 고르는 것은 매우 어려움
  마치 서울 전체에서 특정 건물 하나를 찾는 것


[개선: 특정 장기/질환군으로 범위 축소]

  예: 간(Liver) 질환만 대상으로 하면
  → 관련 SNOMED CT 코드가 ~500개 수준
  → 500개 중 하나를 고르는 것은 훨씬 쉬움
  마치 강남구에서 특정 건물 하나를 찾는 것

  확장 순서 (문서의 로드맵):
  ┌────────────────────────────────────────────┐
  │  1단계: 간(Liver) 질환                     │ ← 가장 좁은 범위
  │  2단계: 폐(Lung) 질환                      │
  │  3단계: 뇌(Brain) 질환                     │
  │  4단계: 복부(Abdomen) 질환                 │
  │  ...                                       │
  │  최종: 전체 영역                           │ ← 점진적 확장
  └────────────────────────────────────────────┘

  각 단계에서 높은 정확도를 달성한 후 다음 단계로 확장
```

**예상 효과:**

| 범위 | 후보 코드 수 | 예상 정확 매칭률 |
|------|:---:|:---:|
| 전체 SNOMED CT | 35만+ | 57.6% |
| 간(Liver) 특화 | ~500 | **80~85%** |
| 간 + 폐 특화 | ~1,200 | **75~80%** |

### 개선 2: Human-in-the-Loop (사람 검증 워크플로우)

```
┌──────────────────────────────────────────────────────────────┐
│                                                                │
│  AI가 코드를 추천할 때, 신뢰도 점수를 함께 출력합니다.       │
│  신뢰도에 따라 3가지 경로로 분기합니다.                      │
│                                                                │
│  ┌─ 신뢰도 95%+ (고신뢰) ──────────────────────────────┐    │
│  │                                                       │    │
│  │   AI 판단: "254637007 | HCC, 신뢰도 97%"            │    │
│  │   → 자동 확정 ✅                                     │    │
│  │   → 사람 검토 불필요                                  │    │
│  │   → 전체의 약 40~50%가 이 경로                       │    │
│  │                                                       │    │
│  └───────────────────────────────────────────────────────┘    │
│                                                                │
│  ┌─ 신뢰도 70~95% (중간) ─────────────────────────────┐    │
│  │                                                       │    │
│  │   AI 판단: "후보 3개 제시"                           │    │
│  │   1. 254637007 | Hepatocellular carcinoma (82%)      │    │
│  │   2. 363346000 | Malignant neoplasm of liver (11%)   │    │
│  │   3. 300332007 | Mass of liver (7%)                   │    │
│  │                                                       │    │
│  │   → 코더(사람)가 화면에서 클릭으로 선택              │    │
│  │   → 수초~수십 초 만에 검토 완료                      │    │
│  │   → 전체의 약 35~40%가 이 경로                       │    │
│  │                                                       │    │
│  └───────────────────────────────────────────────────────┘    │
│                                                                │
│  ┌─ 신뢰도 70% 미만 (저신뢰) ────────────────────────┐     │
│  │                                                       │    │
│  │   AI 판단: "확신 없음, 전문가 검토 필요"             │    │
│  │   → 전문의에게 직접 검토 요청                        │    │
│  │   → 검토 결과가 다시 모델 학습에 피드백              │    │
│  │   → 전체의 약 10~20%가 이 경로                       │    │
│  │                                                       │    │
│  └───────────────────────────────────────────────────────┘    │
│                                                                │
│  핵심: 100% 자동화를 목표로 하지 않고,                       │
│        AI + 사람의 협업으로 효율과 정확도를 동시에 달성       │
│                                                                │
└──────────────────────────────────────────────────────────────┘
```

**왜 100% 자동화가 아닌가?**

```
의료 분야에서 100% 자동화는:
  • 규제적으로 어려움 (의료기기 인허가 필요)
  • 의학적으로 위험 (잘못된 코드 → 잘못된 치료)
  • 법적으로 문제 (AI 오류의 책임 소재)

따라서 현실적인 접근:
  → AI가 80~90%의 작업을 자동 처리 (효율 향상)
  → 나머지 10~20%는 사람이 검토 (안전 확보)
  → 결과적으로 최종 정확도 99%+ 달성 가능
```

### 개선 3: 피드백 루프 (전문의 수정 → 모델 재학습)

```
[선순환 구조]

  ┌──────────────────────────────────────────────────────┐
  │                                                        │
  │  AI 추천 ──→ 전문의 수정 ──→ 수정 데이터 축적        │
  │     ↑                              │                   │
  │     │                              ▼                   │
  │     └──── 모델 재학습 ◄──── 학습 데이터 업데이트      │
  │                                                        │
  └──────────────────────────────────────────────────────┘
```

**시간에 따른 정확도 향상 예상:**

      │

      │                                     ●

      │                           ●

      │                 ●

      │       ●

### 개선 4: 기관별 커스텀 사전 + 전이학습

```
[문제: 병원마다 같은 것을 다르게 표현]

  서울대병원:  "HCC s/p TACE"
  세브란스:    "Hepatocellular ca, post-TACE"
  삼성서울:    "간세포암, TACE 시행 후"
  지방 병원:   "liver ca. TACE done"

  → 전부 같은 뜻인데 AI는 다른 표현으로 인식할 수 있음


[해결: 병원별 맞춤 사전 + 전이학습]

  ┌─────────────────────────────────────────────────┐
  │  기본 모델 (공통)                                │
  │  └── 전체 병원에 공통적인 의학 용어 학습         │
  │                                                   │
  │  + 서울대병원 어댑터                              │
  │    └── "s/p" = status post, "HCC" = 254637007   │
  │                                                   │
  │  + 세브란스 어댑터                                │
  │    └── "ca" = carcinoma, "post-" = s/p           │
  │                                                   │
  │  + 삼성서울 어댑터                                │
  │    └── 한글 위주 판독문, "시행 후" = post-        │
  │                                                   │
  └─────────────────────────────────────────────────┘

  각 병원의 판독문 스타일을 별도로 학습하여
  기관별 정확도를 높이는 전이학습(Transfer Learning) 적용
```

**전이학습이란?**

```
비유: 영어를 잘하는 사람이 프랑스어를 배울 때

  영어 실력(기본 모델) → 프랑스어 학습(어댑터)
  → 영어 모르는 사람보다 훨씬 빨리 프랑스어를 배움

마찬가지로:
  일반 의학 NLP(기본 모델) → 서울대병원 판독문(어댑터)
  → 처음부터 서울대 전용 모델을 만드는 것보다 빠르고 정확함
```

### 개선 5: 다단계 후보 재순위화 (Re-ranking)

```
[현재: 1~2단계로 바로 최종 코드 선택]

  벡터 검색 → LLM 선택 → 끝
  → 35만 개에서 바로 1개를 고르려니 어려움


[개선: 4단계로 점진적 좁히기]

  ┌─────────────────────────────────────────────────┐
  │                                                   │
  │  1단계: 벡터 검색 (SapBERT + FAISS)              │
  │  "HCC" → 후보 100개 추출 (넓은 그물)             │
  │                                                   │
  │  ↓ 100개                                         │
  │                                                   │
  │  2단계: 도메인 필터                               │
  │  100개 중 → 간(Liver) 관련 코드만 필터링          │
  │  → 30개로 축소                                    │
  │                                                   │
  │  ↓ 30개                                          │
  │                                                   │
  │  3단계: LLM 재순위화 (GPT-4o + RAG)              │
  │  30개 → 판독문 맥락과 가장 맞는 상위 5개 선별    │
  │                                                   │
  │  ↓ 5개                                           │
  │                                                   │
  │  4단계: 온톨로지 검증 (IS-A 그래프)              │
  │  5개 → 논리적으로 유효한 1~2개만 남김            │
  │  예: 부위가 "간"인데 "폐" 코드 → 제거            │
  │                                                   │
  │  ↓ 1~2개                                         │
  │                                                   │
  │  5단계: 신뢰도 스코어링                          │
  │  → 고신뢰(95%+): 자동 확정                       │
  │  → 저신뢰(<70%): 사람 검토                       │
  │                                                   │
  └─────────────────────────────────────────────────┘
```

**단계별 정확도 향상 효과:**

| 단계 | 후보 수 | 정확 매칭률 (예상) |
|------|:---:|:---:|
| 벡터 검색만 | 100개 | ~45% |
| + 도메인 필터 | 30개 | ~55% |
| + LLM 재순위화 | 5개 | ~70% |
| + 온톨로지 검증 | 1~2개 | **~80%** |
| + Human-in-the-Loop | 최종 | **~99%** |

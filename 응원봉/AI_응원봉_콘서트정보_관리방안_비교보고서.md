# AI 응원봉 콘서트 정보 관리 방안 비교 보고서

**작성일:** 2026-02-24
**목적:** 다양한 팬 질문에 자연스럽게 대응하기 위한 최적의 방법 도출

---

## 1. 문제 정의

### 1.1 핵심 문제

```
사용자 질문: "다음 곡 뭐야?"
              ↓
AI(Gemini)가 정확히 답변하려면?
              ↓
현재 콘서트의 셋리스트, 현재 곡 정보가 필요!
              ↓
이 정보를 어떻게 수집하고 AI에게 전달할 것인가?
```

### 1.2 대응해야 할 질문 유형

| 카테고리 | 질문 예시 | 필요한 정보 |
|----------|-----------|-------------|
| 셋리스트 | "다음 곡 뭐야?", "몇 곡 남았어?" | 셋리스트, 현재 곡 순서 |
| 응원법 | "이 곡 응원법 알려줘", "떼창 구간 언제야?" | 곡별 응원법, 가사, 타이밍 |
| 아티스트 | "진 생일 언제야?", "RM 본명이 뭐야?" | 멤버 프로필 정보 |
| 콘서트 | "앵콜 보통 몇 곡 해?", "오늘 특별 게스트 있어?" | 공연 정보, 과거 데이터 |
| 팬덤 문화 | "보라해가 무슨 뜻이야?" | 팬덤 용어 사전 |

### 1.3 자연스러운 대응의 조건

1. **정확성**: 틀린 정보 제공 금지
2. **실시간성**: 현재 곡에 맞는 정보 제공
3. **맥락 이해**: 이전 대화 기억, 자연스러운 흐름
4. **포괄성**: 다양한 질문에 대응 가능
5. **개인화**: 최애 멤버 등 개인 정보 반영

## 3. 방법 2: RAG (Retrieval-Augmented Generation)

### 3.1 개념

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                  │
│   RAG = 검색(Retrieval) + 생성(Generation)                       │
│                                                                  │
│   "질문과 관련된 정보를 먼저 검색하고,                            │
│    그 정보를 바탕으로 AI가 답변을 생성한다"                        │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘

┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   사용자      │     │   검색 엔진   │     │   Gemini     │
│   질문       │ ──► │  (관련 정보   │ ──► │   (답변      │
│              │     │   찾기)      │     │   생성)      │
└──────────────┘     └──────────────┘     └──────────────┘
       │                    │                    │
       ▼                    ▼                    ▼
"진 생일 언제야?"     "진: 12월 4일,       "진 오빠 생일은
                      본명 김석진..."       12월 4일이에요! 🎂"
```

### 3.2 동작 원리

```
STEP 1: 지식 베이스 구축 (사전 준비)
────────────────────────────────────────────────────────────
모든 정보를 벡터 임베딩으로 변환하여 저장

문서 예시:
- "BTS 진의 생일은 12월 4일이다. 본명은 김석진이다."
- "Dynamite의 응원법: 0:45초에 떼창, 응원색은 보라색"
- "보라해는 BTS와 아미의 사랑을 상징하는 표현이다"

        ↓ 임베딩 변환

벡터 DB에 저장:
[0.23, 0.45, 0.12, ...] → "진 생일 정보"
[0.67, 0.33, 0.89, ...] → "Dynamite 응원법"
[0.11, 0.78, 0.56, ...] → "보라해 의미"


STEP 2: 질문 처리 (실시간)
────────────────────────────────────────────────────────────
사용자: "진 생일 언제야?"
        ↓
질문을 벡터로 변환: [0.25, 0.44, 0.15, ...]
        ↓
벡터 DB에서 유사한 문서 검색
        ↓
가장 관련 있는 문서 찾음: "BTS 진의 생일은 12월 4일..."
        ↓
검색된 문서 + 질문을 Gemini에 전달
        ↓
Gemini 답변: "진 오빠 생일은 12월 4일이에요! 🎂"
```

### 3.4 구현 예시 (Python 서버)

```python
from langchain.vectorstores import Chroma
from langchain.embeddings import OpenAIEmbeddings
from langchain.chat_models import ChatGoogleGenerativeAI

class RAGSystem:
    def __init__(self):
        # 벡터 DB 초기화
        self.embeddings = OpenAIEmbeddings()
        self.vectorstore = Chroma(
            collection_name="kpop_knowledge",
            embedding_function=self.embeddings
        )
        self.llm = ChatGoogleGenerativeAI(model="gemini-2.0-flash")

    def add_knowledge(self, documents):
        """지식 베이스에 문서 추가"""
        self.vectorstore.add_documents(documents)

    def query(self, question, current_context):
        """질문에 답변"""
        # 1. 관련 문서 검색
        relevant_docs = self.vectorstore.similarity_search(question, k=3)

        # 2. 프롬프트 구성
        context = "\n".join([doc.page_content for doc in relevant_docs])

        prompt = f"""
당신은 K-POP 콘서트 AI 비서입니다.

## 현재 상황
{current_context}

## 관련 정보
{context}

## 질문
{question}

## 규칙
- 관련 정보를 바탕으로 답변
- 정보가 없으면 "잘 모르겠어요"라고 솔직히 답변
- 친근하게 1-2문장으로 답변
"""

        # 3. Gemini로 답변 생성
        response = self.llm.invoke(prompt)
        return response.content
```

| 항목 | 내용 |
|------|------|
| **장점** | |
| ✅ 확장성 | 무한한 지식 추가 가능 |
| ✅ 정확성 | 관련 정보만 정확히 검색 |
| ✅ 토큰 절약 | 필요한 정보만 프롬프트에 포함 |

### 3.6 적합한 상황

- **풍부한 지식 베이스**: 응원법, 가사, 팬덤 문화 등
- **상용화 단계**: 정확하고 다양한 답변 필요

### 4.4 스마트 캐싱 전략

```kotlin
class HybridDataManager {

    // Layer 1: 앱 내장 데이터
    private val embeddedData = loadFromAssets("kpop_base_data.json")

    // Layer 2: 로컬 캐시
    private val localCache = Room.databaseBuilder(...)

    // Layer 3: 클라우드 서버
    private val cloudApi = RetrofitClient.create(CloudApi::class.java)

    suspend fun getData(query: String, category: String): String {
        return when (category) {
            "member_info" -> {
                // 1순위: 로컬 내장 데이터 (항상 빠름)
                embeddedData.members[query] ?: "정보 없음"
            }
            "setlist" -> {
                // 1순위: 로컬 캐시
                localCache.getSetlist() ?: run {
                    // 2순위: 서버에서 다운로드 후 캐시
                    val data = cloudApi.getSetlist(concertId)
                    localCache.saveSetlist(data)
                    data
                }
            }
            "realtime" -> {
                // 항상 서버에서 가져옴
                cloudApi.getCurrentSong(concertId)
            }
            else -> embeddedData.search(query)
        }
    }

    // 공연 시작 전 데이터 미리 다운로드
    suspend fun preloadConcertData(concertId: String) {
        val setlist = cloudApi.getSetlist(concertId)
        val cheerMethods = cloudApi.getCheerMethods(concertId)
        localCache.saveAll(setlist, cheerMethods)
    }
}
```

### 4.6 장단점

| 항목 | 내용 |
|------|------|
| **장점** | |
| ✅ 빠른 응답 | 기본 정보는 로컬에서 즉시 |
| ✅ 오프라인 지원 | 핵심 기능은 인터넷 없이 동작 |
| ✅ 확장 가능 | 필요 시 클라우드 기능 추가 |
| ✅ 비용 효율 | 자주 쓰는 건 로컬, 가끔 쓰는 건 클라우드 |
| **단점** | |
| ❌ 구현 복잡 | 여러 계층 관리 필요 |
| ❌ 동기화 이슈 | 로컬/클라우드 데이터 불일치 가능 |
| ❌ 개발 기간 | 단순 방법보다 오래 걸림 |

### 4.7 적합한 상황

- **MVP 이후 확장**: 처음엔 로컬만, 점점 클라우드 추가
- **다양한 환경 대응**: 오프라인/온라인 모두 지원
- **상용화 준비**: 안정성과 확장성 모두 필요
